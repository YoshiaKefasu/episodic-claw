## 2. 分割方針（YAGNI / KISS）

### 実装ガード（CRITICAL）

- **v0.4.29e では `PYTHON` と「スクリプトによるファイル編集/書込み」を禁止する。**
- 禁止対象の例:
  - `python -c` / `python script.py` でのテストファイル自動書換え
  - `node -e` / `pwsh` ワンライナーでの一括置換・上書き
  - 自動生成スクリプト経由での `test_phase4_5.ts` 分割書換え
- 許可対象:
  - `apply_patch` / 手動差分による明示的な編集のみ

**理由**: 直近でスクリプト編集により括弧崩れ・環境変数復元漏れが発生し、`npm test` 連鎖停止を引き起こしたため。

### Option A（推奨）: 機能責務ごとの4分割 + 薄い集約ランナー

分割対象:

1. `test_phase4_5_gateway_runtime.ts`
   - gateway_start/stop, runtime mode, startup/shutdown 系
2. `test_phase4_5_retriever_anchor.ts`
   - retriever runtime/source smoke, recall/query/anchor 系
3. `test_phase4_5_narrative_worker.ts`
   - language guard, retry phases, empty rawText, queue lease/save 系
4. `test_phase4_5_cache_compaction_segmenter.ts`
   - cache queue smoke, compaction, idle flush, segmenter 系

互換ランナー:

- `test_phase4_5.ts` は薄い orchestrator に縮小
  - 各分割ファイルの `runXxx()` を順番に呼ぶだけ

**理由**: 既存の `npm test` 入口を変えずに保守性を上げられる。

### Option B: いきなり完全撤去して新エントリへ置換

- `test_phase4_5.ts` を削除し、`package.json` を新ファイル群へ直結

**非推奨理由**: 変更面積が大きく、回帰時の復旧コストが上がる。

### 🛤️ Solution Options

#### Option A — 責務ごとの4分割 + 薄い集約ランナー *(推奨)*
**Approach**: `test_phase4_5.ts` を機能単位（Gateway, Retriever, NarrativeWorker, Cache等）の4ファイルに分割し、共通関数は shared に逃がす。旧ファイルはこれらを順番に呼び出すだけのランナーにする。  
**Implementation cost**: Medium  
**Risk**: Medium (import/export の繋ぎ込みや、グローバルな mock/spy の漏れに注意が必要)  
**Why recommended**: 呼び出し口（`npm test`）を変えずに中身だけを疎結合化できるため、既存のエコシステム（CIや開発者の手癖）を壊さずに保守性を劇的に向上できる。  

#### Option B — 巨大ファイルを削除し、package.json に完全委譲
**Approach**: `package.json` の `test` スクリプトに `&& node test_gateway.ts && node test_retriever.ts ...` と数珠繋ぎに書く。  
**Implementation cost**: Medium  
**Risk**: High (Windows 環境での `&&` 解析エラーなど、実行環境依存のトラブルが起きやすい。現に直近の検証でも PowerShell + `&&` でエラーになっている)

### ✅ Pro Recommendation
> **Choose Option A because**: クロスプラットフォーム（Windows等）でのスクリプト連結リスクを避けつつ、既存の `npm test` 導線を安全に維持できる。SRP（単一責任）と DRY の観点からも非常に優れたリファクタリング計画。  
> Estimated implementation: 45 minutes  
> Rollback plan: Git revert して `test_phase4_5.ts` を元に戻すだけ。
