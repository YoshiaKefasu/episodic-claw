## 2. 根本原因

v0.4.22c で `NarrativePool` を「passive accumulator（常時null返却）」に変更した一方、
`segmenter.poolAndQueue()` 側は「`pool.add()` が flush item を返す」という旧前提のまま残っている。

そのため境界（idle / surprise / time-gap / size-limit）で `handleSegmentBoundary()` が呼ばれても、
enqueue が起動せず、データがpoolに溜まり続ける。

---

## 3. 修正方針（Option A: 推奨）

### Option A（推奨）— boundary発生時は `pool.forceFlush()` で明示flush

**考え方**: いま boundary 判定主体は segmenter。なら boundary時に flush 指示も segmenter が明示的に出すべき。

#### 変更案

`src/segmenter.ts` `poolAndQueue()`

```diff
- const item = this.pool.add(this.buffer.slice(), surprise, agentWs, agentId);
+ this.pool.add(this.buffer.slice(), surprise, agentWs, agentId);
+ const item = this.pool.forceFlush(agentWs, agentId);

  this.buffer = [];
  this.resetBufferTokens();
  this.lastProcessedLength = 0;
  this.clearIdleFlushTimer();

  if (item) {
    ... enqueueNarrativeChunks ...
  }
```

#### Option Aの評価

- YAGNI: ✅ 最小修正（segmenter 1箇所）
- KISS: ✅ 既存API (`forceFlush`) を再利用
- DRY: ✅ 新しいflush APIを増やさない
- SOLID: ✅ 境界責務（segmenter）と保存責務（pool）の分離を維持

### Option B（非推奨）— `NarrativePool.add()` の戻り値仕様を復活

`add()` に境界ロジックを再注入すると、v0.4.22cの「pool受動化」と矛盾し、責務が再び混ざる。
