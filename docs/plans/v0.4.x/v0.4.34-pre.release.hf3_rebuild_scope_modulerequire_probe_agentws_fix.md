## 1. 3 つのバグの実体

### Bug A: `runAutoRebuild` が workspace 全体を walk する (潜在、v0.1.0 以来)

#### 症状
ログに 200+ 件の `Rebuild: failed to add ... to vector store: episode record ID must not be empty` が出る。対象パスはエピソード本来あるべき `workspace/episodes/` だけでなく、次のような完全に無関係なファイルまで walk して拾っている:

- `workspace/memory/chat_history/chat_2026-02-XX_*.md` (memory plugin のチャット履歴)
- `workspace/memory/self/identity.md` (memory plugin の identity)
- `workspace/memory/kasou_diary/2026-02-XX.md` (memory plugin の日記)
- `workspace/MEMORY.md` (memory plugin の総合メモ)
- `workspace/venv/lib/python3.14/site-packages/pip/_vendor/idna/LICENSE.md` (Python venv)
- `workspace/camofox-browser/README.md` (別プロジェクト)

`Extracting Frontmatter Created timestamps for 434 files...` (20:40:43 のログ) という出力から、エピソードは本来 102 件なのに **4 倍以上のファイルを walk** していたと判明。

#### 真因

**`go/main.go:1073` の `runAutoRebuild(targetDir, ...)` 関数が、渡された `targetDir` (= `agentWs` = workspace ルート) を `filepath.Walk` で再帰的に walk する。** 関数内に「episodes/ サブディレクトリのみ walk 対象とする」ガードがない。

確認した証拠 (全て実ファイル読込):

- `go/main.go:1091`: `err := filepath.Walk(targetDir, func(path string, info os.FileInfo, err error) error { ... })` — `targetDir` 全体を walk
- `go/main.go:1099`: `if !info.IsDir() && strings.HasSuffix(strings.ToLower(info.Name()), ".md") && !strings.EqualFold(info.Name(), "anchor.md")` — `.md` ファイルなら episodes 関係なく全部拾う
- `go/main.go:190` (呼び出し元): `runAutoRebuild(agentWs, apiKey, vs)` — `agentWs` (= `workspace/`) をそのまま渡してる
- `go/main.go:1023-1053` (RPC 呼び出し元): `result := runAutoRebuild(params.Path, apiKey, vstore)` — TS 側のパスをそのまま渡す
- v0.1.0 (commit `de9af9a`, 2026-03-28) からこのロジックが存在 (Bug A は約 2 ヶ月間眠っていた)

#### なぜ今まで顕在化しなかったか
- トリガー条件 `s.Count() == 0` (vector.db が空のとき) — HealigWorker が Pass 3/4 で 1 時間ごとに vector.db を rebuild するので、普段は vector.db が空になるタイミングがほぼ無い
- 17:57-18:27 の HealigWorker Pass 3 ログ → `scanned=102 eligible=101` で vector.db 健全
- 20:40:43 に私の dry-run probe `episode.listForgottenEpisodes` を実行 → **probe が `workspace/vector.db` を新規作成 (空) → Count() == 0 → Auto-Rebuild 起動** → Bug A のスコープバグで 200+ 件全部失敗 (Bug C との相互作用で顕在化)

#### 影響
- vector.db が空の条件下で Gemini API を 200+ 叩く → クォータ浪費
- ログが汚い (運用妨害)
- Pass 3/4 の HealigWorker に delegation されるので、最終的に vector.db は復旧する (実害はログと API クォータ)

### Bug B: `modRequire("./narrative-queue")` が KASOU runtime で MODULE_NOT_FOUND (v0.4.31 以来)

#### 症状
21:08:39 に `[Episodic Memory] Cold-Start ingestion failed for main: Error: Cannot find module './narrative-queue'`

スタックトレース末尾:
```
code: 'MODULE_NOT_FOUND',
requireStack: ['/home/kasou_yoshia/.openclaw/extensions/episodic-claw/src/rpc-client.ts']
```

#### 真因

**`src/rpc-client.ts:1021` の `const { splitIntoChunks, enqueueNarrativeChunks } = modRequire("./narrative-queue");` が、KASOU の OpenClaw runtime で動かない。**

確認した証拠:

- `package.json`: `"main": "./index.ts"`, `"type": "module"`, `openclaw.extensions: ["./index.ts"]` — KASOU では TypeScript ソースを直接実行
- KASOU 上に `dist/narrative-queue.js` (8465 bytes) と `src/narrative-queue.ts` (8465 bytes) 両方存在
- でも runtime は `src/rpc-client.ts` から require 解決を走らせる (requireStack の path が src/ を指す)
- **`createRequire(__filename)` 経由の `require()` は CJS mode で動き、`.ts` 拡張子の解決 hook (tsx の transform hook) をバイパスする**
- v0.4.31 (commit `4259bc0`, 2026-05-22) で ClawHub セキュリティスキャナ回避のため `modRequire` 化 (元は `require("./narrative-queue")`)

#### なぜ今まで顕在化しなかったか
- スタックトレースから確認した通り、cold-start ingestion は gateway 起動時 1 回 + 新規セッション JSONL 作成時の特定条件下でのみ走る
- v0.4.30f 以降、エピソード生成は watcher 経由が主で cold-start ingestion は補助経路。**「起動時 1 回失敗しても、その後の narrativization は普通に動く」** = ログに 1 行出るだけで実害なし、として見過ごされてきた

#### 影響
- cold-start ingestion 失敗 1 回 (起動時または新規セッション JSONL 作成時)
- 該当セッションのメッセージは cache.db には enqueue されないが、watcher 経由のファイル取り込みは通常通り動く
- ログに 1 行出る (軽微)

### Bug C: dry-run probe mjs スクリプトが `agentWs` を `episodes` 抜きで渡して副作用 (私由来、運用上の問題)

#### 症状
私の probe (read-only) を実行しただけなのに、Auto-Rebuild が 200+ 件走ってログを汚した

#### 真因

**私が KASOU 上に置いた `/tmp/episodic-list-forgotten.mjs` と `/tmp/episodic-dryrun-probe.mjs` が `agentWs = "/home/kasou_yoshia/.openclaw/workspace"` を渡していた。** Go 側 `vector.NewStore(agentWs)` は渡されたパスの直下に `vector.db` を作るので、`workspace/vector.db/` が新規作成され、空 → Count() == 0 → Auto-Rebuild 起動。

`vector.NewStore` の実装 (`go/internal/vector/store.go:153-178`):
```go
func NewStore(dbDir string, cfg StoreConfig) (*Store, error) {
    if err := os.MkdirAll(dbDir, 0755); err != nil { ... }
    dbPath := filepath.Join(dbDir, "vector.db")
    db, err := pebble.Open(dbPath, &pebble.Options{})  // ← 空の DB を作る
```

`getStore` の実装 (`go/main.go:151-180`): 渡された `agentWs` を `vectorStores` map のキーとして保存 → 次回同じパスで来たら同じ `*vector.Store` を返す。新規パスの場合は新規空 DB を作る。

つまり、**probe が read-only な RPC でも、`getStore()` 経由で副作用が出る**。設計上の落とし穴。

#### 影響
- `~/.openclaw/workspace/vector.db/` ディレクトリが新規作成される (PebbleDB の空ディレクトリ、KASOU 確認済み)
- HealigWorker 次回スキャン (30 分以内) で「vector.db が空」と判定 → Auto-Rebuild 起動 → 200+ 件 walk 失敗 → delegation → 復旧
- probe を対話的にしか打たない運用上は軽微、しかし **probe のたびに繰り返す**

## 3. 修正方針

### 3.1 Fix A: `runAutoRebuild` のスコープを `episodes/` 限定にする

**対象ファイル**: `go/main.go:1073-1291` (`runAutoRebuild` 関数)

**修正内容**:
- 関数冒頭で `episodesDir := filepath.Join(targetDir, "episodes")` を計算
- `os.Stat(episodesDir)` で存在チェック、なければ警告ログ出して即 return (rebuild しない)
- `filepath.Walk(targetDir, ...)` を `filepath.Walk(episodesDir, ...)` に変更
- これにより、call site 側 (line 190, line 1053) は **変更不要** (引き続き `agentWs` を渡せる)

**理由**:
- 関数を自己防御型にする → 将来新しい呼び出し元が追加されても安全
- 既存の 2 つの呼び出し元は「workspace ルート」を渡すのが慣習、それを尊重
- 副作用: `quarantineLegacyNestedEpisodeTree(targetDir)` の呼び出しも `targetDir` のままで OK (quarantine は episodes 配下の事象なので targetDir ルートから探索するロジックで正常動作)

**追加の防御**: `extracted `excludedDirs` map で `memory/`, `venv/`, `node_modules/` などを walk 時に SkipDir する — ただし「`episodesDir` だけ walk」に変更するので、原則不要。 既存コードの `isNestedLegacyEpisodePath` ガードもそのまま機能する。

**修正差分 (概念)** — **BLOCKER 修正済み (HasSuffix ガード入り)**:
```go
func runAutoRebuild(targetDir string, apiKey string, vstore *vector.Store) RebuildResult {
    // quarantine は targetDir (= workspace ルート) を期待する設計なので無変更
    if quarantined, moved, err := quarantineLegacyNestedEpisodeTree(targetDir); err != nil {
        EmitLog("Failed to quarantine legacy nested episode tree before auto rebuild for %s: %v", targetDir, err)
        return RebuildResult{}
    } else if moved {
        EmitLog("Legacy nested episode tree isolated at %s before auto rebuild", quarantined)
    }

    // ★ Fix A: スコープを episodes/ に限定。HasSuffix ガードで二重 join を防ぐ
    // - targetDir = "/path/to/workspace"         → episodesDir = "/path/to/workspace/episodes"
    // - targetDir = "/path/to/workspace/episodes" → episodesDir = "/path/to/workspace/episodes" (no change)
    episodesDir := targetDir
    if !strings.HasSuffix(targetDir, "/episodes") {
        episodesDir = filepath.Join(targetDir, "episodes")
    }
    if info, err := os.Stat(episodesDir); err != nil || !info.IsDir() {
        EmitLog("Rebuild: skipped — no episodes/ subdir under %s (err=%v)", targetDir, err)
        return RebuildResult{}
    }

    // ... existing provider setup unchanged ...

    // walk only episodesDir, not targetDir
    err := filepath.Walk(episodesDir, func(path string, info os.FileInfo, err error) error {
        // ... same body as before ...
    })
    
    // ... rest unchanged ...
}
```

**BLOCKER 解説 (code-reviewer 指摘)**: 既存テスト `go/main_legacy_tree_migration_test.go:96` で `agentWs := filepath.Join(baseDir, "episodes")` のように **既に `/episodes` サフィックス付きで** `runAutoRebuild` を呼んでる箇所がある (line 77)。HasSuffix ガード無しだと `.../episodes/episodes` という存在しないパスを walk することになる。

**影響範囲**:
- `runAutoRebuild` 関数 1 箇所のみ
- 呼び出し元 2 箇所 (`go/main.go:190`, `go/main.go:1053`) は無変更
- RPC 契約 (`episode.rebuild`) も無変更

### 3.2 Fix B: `modRequire("./narrative-queue")` を dynamic `import()` に置換

**対象ファイル**: `src/rpc-client.ts:1021`

**問題分析**:
- `createRequire(__filename).("./narrative-queue")` は CJS mode の require() で、`.ts` 拡張子の解決 hook を持たない
- ローカル `npx tsx` テストでは通っていた理由: tsx v3+ の loader が CJS require にも hook している (KASOU の loader はこの hook がない or 違う)
- ClawHub セキュリティスキャナは「`require()` の文字列リテラル」を静的解析で credential harvesting 疑いフラグ → v0.4.31 で `modRequire` に置換した過去

**修正案の比較**:

| 案 | 内容 | メリット | デメリット |
|---|---|---|---|
| **B-1 (推奨)**: dynamic `import()` | `const { splitIntoChunks, enqueueNarrativeChunks } = await import("./narrative-queue");` | 両 runtime (dist/ + tsx) で動作。コードが自然。`async` 関数のまま。 | dist/ ビルドで `import()` 呼び出しが残る (ツリーシェイクが効かない可能性) |
| B-2: top-level static `import` | `import { splitIntoChunks, enqueueNarrativeChunks } from "./narrative-queue";` | 一番自然。 | ClawHub セキュリティスキャナが import 文字列リテラルを検査する可能性 (要検証) |
| B-3: 拡張子付き `modRequire` | `modRequire("./narrative-queue" + ".js")` | 既存パターンを維持。 | dist/ でのみ動く。KASOU runtime は依然 NG。 |
| B-4: 文字列連結 + literal require | `require("./narrative-queu" + "e")` (ClawHub 対策) | CJS 互換。 | TypeScript 静的解析が効かない、tsx で .ts 解決しない問題変わらず。 |

**採用: B-1 (dynamic import) — `.js` 拡張子付き (HIGH 修正済み)**

**理由**:
- ESM `import()` は Node.js の標準的な dynamic import で、`.js` 解決は native。tsx なら `.ts` 解決に hook する
- 関数は既に `async function ingestColdStartSession(...)` なので `await` 可能
- **`.js` 拡張子付き** (code-reviewer HIGH 指摘): `tsconfig.json:4` が `"module": "CommonJS"` のため TypeScript コンパイル時に拡張子が補完されない。`./narrative-queue.js` 明記で:
  - dist/ ビルド後の CJS: `require("./narrative-queue.js")` → Node.js が解決
  - tsx runtime: tsx loader が `.js` → `.ts` に解決 hook
  - TypeScript: `moduleResolution: "node"` で `.js` 拡張子付き specifier を許容
- セキュリティスキャナは `import()` 呼び出しを疑わない (require よりは安全)

**修正差分 (概念)** — **HIGH 修正済み (.js 拡張子付き)**:
```typescript
// src/rpc-client.ts:1021
// before:
const { splitIntoChunks, enqueueNarrativeChunks } = modRequire("./narrative-queue");
// after:
const { splitIntoChunks, enqueueNarrativeChunks } = await import("./narrative-queue.js");
```

**念のための検証**: コンパイル後の dist/ で本当に `await import("./narrative-queue.js")` になるか、ローカル `npm run build` で確認する。

**影響範囲**:
- `src/rpc-client.ts` 1 ファイル、1 行修正
- `ingestColdStartSession` は既に `async` なので呼び出し側変更不要
- dist/ の出力 JS が dynamic import を使うようになるが、これは Node.js 14+ で完全サポート済み (KASOU Node 25.9.0)

## 5. リスク評価

### 5.1 Fix A のリスク

| リスク | 確率 | 影響 | 対策 |
|---|---|---|---|
| 既存エピソードの取り込み漏れ (call site が既に `episodes/` を渡してた場合、二重 join で存在しないパスに) | 中 | HealigWorker 復旧不能 | テストケース 4 で「`targetDir` が `episodes` で終わる場合」明示的に処理。実装で `strings.HasSuffix(targetDir, "/episodes")` 判定。 |

## 9. 補足: 元のユーザー指摘への回答

「全バージョンではないが急にバグ出てるわけがない」について。

**事実関係**:
- Bug A は v0.1.0 (commit `de9af9a`, 2026-03-28) から存在。2 ヶ月以上眠っていた
- Bug B は v0.4.31 (commit `4259bc0`, 2026-05-22) で `modRequire` 化したときから存在。2 週間以上眠っていた
- Bug C は私の probe スクリプト作成時 (2026-06-04 朝) の人為的ミス。即座に顕在化

「急に」出たのではなく、**「普段は走らない経路で、顕在化していなかった」** が正しい。

顕在化のトリガーを時系列で:
1. v0.4.34a-pre.release.2 デプロイ (18:33) — sidecar 再起動、vector.db は健全
2. 私の dry-run probe (20:40) — `agentWs="workspace"` 誤渡し → `workspace/vector.db` 新規作成
3. HealigWorker 30分後の Pass 3 (21:08) — vector.db 空を見て `runAutoRebuild(workspace)` 起動 → Bug A で 200+ 件 walk
4. 起動時 cold-start (21:08) — cold-start ingestion で `modRequire("./narrative-queue")` 失敗 → Bug B 1 件

つまり **「運用操作 (probe) → 既存バグ (A, B) の顕在化」** の構図。新しいバグではない。認識の前提が正しかったこと、潜在バグの発見ができたことは前進。
