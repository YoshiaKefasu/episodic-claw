## 1. 実読ベースの根拠（Source Evidence）

### Evidence 1 — `narrative-worker` は `item.rawText` を無条件でプロンプトへ流す

- `src/narrative-worker.ts:544-546, 590-592`
  - `const conversationText = item.rawText;`
  - `const userMessage = this.resolveUserPrompt(previous?.body, conversationText);`

**意味**: 空文字 `rawText` が来ても、現状はそのまま LLM 呼び出し側へ進む。

### Evidence 2 — 型上は `rawText: string` 必須だが、中身の非空は保証していない

- `src/types.ts:212-215` (`PoolFlushItem.rawText: string`)
- `src/narrative-queue.ts:25` (`CacheQueueItem.rawText: string`)
- `go/internal/cache/queue.go:113-129` (`EnqueueBatch`)  

**意味**: 構造上の必須性はあるが、`""`（空文字）自体は投入可能。

### Evidence 3 — `GEMINI_API_KEY` は worker 側で既に trim してから client 作成

- `src/narrative-worker.ts:473-482`
  - `const apiKey = process.env.GEMINI_API_KEY?.trim() || "";`
  - `new GeminiDirectClient(apiKey, 30_000)`

**意味**: code-review 指摘の「header送信前 trim不足」は、実際には worker 側で先に実施済み。
ただし client 単体利用に備えた二重防御は still valuable。

### Evidence 4 — 大型 source-smoke regex が複数あり、テキスト変化に脆い

- `test_phase4_5.ts:1092-1110`
  - `assert.match(... /[\s\S]*?/s ...)` 系の広域正規表現

**意味**: 意図が「機能の存在確認」でも、コメントや改行変化で壊れやすい。

### Evidence 5 — `JSON.stringify` ログは DEBUG 環境変数で既にガード済み

- `src/index.ts:1035-1053`
  - `if (process.env.DEBUG_EPISODIC_RECALL_FINGERPRINT) { console.log(JSON.stringify(...)) }`

**意味**: 常時ホットパス性能問題ではない。v0.4.26 の必須修正対象からは外すのが妥当。

## 2. 問題定義（v0.4.26で扱う範囲）

### 対象に含める

1. `rawText` 空入力時の fail-fast 防御（worker側）
2. source-smoke regex の brittle 性の低減
3. Gemini client の API key trim を defensive に追加（任意利用時の安全網）

### 対象に含めない

- DEBUGログ `JSON.stringify` の最適化（現状ガード済みで優先度低）

---

## 3. 解決方針

### Option A（推奨）— 最小差分 hardening

- `rawText` ガードを worker に追加（OpenRouter/Gemini 両経路共通で適用）
- brittle regex を段階的 assertion（`includes` + 局所regex）へ置換
- `GeminiDirectClient` でも `apiKey.trim()` を適用（defense in depth）

**メリット**: 低コストで運用事故率を下げる。既存挙動への影響が小さい。  
**リスク**: 低。

### Option B（非推奨）— queue層で厳格 reject まで一気に実施

- Go queue enqueue 時に `rawText==""` を reject
- 既存 path 全体でエラーハンドリング再設計

**非推奨理由**: 変更半径が広く、v0.4.26の目的（hardening）を超える。

## 4. 実装計画（v0.4.26）

### Fix 1 — NarrativeWorker fail-fast guard for empty `rawText`

- ファイル: `src/narrative-worker.ts`
- 内容:
  1. `narrativizeWithRetry()` の入口で `item.rawText.trim().length === 0` を検出（provider別関数で重複実装しない）
  2. 空なら LLM 呼び出しに進まず、`empty_raw_text`（dedicated error class か固定エラーコード）を throw
  3. `processNextFromCache()` の catch で `cacheRetry(..., errMsg, MAX_CACHE_ATTEMPTS)` に流し、`errMsg` に `empty_raw_text` を含める
  4. Warnログに `item.id`, `agentId`, `source`, `reason=empty_raw_text` を残す

> 方針理由: KISS/DRY。guard を phase入口に1箇所置くと OpenRouter/Gemini 両経路へ確実に効く。

### Fix 2 — Gemini client API key defensive trim

- ファイル: `src/gemini-direct-client.ts`
- 内容:
  1. constructor で `this.apiKey = apiKey.trim()` を保証
  2. 空なら即 `GeminiDirectError("gemini_missing_api_key")` を返す（HTTP分類に混ぜない dedicated class）

> Note: 実運用 path では worker側で trim済みだが、client単体利用の安全網として実施。

### Fix 3 — brittle source-smoke regex の安定化

- ファイル: `test_phase4_5.ts`
- 対象例: `1092-1110` 付近
- 内容:
  1. 広域 `([\s\S]*?)` regex を削減
  2. 意味単位の assertion に分割
     - 「A が存在する」
     - 「B が存在する」
     - 「A より B が後にある（index比較）」
  3. コメント文言依存の検証を最小化

### Fix 4 — テスト追加

- ファイル: `test_phase4_5.ts`（必要なら `test_narrative_quality_gate.ts`）
- ケース:
  1. `rawText=""` の queue item を worker が LLM呼び出しせず retryへ返す
  2. `rawText="   "`（空白のみ）でも同挙動
  3. 正常 `rawText` は既存どおり成功経路を維持

## 6. リスクと対策

### リスク1 — guardが厳しすぎて正常データを誤判定
- 対策: `trim().length === 0` のみ reject。1文字以上は通す。

### リスク2 — テスト変更で検証力が下がる
- 対策: assertion分割時に「存在 + 順序 + 非存在」の3軸を維持。

### リスク3 — error class 追加でログ集計が分断
- 対策: `empty_raw_text` を既存ログ項目へマップし、ダッシュボード側キーを事前合意。
