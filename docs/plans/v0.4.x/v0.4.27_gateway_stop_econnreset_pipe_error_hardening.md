# v0.4.27 — gateway_stop 時の `Uncaught ECONNRESET` 防止（pipe error hardening）

> Date: 2026-04-22  
> Status: ✅ IMPLEMENTED（Local verification complete）

---

## 0. 背景

`v0.4.26` 運用ログで、gateway 停止シーケンス中に以下のエラーが 1 回発生した。

```text
[openclaw] Uncaught exception: Error: read ECONNRESET
    at Pipe.onStreamRead (node:internal/stream_base_commons:216:20)
```

今回の範囲はこの `ECONNRESET` のみ。  
`memory-lancedb` 警告と ClawHub suspicious pattern 警告はユーザー指示により除外。

---

## 1. 実読ベースの根拠（Source Evidence）

### Evidence 1 — エラー直前が gateway_stop の停止手順
- `X:/tmp/openclaw/openclaw-2026-04-22.log:1018-1025`
  - `signal SIGTERM received`
  - `received SIGTERM; shutting down`
  - `[Episodic Memory] Stopping plugin... (reason: gateway stopping)`
  - `gateway_stop: all buffers flushed`
  - `Stopping narrative worker...`
  - 直後に `Uncaught exception: Error: read ECONNRESET`

### Evidence 2 — 実際の停止コードが同じ順序で実行される
- `src/index.ts:912-945`
  - `gateway_stop` で `segmenter.forceFlush(...)` → `narrativeWorker.stop()` → `rpcClient.stop()` の順。
  - ログ順とコード順が一致。

### Evidence 3 — sidecar stderr に `error` リスナーが無い（stdout も同様）
- `src/rpc-client.ts:236-257`
  - `this.child.stderr.on("data", ...)` はある。
  - しかし `this.child.stderr.on("error", ...)` が無い。
  - ⚠️ **[Pro Eng Review 乖離1]** `child.stdout` には `"data"` も `"error"` も存在せず、stderr よりも pipe error に露出している。ECONNRESET/EPIPE の発生源になり得る。

### Evidence 4 — 停止時に socket destroy + child kill を行う
- `src/rpc-client.ts:366-397`
  - `this.socket.destroy()`
  - `p.kill()`
  - 停止境界で pipe がリセットされる余地がある。

### Evidence 5 — 当該ログにはプラグイン側の post-connect socket error ログが出ていない
- `X:/tmp/openclaw/openclaw-2026-04-22.log` 全体検索
  - `"[Plugin] Go RPC socket error (post-connect):"` が見当たらない。
  - つまり今回の `Pipe.onStreamRead` は RPC socket より、child stdio 側の可能性が高い。

---

## 2. 問題の本質（1文）

> gateway 停止中に sidecar の pipe が `ECONNRESET` を返した時、child stdio 側で未処理 `error` が残っているため、`Uncaught exception` として表面化する。

---

## 3. 方針（Decision）

### Option A（採用）
**plugin 側で shutdown 境界の pipe/socket エラーを明示吸収する最小差分 hardening**

- `rpc-client.ts` に `isStopping` フラグを導入
- child `stderr/stdout` に `error` リスナー追加
- 停止中の `ECONNRESET` / `EPIPE` は info/warn に降格して握る
- 停止中以外は従来どおり error として扱う

### Option B（不採用）
OpenClaw 本体の `uncaughtException` ハンドラ側で吸収

- 本件は episodic-claw だけで再現し得る停止境界の問題なので、まず plugin 側で閉じる。
- 依存先本体への変更はリードタイムが長く、今回の修正目的（v0.4.27迅速安定化）から外れる。

---

## 4. 実装計画（最小差分）

### 4.1 変更ファイル
- `src/rpc-client.ts`
- `src/index.ts`（必要最小限の defensive logging のみ）

> ⚠️ ~~`test_phase4_5.ts`~~ — 当該ファイルはコードベースに存在しないため参照削除（Pro Eng Review 乖離4修正）

### 4.2 Fix A — `rpc-client.ts` に shutdown 境界ガードを追加
1. `private isStopping = false;` を追加
2. `stop()` 冒頭で `isStopping = true`、完了後に `false`（または child/socket 未接続時も整合維持）
3. `child.stderr.on("error", ...)` と `child.stdout?.on("error", ...)` を追加
   - ⚠️ **[Pro Eng Review 乖離1修正]** `child.stdout` には `"data"` も `"error"` も存在せず、stderr よりも露出している。両方に error リスナーが必須
4. ハンドリング規約:
   - `isStopping && (code==="ECONNRESET" || code==="EPIPE")` → warn/info ログで吸収
   - それ以外 → error ログ + 必要な reject

### 4.3 Fix B — socket close/error の停止中分岐 + reconnect 競合ガード
`setupSocketReader()` の `sock.on("close")` / `sock.on("error")` で:
- `isStopping === true` の時は「unexpected」扱いを避け、過剰な pending reject を抑制
- 運用中 (`isStopping === false`) は従来通り

**[Pro Eng Review 乖離3修正]** `reconnect()` と `stop()` の競合レース対応:
- `reconnect()` 内で `this.isStopping` をチェック — 停止中は再接続を即座に reject
- これにより `setupSocketReader()` が停止中にハンドラーを追加する事態を防止

### 4.4 Fix C — `gateway_stop` の防御強化（最小）
`src/index.ts` の `gateway_stop` で:
- `narrativeWorker.stop()` と `rpcClient.stop()` を個別 try/catch
- 停止中エラーを握りつつ shutdown 継続
- ⚠️ **[Pro Eng Review 乖離2修正]** 現状は bare `await` で、`narrativeWorker.stop()` が例外を投げると `rpcClient.stop()` が実行されず sidecar が孤児化する実リスクあり

### 📍 Current Reality (Source Code vs. Document)

- ✅ Evidence 1–2: ログ→コード順序の対応は正確。`gateway_stop` の `forceFlush → narrativeWorker.stop → rpcClient.stop` 順を確認
- ✅ Evidence 3: `child.stderr.on("data")` は存在（L236）、`child.stderr.on("error")` は不在 — プラン記述通り
- ✅ Evidence 4: `socket.destroy()` + `p.kill()` — プラン記述通り
- ✅ Evidence 5: `"[Plugin] Go RPC socket error (post-connect):"` はコード内に存在するが、ログ上は出力なし — プラン推論と整合
- ⚠️ **乖離1: `child.stdout` にハンドラーが一切ない** — プランは stderr の `error` リスナー欠落のみ指摘しているが、`child.stdout` には `"data"` も `"error"` も存在しない。stdout も pipe であり、ECONNRESET/EPIPE の発生源になり得る。Evidence 5 の推論（「child stdio 側の可能性が高い」）は正しいが、**stdout がより露出している** ことをプランは見落としている
- ⚠️ **乖離2: `narrativeWorker.stop()` と `rpcClient.stop()` が個別 try/catch されていない** — プラン §4.4 Fix C で修正を計画しているが、現状コードでは bare `await` のまま。`narrativeWorker.stop()` が例外を投げると `rpcClient.stop()` が実行されず、sidecar プロセスが孤児化する実リスクがある
- ⚠️ **乖離3: `reconnect()` と `stop()` の競合レース** — `stop()` 実行中に `reconnect()` が進行中の場合、reconnect 成功後に `setupSocketReader()` がハンドラーを追加し、直後に `socket.destroy()` が close イベントを発火 → "unexpectedly" ログ + `rejectPending` が走る。プランはこの競合に言及していない
- ⚠️ **乖離4: `test_phase4_5.ts` が存在しない** — §4.1 が変更ファイルとして挙げているが、コードベース内に存在しない
- ℹ️ Evidence 3 の行番号が若干ずれ（232→236）— 実害なし

### 🎯 Core Problem (1 sentence)
> gateway 停止中に child process の stdio pipe が ECONNRESET を返す際、stderr/stdout に `error` リスナーが不在のため Node.js の `uncaughtException` に表面化する

### 🛤️ Solution Options

#### Option A — プラン修正版（isStopping + stdout/error ハンドラー + 競合ガード） *(推奨)*
**Approach**: 元プランの方向性は正しいが、3つの乖離を修正して実装する
**Implementation cost**: Low
**Risk**: Low
**Why recommended**: 元プランの最小差分方針は妥当。乖離の修正も数十行で完了し、過度設計にならない
**Concrete steps**:
1. `private isStopping = false;` 追加
2. `stop()` 冒頭で `isStopping = true`
3. `child.stderr.on("error", ...)` + `child.stdout?.on("error", ...)` 追加（**stdout も対象 — 乖離1修正**）
4. `isStopping && (ECONNRESET|EPIPE)` → info ログで吸収、それ以外 → error
5. `setupSocketReader()` で `isStopping` チェック追加（**乖離3修正**）
   - `isStopping` 時は close/error ハンドラーを登録しない、または "unexpectedly" を "during shutdown" に変更
6. `reconnect()` で `isStopping` チェック追加 — 停止中は再接続を中止（**乖離3修正**）
7. `gateway_stop` で `narrativeWorker.stop()` / `rpcClient.stop()` を個別 try/catch（**乖離2修正 — プラン通り**）
8. §4.1 の `test_phase4_5.ts` 参照を削除（**乖離4修正**）
9. Evidence 3 に stdout の記述を追加（**乖離1修正**）

#### Option B — 超最小案（isStopping なし、error リスナーのみ）
**Approach**: `isStopping` フラグを使わず、stderr/stdout の `error` リスナーだけ追加する。全ての ECONNRESET/EPIPE を warn で扱う
**Implementation cost**: Very Low
**Risk**: Medium
**When to choose this instead**: 今回1回限りの事象であり、今後再発しない可能性が高い場合
**Concrete steps**:
1. `child.stderr.on("error", ...)` + `child.stdout?.on("error", ...)` 追加
2. ECONNRESET/EPIPE は常に warn で処理（child 死亡時しか起きないので実質無害）
3. `gateway_stop` に try/catch 追加
**欠点**: setupSocketReader の競合レースに対応できない。reconnect→stop 競合時の "unexpectedly" ログや rejectPending が抑制できない

#### Option C — プラン原案そのまま（stdout / 競合を見落としたまま実装）
**Approach**: プラン §4 のまま実装。stdout の error リスナーと reconnect 競合は後回し
**Implementation cost**: Low
**Risk**: Medium-High
**When to choose this instead**: なし
**欠点**: stdout が ECONNRESET 発生源の場合に未解決。reconnect→stop 競合も放置
