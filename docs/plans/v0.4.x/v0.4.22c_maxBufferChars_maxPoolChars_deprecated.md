## 2. 設計

### 2.1 基本方針

**64Kハードキャップ + surprise + idle timeout + time-gap + force flush の5条件が揃っているため、
`maxBufferChars` も `maxPoolChars` も「surprise未検出時の保険」として不要（YAGNI）。**

### 2.2 例え話

- `maxBufferChars` = 「3階建てのビルに『2階で止まれ』って標識」。でも4階（64K）で止まる法律が既にあるから、2階の標識は意味ない。
- `maxPoolChars` = 「集荷所に『15000文字で出荷せよ』ってルール」。でもトラック（NarrativeWorker）は64Kまで積めるし、運転手（surprise）が「ここで区切れ」って判断するから、集荷所での強制出荷は不要。

### 2.3 変更方針

**設定値は読むが、動作には反映しない。** ユーザーが設定していても無害。
次期バージョンで設定項目自体を削除できる。

## 8. v0.4.22 + v0.4.22b 回帰バグ（ソース検証で発見）

以下3件は v0.4.22c で修正する。

### BUG-1 (HIGH) — handleIdleFlush が WAL rotate を呼んでいない

**現状:**
`segmenter.ts:457`:
```typescript
await this.handleSegmentBoundary(agentWs, agentId, 0, "idle-timeout");
//                                             walFlushId なし（デフォルト -1）
```

**何が起きるか:**
- idle flush が発火しても WAL は rotate されない
- active WAL にメッセージが残ったまま `buffer = []`（L464）
- enqueue が成功しても `walDeleteStaged` が呼ばれない（flushId=-1 だから）
- **結果: active WAL が永遠にクリアされず、次回 warm-start で二重注入される**

**修正:**
```diff
-   await this.handleSegmentBoundary(agentWs, agentId, 0, "idle-timeout");
+   // [v0.4.22c] WAL: rotate before idle boundary processing
+   const idleFlushId = this.walRotateForFlush(agentWs, agentId);
+   await this.handleSegmentBoundary(agentWs, agentId, 0, "idle-timeout", idleFlushId);
```

さらに L464 の `this.buffer = [];` の後に WAL buffer flush を追加:
```diff
    this.persistCursor(agentWs, agentId);
    this.buffer = [];
+   // [v0.4.22c] WAL: ensure write buffer is flushed after idle boundary
+   this.walFlushWriteBuffer();
    return true;
```

### BUG-2 (MED) — forceFlush catch内で writeBuffer がフラッシュされない

**現状:**
`segmenter.ts:931-935`:
```typescript
catch (err) {
  console.error("[Episodic Memory] Error in segmenter forceFlush:", err);
  this.lastProcessedLength = savedCursor;
  this.persistCursor(agentWs, agentId);
  // ← walFlushWriteBuffer() がない
}
```

**何が起きるか:**
- `walRotateForFlush` が先に走って writeBuffer はフラッシュされるが
- その後の `enqueueNarrativeChunks` が投げられた場合、
  rotate中にバッファに溜まった行（rotate→enqueue間に到着したメッセージ）が
  ディスクに書かれないままプロセスが終了する可能性がある

**修正:**
```diff
  catch (err) {
    console.error("[Episodic Memory] Error in segmenter forceFlush:", err);
+   // [v0.4.22c] WAL: flush write buffer on failure too — data in memory must reach disk
+   this.walFlushWriteBuffer();
    this.lastProcessedLength = savedCursor;
    this.persistCursor(agentWs, agentId);
  }
```

### BUG-3 (MED) — context reset 時に WAL 残骸がクリアされない

**現状:**
`segmenter.ts:512-521`:
```typescript
if (this.lastProcessedLength > currentMessages.length) {
  if (this.buffer.length > 0) {
    await this.forceFlush(agentWs, agentId);
  }
  this.clearIdleFlushTimer();
  this.lastProcessedLength = 0;
  this.buffer = [];
  // ← walClearAll() がない
}
```

**何が起きるか:**
- context reset = セッション全消去
- `forceFlush` が成功すれば staged は削除される
- ただし forceFlush が失敗した場合、staged が残る
- 新しいセッションが始まった後に `walRestore` が走ると、**前セッションのメッセージが混入**する

**修正:**
```diff
  this.clearIdleFlushTimer();
  this.lastProcessedLength = 0;
  this.buffer = [];
+ // [v0.4.22c] WAL: clear all WAL files on context reset — new session must start clean
+ this.walClearAll(agentWs, agentId);
```

forceFlush が成功していれば staged は既にないので walClearAll は active だけを消す（無害）。
forceFlush が失敗していても、context reset 後に古いデータを復元するのは有害なので、強制クリアが正しい。

| # | 深刻度 | 指摘 | 対応 | 影響ファイル |

### 12.1 AF1: bufferTokenCount インクリメンタル計測の詳細

**設計:** バッファにメッセージが追加・置換・クリアされる度にトークン数を増減する。

| 操作 | トークン管理 | 呼び出し箇所数 |
|---|---|---|
| `this.buffer.push(...msgs)` | `this.addBufferTokens(msgs)` | 4箇所（first absorb / append / catch fallback / WAL inject） |
| `this.buffer = [...msgs]` | `this.recomputeBufferTokens()` | 2箇所（time-gap後 / surprise boundary後） |
| `this.buffer = []` | `this.resetBufferTokens()` | 8箇所（idle flush / compaction skip / context reset / poolAndQueue / afterCompaction / bootstrapCursor / forceFlush成功2パス） |

**64K判定の変更:**
```typescript
// 変更前: const bufferText = this.buffer.map(m => extractText(m.content)).join("\n");
//          const estimatedBufferTokens = estimateTokens(bufferText);
//          const sizeLimitExceeded = estimatedBufferTokens >= HARD_TOKEN_CAP;

// 変更後: const sizeLimitExceeded = this.bufferTokenCount >= HARD_TOKEN_CAP;
```

O(N)の `buffer.map().join()` + `estimateTokens()` がO(1)の数値比較に置換。毎turnの定数時間化。

### 12.2 AF2: EPISODIC_WAL_STRICT モード

```typescript
private readonly WAL_FLUSH_INTERVAL_LINES = process.env.EPISODIC_WAL_STRICT ? 1 : 10;
```
