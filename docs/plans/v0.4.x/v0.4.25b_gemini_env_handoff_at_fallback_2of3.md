## 0. 目的

`NarrativeWorker` が `primary(12)` を使い切り、`fallback(2/3)` に入る瞬間で、
`ENV(GEMINI_API_KEY)` を使って **Gemini direct (`gemini-3.1-flash-lite-preview`)** にハンドオフできるようにする。

狙いは「OpenRouter経路の429連打時に、別経路で救済して dead-letter 到達率を下げる」こと。

---

## 1. ソースコード根拠（実読）

### Evidence 1 — 現行リトライ段階は OpenRouter 2段のみ

- `src/narrative-worker.ts:406-419`
  - `primary(MAX_RETRIES=12)` → `fallback(openrouter/free, FALLBACK_RETRIES=3)`

**意味**: 現状は OpenRouter 以外の経路がない。

### Evidence 2 — LLM呼び出し実体は `OpenRouterClient` 固定

- `src/narrative-worker.ts:8, 254, 441-444`
  - `OpenRouterClient` を直接利用し `chatCompletion(..., { modelOverride })`

**意味**: Gemini direct API へ回すにはクライアント追加が必要。

### Evidence 3 — 12/12後は実際に fallbackへ移行している

- `X:\tmp\openclaw\openclaw-2026-04-21.log:1589`
  - `primary attempt 12/12 failed [http_429]`
- 同ログ `:1608-1609`
  - `Phase "primary" exhausted ... Falling back ...`
  - `Phase "fallback": trying model=openrouter/free, maxAttempts=3`

**意味**: 介入ポイント（fallback 2/3手前）は実運用でも発生している。

### Evidence 3.5 — 同ケースでは fallback 1/3 で最終成功している

- `X:\tmp\openclaw\openclaw-2026-04-21.log:1617-1621`
  - `fallback attempt 1/3 failed [timeout]` の後、`cacheAck` / `Successfully narrativized` に到達

**意味**: 現象は「常に dead-letter」ではなく、**429/timeout が長引いた時に dead-letter 側へ寄る確率問題**。
本対応は成功率底上げ（救済経路追加）として位置づける。

### Evidence 4 — 失敗最終形は queue retry → max到達で dead-letter

- `src/narrative-worker.ts:365` (`cacheRetry(..., MAX_CACHE_ATTEMPTS)`) 
- `go/internal/cache/queue.go:229-233`
  - `item.Attempts >= maxAttempts` で `StatusDeadLetter`

**意味**: 429連打が続くと最終的に dead-letter に落ちうる。

### Evidence 5 — ENVの Gemini API key は既に runtime で参照実績あり

- `src/index.ts:897`
  - `const hasApiKey = !!process.env.GEMINI_API_KEY;`

**意味**: ENVベース運用方針とは整合する（ただし narrative生成では未使用）。

## 2. 要件定義（ユーザー意図を固定）

1. トリガーは **fallback(2/3) に入る瞬間**。  
   （= fallback 1回目失敗後、2回目に行く前）
2. `process.env.GEMINI_API_KEY` がある場合のみ Gemini direct を試す。
3. モデルは固定: `gemini-3.1-flash-lite-preview`。
4. key が無い/失敗時は既存挙動にフォールバック（回帰なし）。

---

## 3. 解決方針（Option A 推奨）

### Option A（推奨）— Phase分割で deterministic handoff

`getRetryModels()` を「段階列」にし、旧 fallback(3) を以下に分割する：

- Phase 1: `primary` (OpenRouter custom, 12)
- Phase 2: `fallback-openrouter-head` (`openrouter/free`, 1)
- Phase 3: `fallback-gemini-direct` (`gemini-3.1-flash-lite-preview`, 2) ※ENVあり時のみ
- Phase 4: `fallback-openrouter-tail` (`openrouter/free`, 2)

これで「fallback 2/3相当のタイミング」で Gemini へ確実に切り替えられる。

#### なぜ Option A か

- KISS: 条件分岐地獄にせず、phase順序で明示化できる
- YAGNI: 今必要なトリガー条件だけ実装
- DRY: 既存 `narrativizeWithRetry` ループを再利用

### Option B（非推奨）— OpenRouter model overrideで Gemini名を投げる

OpenRouter経由で Gemini系モデル名を指定して凌ぐ。

**非推奨理由**: ユーザー意図の「ENVにある Gemini API の直利用」にならない。OpenRouter障害ドメインも共有する。

## 4. 実装計画（ファイル別）

### Fix 1 — Gemini direct クライアント追加

- 追加: `src/gemini-direct-client.ts`
- 内容:
  - `generateNarrative(systemPrompt, userMessage, model)`
  - Endpoint: `https://generativelanguage.googleapis.com/v1beta/models/{model}:generateContent?key=${GEMINI_API_KEY}`
  - typed error (`gemini_http_429`, `gemini_http_5xx`, `gemini_timeout`, `gemini_http_4xx`, ...)
  - **重要**: このクライアント内で多重 retry はしない（または maxRetries=0 固定）

> 理由: `NarrativeWorker` 側が既に phase/attempt 管理を持つため、
> providerクライアント側 retry を重ねると遅延が乗算され、回復時間が悪化する。

### Fix 2 — NarrativeWorker の phase定義を provider-aware 化

- 変更: `src/narrative-worker.ts`
- 内容:
  1. `RetryPhase` 型追加（`provider: "openrouter" | "gemini-direct"`）
  2. `getRetryModels()` → `getRetryPhases()` に改名
  3. fallback分割（head=1, gemini=2, tail=2）
  4. `process.env.GEMINI_API_KEY` 未設定時は gemini phase を生成しない（現行互換）
  5. phaseに `handoffReason?: "fallback_2_of_3"` を持たせ、ログへそのまま出せる形にする

### Fix 3 — phase実行器の分岐追加

- 変更: `src/narrative-worker.ts`
- 内容:
  - OpenRouter phase: 既存 `narrativizeWithModel()` を流用
  - Gemini phase: 新規 `narrativizeWithGeminiModel()`
  - Quality gate（圧縮率/echo/format）は **既存と同一** を適用

### Fix 4 — 観測ログ強化

- 変更: `src/narrative-worker.ts`
- 追加ログ:
  - `phaseHandoffReason: "fallback_2_of_3"`
  - `provider: "gemini-direct"`
  - `geminiModel: "gemini-3.1-flash-lite-preview"`
  - phase毎の失敗分類（429/timeout/policy）
  - ログレベル規約:
    - handoff開始/phase開始は `INFO`
    - phase失敗（再試行あり）は `WARN`
    - 最終失敗（cacheRetryへ返却）は `WARN`

### Fix 5 — テスト

- 変更: `test_phase4_5.ts`, 必要なら `test_narrative_quality_gate.ts`
- ケース:
  1. `GEMINI_API_KEY` あり: fallback1失敗後に gemini phase が呼ばれる
  2. Gemini成功時: `cacheAck` まで到達
  3. Gemini失敗時: openrouter tail に戻る
  4. `GEMINI_API_KEY` なし: 既存 12+3 挙動を維持（回帰防止）
  5. Geminiクライアントが provider retry を持たず、worker側 attempt 管理のみで進む（遅延乗算防止）
  6. missing key 時の warn は1回だけ（ログ嵐防止）

## 6. リスクと対策

### リスク1 — Geminiレスポンス形式差異
- 対策: extract関数を専用化、空応答時は typed error で再試行

### リスク2 — 2経路実装で保守複雑化
- 対策: `RetryPhase` 型で責務を分離、quality gateは共通関数を再利用

### リスク3 — Key管理の混乱
- 対策: v0.25bは ENV (`GEMINI_API_KEY`) のみ。plugin schemaに新規secretは追加しない（YAGNI）

### リスク4 — retry多重化で回復遅延が悪化
- 対策: Gemini direct クライアント側 retry は無効化し、retryは NarrativeWorker の phase/attempt に一本化
