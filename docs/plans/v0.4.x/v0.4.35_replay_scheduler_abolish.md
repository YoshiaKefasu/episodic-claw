# v0.4.35 — Replay Scheduler 廃止 + クリーンアップ

> Status: 📝 PLAN ONLY
> Created: 2026-06-09
> Target: v0.4.35 (next stable after v0.4.34-pre.release.hf3)
> Scope: Replay Scheduler の完全廃止 + replay tie-breaker 廃止。HealingWorker / Snapshot worker は維持。

---

## 1. 背景と問題

Replay Scheduler は過去の episodes を定期的にレビューし、memory の鮮度を保つ機能。しかし以下の問題がある:

**問題 1: 過度な API 消費**
- タイマー: 15 分ごとに実行
- 新規 episode の初期 DueAt: 作成 10 分後に due
- 150 episodes が全て 10 分で due → 毎 15 分 2 件ずつ処理 → 約 19 時間で全件消化
- 1 episode = 1 Gemini API 呼び出し (gemma-4-31b-it)
- quota 枯渇で 429 → crash loop → gateway 再起動の連鎖

**問題 2: 実用上の価値が薄い**
- HealingWorker (embedding) が既に episode の index を保持
- Replay review は「鮮度を保つ」が、実際には episode は不変 (一度書かれた MD は変わらない)
- 変更された episode は新規 ingested として再処理されるので、replay は不要

**問題 3: 廃止によるメリット**
- Gemini API quota の大幅節約 (150 回分/起動 → 0)
- Crash loop の根本解消
- コードベースの単純化

## 6. リスク評価

| リスク | 確率 | 影響 | 対策 |
|--------|------|------|------|
| replay tie-breaker 廃止で recall 品質が変わる | 中 | 低 | tie-breaker は max 0.04 の微小ブースト。影響は限定的 |
| D1 clustering のソート順が変わる | 低 | 低 | `assignReplayPriority` は clustering 優先度に使うだけ。廃止後はデフォルト順 |
| consolidation で `PromoteReplayStateToParent` が無くなる | 低 | 低 | replay state が親に伝播しなくなるが、replay 自体が不要なので害なし |
| EpisodeRecord の replay フィールド削除で既存 DB データが不整合 | 低 | 低 | PebbleDB はスキーマレス。フィールド削除は JSON マarshal 時に無視される |
| TS 側の config が壊れる | 低 | 中 | `recallReplay*` 設定は `optional`。削除後は無視される |
