# v0.4.30g — BUG-1 ガード根本解決

> **作成日**: 2026-05-21
> **ステータス**: Phase 1 実装済み（Phase 2 未着手）
> **関連問題**: `[Episodic Memory] Singleton reused (BUG-1 guard active).` が gateway 起動時に2回流れる

---

## A. 問題

### A1. 症状

gateway 起動ログで毎回このメッセージが2回出る:

```
[Episodic Memory] Singleton created.                    ← 1回目: 正常作成
[Episodic Memory] Singleton reused (BUG-1 guard active). ← 2回目
[Episodic Memory] Singleton reused (BUG-1 guard active). ← 3回目
```

実害はゼロ（BUG-1 ガードが正しく二重初期化を防いでいる）。しかし:
- 無視していいログノイズが毎日起動時に出る
- 初見者に「何かバグってる？」と思わせる
- 根本原因が5ヶ月以上放置されている

### A2. 現在の回避策（BUG-1 ガード）

`src/index.ts:625-781`:

```typescript
const SINGLETON_KEY = Symbol.for("__episodic_claw_singleton__");
let _singleton: SingletonType | null = null; // モジュールレベル

// register() 内:
_singleton = (global as any)[SINGLETON_KEY] ?? null;
if (!_singleton) {
    // ... 初期化 ...
    (global as any)[SINGLETON_KEY] = _singleton;
} else {
    console.log("[Episodic Memory] Singleton reused (BUG-1 guard active).");
}
```

モジュールレベルの `_singleton` は Node.js のモジュールキャッシュが無効化されるとリセットされる。そこで `global`（Symbol.for キー）に保存することでプロセス内で永続化している。

**なぜこれが「対症療法」か**: 二重呼び出しの発生自体を止めておらず、起動ごとに無駄なコードパスが3回走っている。

---

## B. なぜ register() が複数回呼ばれるのか

### B1. わかっていること

- OpenClaw のプラグインシステムは `register()` 関数を **最低3回** 呼び出す
- `register()` は同一の `api` オブジェクトではなく、毎回異なるコンテキストから呼ばれている可能性がある
- DennouAibou のプラグインローダーが `plugins.entries["episodic-claw"].config` を抽出する仕組み（L699-703）は1回目の呼び出しでのみ動作

### B2. 仮説（確率順）

**仮説A（最も可能性が高い）: スロット別再初期化** — OpenClaw は `contextEngine` と `memory` の2つのスロットに同じプラグインを割り当てると、**スロットごとに `register()` を再実行する**。`plugins.slots` に2つのスロットが設定されているため、初回 + 2スロット = 3回の呼び出しになる。検証: 各呼び出しの `api` オブジェクトが異なるか確認する。

**仮説B: モジュールキャッシュ分離** — OpenClaw のプラグインサンドボックスが `require()` のキャッシュを分離しており、同一ファイルが異なるモジュールオブジェクトとして評価される。

**仮説C: hot-reload / ウォッチモード** — 開発環境で gateWay がファイル変更を検出してプラグインをリロードする。

### B3. 検証方法

デバッグログを仕込んで、各呼び出しのスタックトレースと呼び出し回数・`api` オブジェクトの同一性を記録する（Phase 1 実装済み）:

```typescript
const BUG1_REGISTER_CALL_COUNT_KEY = Symbol.for("__episodic_claw_bug1_register_call_count__");
const lifecycleDebugLevel = process.env.DEBUG_EPISODIC_PLUGIN_LIFECYCLE;
const bug1RegisterCallCount = (((global as any)[BUG1_REGISTER_CALL_COUNT_KEY] ?? 0) + 1) as number;
(global as any)[BUG1_REGISTER_CALL_COUNT_KEY] = bug1RegisterCallCount;

if (lifecycleDebugLevel === "2") {
  const bug1Phase = _singleton ? "reuse" : "create";
  console.log(`[BUG-1 DIAG] register() call #${bug1RegisterCallCount} (${bug1Phase})`);
  console.log(`[BUG-1 DIAG] stack: ${new Error().stack?.split("\n").slice(2, 6).join(" → ")}`);
  console.log(`[BUG-1 DIAG] api identity: ${Object.prototype.toString.call(api)}, keys: ${Object.keys(api).join(",")}`);
}
```

特に `api` オブジェクトの同一性が鍵:
- **`api` が異なる** → 仮説A（スロット別）が有力
- **`api` が同一** → 仮説B（モジュールキャッシュ分離）が有力

**注意**: OpenClaw のプラグインローダーがバンドル（webpack/esbuild）されている場合、スタックトレースは `bundle.js:1:23456` のように読めない行番号になる。その場合はスタックトレースより `api` の同一性と `process.argv` の方が有用。

## C. 修正案

### 案1: ログ抑制（最小工数）

BUG-1 ガードはそのまま維持し、**2回目以降の `console.log` を `console.debug` に変更** または **`process.env.DEBUG_EPISODIC_BUG1` でゲート**する（v0.4.30e の idle poll log 抑制と同じパターン）。

**メリット**: 3行の変更。リスクゼロ。
**デメリット**: 根本原因は不明のまま。

### 案2: 登録解除フックの利用（中工数）

OpenClaw のプラグイン API に `unregister` または `dispose` フックがある場合、初回登録時に古いインスタンスを破棄して新しいインスタンスで上書きする。重複登録を許容し、常に最新のインスタンスだけを生かす。

```typescript
// register() の先頭:
const prev = (global as any)[SINGLETON_KEY];
if (prev) {
    // cleanup: shutdown old sidecar, stop old worker
    prev.rpcClient.shutdown();
    // 上書き: old に new をコピー
}
```

**メリット**: メモリリーク防止。リソースの二重確保を防ぐ。
**デメリット**: OpenClaw API に dispose が存在するか不明。調査が必要。

### 案3: OpenClaw 側の修正（大工数・非推奨）

OpenClaw 本体のプラグインローダーが `register()` を複数回呼ばないように修正する。

**メリット**: 根本解決。
**デメリット**: 
- DennouAibou の上流変更が必要（DennouAibou は v2026.4.5 で凍結中）
- 上流のプラグインローダーは複雑で、変更の影響範囲が広い
- 現在の開発リソースに対して工数が見合わない

### 案4: プロセスレベルファイルロック（中工数）

`global` ではなく、ファイルシステムにロックファイルを書き込む:

```typescript
const lockFile = path.join(os.tmpdir(), ".episodic-claw-bug1.lock");
try {
    fs.writeFileSync(lockFile, String(process.pid), { flag: "wx" });
    // 初回: 通常初期化
} catch {
    // 2回目以降: スキップ
}
```

**メリット**: プロセスクラッシュ後も lock が確実に解除される（tempdir は再起動で消える）。
**デメリット**: tempdir が消えない環境では手動削除が必要。Windows の `wx` フラグは atomic だが NFS では信頼できない。

## D. 推奨

**案1（ログ抑制）+ 案2の調査（dispose フック）** の2段階:

### Phase 1（即時対応・最小工数）

BUG-1 ガードのログを抑制する。v0.4.30e と同じパターン:

```typescript
// src/index.ts:694-794 — 3段階のデバッグレベル
// 未設定: ログ完全抑制（本番デフォルト）
// =1: "Singleton reused" のみ表示（通常デバッグ）
// =2: スタックトレース + api 同一性 + 呼び出し回数（根本調査用）
const debugLevel = process.env.DEBUG_EPISODIC_PLUGIN_LIFECYCLE;
if (debugLevel === "2") {
  console.log(`[BUG-1 DIAG] register() call #${bug1RegisterCallCount} (${bug1Phase}). stack: ${new Error().stack?.split("\n").slice(2, 6).join(" | ")}`);
  console.log(`[BUG-1 DIAG] api identity: ${Object.prototype.toString.call(api)}, keys: ${Object.keys(api).join(",")}`);
} else if (debugLevel === "1") {
  console.log("[Episodic Memory] Singleton reused (BUG-1 guard active).");
}
// 未設定 → 完全サイレント（本番デフォルト）
```

同時に、デバッグログ（stack trace）を `DEBUG_EPISODIC_PLUGIN_LIFECYCLE=2` で出力するようにする。

### Phase 2（調査・根本解決）

`DEBUG_EPISODIC_PLUGIN_LIFECYCLE=2` を有効にして KASOU で起動し、コールスタックから二重呼び出しの原因を特定。それに応じて案2（dispose フック）または案3（OpenClaw 側）の実装判断をする。

## E. リスク

| リスク | 確率 | 影響 | 軽減策 |
