# v0.4.29d — openrouterConfig 互換警告ログのクリンアップ（deprecation warning flood control）

> Date: 2026-04-27  
> Status: ✅ IMPLEMENTED + VERIFIED  
> Release Target: v0.4.29d

---

## 0. 目的

`openrouterConfig` は v0.4.29c で deprecated 化されたが、互換読込を残しているため警告ログが多く出る。  
本プランは **互換性を壊さずに**、deprecation warning のノイズを抑え、運用ログの可読性を上げる。

---

## 1. 実読証拠（3点以上）

### Evidence A — deprecated warning は loadConfig 内で毎回発火し得る

- `src/config.ts:141-146`
  - `hasOc && !hasNc` のとき `console.warn("openrouterConfig is deprecated ...")`

**意味**: 同条件で `loadConfig()` が呼ばれるたびに同じ警告が繰り返される。

### Evidence B — 互換読込は意図的に残っている

- `src/config.ts:130-154`
  - 優先順位: `narrativeConfig > openrouterConfig > flat > default`
- `openclaw.plugin.json:223-277`
  - `openrouterConfig` が `[DEPRECATED]` と明記されつつ schema に残存

**意味**: いまは「削除」ではなく「移行期間」。警告抑制は必要だが互換性は維持が前提。

### Evidence C — 移行済み判定用の観測フィールドは既にある

- `src/config.ts:161`
  - `narrativeConfigSource` を出力
- `test_config_pipeline.ts:838-856`
  - `narrativeConfigSource` の4状態をテスト済み

**意味**: 警告を大量に出さなくても、sourceフィールドで移行状況を追跡できる。

### Evidence D — 現在の設定読み込みはテスト固定化されている

- `test_config_pipeline.ts:821-862`
  - `narrativeConfig` 反映・source分類・reasoning反映が固定化

**意味**: cleanup 実装時は既存の読込契約を壊さないことが必須。

---

## 2. 方針

### Option A（推奨）

**one-shot 警告（プロセス内1回）+ source観測維持**

- `openrouterConfig` 互換読込は維持
- deprecation warning はプロセス内1回のみ出す
- `narrativeConfigSource` は継続利用

**理由**: YAGNI/KISS。最小差分でログ洪水を止め、移行情報も失わない。

### Option B

タイムベース rate-limit（例: 10分に1回）

- 実装がやや重い（時刻管理が増える）
- 今回は過剰

## 🔧 Pro Engineer Review — 2026-04-27
> Perspective: Google / IBM Production Engineering  
> Principles applied: YAGNI · KISS · DRY · SOLID  
> Source code verified: ✅ (as of 2026-04-27)

### 📍 Current Reality (Source Code vs. Document)
- ✅ **Document matches code**: `src/config.ts` 内の `loadConfig` は、`openrouterConfig` が存在しかつ `narrativeConfig` がない場合、呼ばれるたびに `console.warn` を出力している。
- ✅ **Document matches code**: `narrativeConfigSource` フィールドは既に実装・テスト済みであり、警告を減らしても observability（観測性）は維持される。

### 🎯 Core Problem (1 sentence)
> 互換性のために残した `openrouterConfig` の読み込み処理が、設定ロードのたびに無駄な警告ログを出力し、運用時のノイズ（ログスパム）になっている。

### 🔍 Principle Filter
| Check | Result | Note |
|-------|--------|------|
| YAGNI — Is this actually needed now? | ✅ Yes | 不要なログスパムは本番環境での監視やデバッグを妨げるため、即時対応が必要。 |
| KISS — Is there a simpler solution? | ✅ Simple enough | プロセス内1回（モジュールスコープのフラグ）で制御するのは最もシンプルで確実なアプローチ。 |
| DRY — Any duplication to eliminate? | ✅ None | 該当せず。 |
| SOLID — Any violation causing real problems? | ✅ None | 該当せず。 |

### 🛤️ Solution Options

#### Option A — モジュールスコープのフラグによる One-shot 警告 *(推奨)*
**Approach**: `src/config.ts` のモジュールレベルに `warnedOpenrouterDeprecated = false` を配置し、警告をプロセスで1回のみにする。  
**Implementation cost**: Low  
**Risk**: Low  
**Why recommended**: KISS の原則に完全に合致する。設定リロード等の理由で `loadConfig` が複数回呼ばれた場合のログスパムを防ぎつつ、「設定移行が必要」という最も重要な情報はプロセス起動時に必ず1回伝わるため、要件を過不足なく満たせる。  
**Concrete steps**:
1. `src/config.ts` に `let warnedOpenrouterDeprecated = false;` を追加。
2. `if (hasOc && !hasNc && !warnedOpenrouterDeprecated)` の時にのみ警告を出力。
3. 出力後、直ちに `warnedOpenrouterDeprecated = true;` をセット。
4. 警告文に「使用中のフォールバック元」等の文脈（`using openrouterConfig fallback`）を足す。
5. `test_config_pipeline.ts` で警告回数をモック検証。

#### Option B — Rate Limit（時間ベースの抑制）
**Approach**: 前回警告した時刻を保存し、一定時間（例: 10分）経過していれば再度出力する。  
**Implementation cost**: Medium  
**Risk**: Low  
**When to choose this instead**: サーバーが長期間起動し続け、その間に運用者が何度も切り替わるようなシステムにおいて、再起動なしで定期的に注意喚起したい場合。

### ✅ Pro Recommendation
> **Choose Option A because**: エージェント（またはプラグイン）のライフサイクルにおいて、1回警告を出せば設定管理者が気づくには十分。それ以上のレートリミット制御を追加するのは YAGNI に反し、無駄な複雑さを持ち込むだけであるため。  
> Estimated implementation: 15 minutes  
> Rollback plan: `src/config.ts` のフラグを削除するだけ。

### ⚡ Quick Wins (implement regardless of option chosen)
- [x] テストファイル (`test_config_pipeline.ts`) で `console.warn` の発火回数を検証する際は、`jest.spyOn` 等（今回は `sinon` か生の関数置き換え）を使い、テスト実行時の標準出力を汚さないよう `afterEach` 等で元の `console.warn` に必ず戻すこと。
