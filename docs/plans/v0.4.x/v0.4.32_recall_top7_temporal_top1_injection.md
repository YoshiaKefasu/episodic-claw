# v0.4.32 — Recall Top-7 → 時系列 Top-1 注入

> **作成日**: 2026-05-24  
> **ステータス**: Implemented / Unreleased  
> **目的**: Episodic-Claw の自動メモリ注入を「全DB → ベクトル検索 → Top-K(7) → 時系列重みで Top-1 → 注入」に変える。  
> **スコープ**: Episodic-Claw のみ。DennouAibou / OpenClaw core は変更しない。

---

## A. 結論

今の自動回収は、Go 側で候補をスコア順に返し、TS 側でそのまま複数件を注入している。  
今回の v0.4.32 では、**自動回収だけ**を対象にして、まず Top-K を 7 件に広げ、その 7 件の中から **時系列が最も新しい 1 件だけ**を注入する。

この変更でやることは 2 つだけ。

1. 自動回収の取得件数を 5 → 7 に上げる
2. `retrieveRelevantContext()` の注入段階を「複数件」から「1件」に変える

---

## B. 調査で読んだ証拠

### B1. 自動回収の Top-K は今 5 件で固定

`src/index.ts:1332` と `src/index.ts:1540`:

```ts
const k = 5;
```

意味: before_prompt_build と assemble の両方で、今は自動回収の候補数が 5 件固定。

### B2. 注入処理は Top-K をそのまま複数件流している

`src/retriever.ts:760-893`:

- `rpcClient.recall(query, k, ...)` で候補を取得
- `deduped = sourcedResults.slice().sort((a, b) => scoreOf(b.item) - scoreOf(a.item))`
- その後、token budget が尽きるまで複数件を `assembled` に積む

意味: いまは「Top-K から 1 件だけ選ぶ」段階がない。注入は複数件前提。

### B3. Go 側は freshness を既に計算している

`go/internal/vector/store.go:1315-1421` と `go/internal/vector/bayes.go:49-61`:

```go
freshnessScore := freshnessScore(rec.Timestamp, now)
finalScore := ... + (defaultRecallWeights.freshness * freshnessScore) + ...
```

意味: 時系列の重み自体は、すでに Go 側で算出できている。  
このため、v0.4.32 では Go 側の DB/検索ロジックを触らず、TS 側で「どの 1 件を注入するか」を決めれば足りる。

### B4. レスポンス型には freshnessScore がもうある

`src/types.ts:199-230`:

```ts
export interface RecallScoreBreakdown {
  semanticScore?: number;
  freshnessScore?: number;
  ...
}
```

意味: 新しい schema 追加は不要。既存の戻り値で時系列重みを選べる。

## C. 現在の状況

現状の流れはこう。

```text
全DB
→ Go 側でベクトル検索 + 現在の総合スコア評価
→ Top-K(5)
→ TS 側でスコア順に並べる
→ token budget の範囲で複数件を注入
```

今回やりたい流れはこう。

```text
全DB
→ Go 側でベクトル検索 + 現在の総合スコア評価
→ Top-K(7)
→ TS 側で時系列重みの Top-1 を選ぶ
→ 1件だけ注入
```

補足: `ep-recall` のような明示呼び出しはこの変更の対象外。自動注入だけを絞って変える。

---

## D. 実装方針

### D1. 自動回収の Top-K を 7 に固定

- `src/index.ts` の `before_prompt_build` と `assemble` の両方を 7 にする
- `retrieveRelevantContext()` のデフォルト値はそのままでもよい。呼び出し側 2 箇所を 7 にするだけで足りる
- 明示ツール `ep-recall` はそのまま

### D2. 注入前に「時系列 Top-1」を選ぶ

`src/retriever.ts` に小さな selector を追加する。

選び方の優先順はこうする。

1. まず既存の degraded fallback 低スコア除外で候補集合を絞る
2. `freshnessScore` が `number` で入っているならそれを最優先
3. `freshnessScore` が無い / 0 で省略される場合は `timestamp` の新しさで判定する
4. それでも同点なら `Score` をタイブレークに使う

補足: Go 側の JSON は `freshnessScore,omitempty` なので、0 の場合はフィールドが省略される。TS 側は truthy 判定ではなく `typeof freshnessScore === "number"` で扱う。

### D3. 既存の安全ガードは残す

- degraded fallback の低スコア除外は残す
- re-injection guard もそのまま残す
- episodeIds が 1 件になるので、re-injection guard のハッシュ対象は自然に 1 件分へ変わる。別のハッシュ変更は不要。

### D4. 返却値は 1 件前提にする

- `injectedEpisodeCount` は 1 か 0
- `episodeIds` は 1 件だけ
- `firstEpisodeId` は選ばれた 1 件
- `truncatedEpisodeCount` は原則 0（1件しか注入しないため）
- もし選ばれた 1 件が token budget を超えるなら、部分注入はしない。`recall_empty` か `degraded_low_confidence` のどちらかで空返しにする

## E. テスト方針

### E1. 時系列 Top-1 の選択テスト

`test_phase4_5_retriever_anchor.ts` に追加する。

複数の mock recall 結果を返して、以下を確認する。

- Top-K が 7 件で呼ばれる
- その 7 件の中で最も新しいものが 1 件だけ注入される
- `freshnessScore` がある場合はそれが優先される
- `freshnessScore` が省略されるケースでも `timestamp` へフォールバックできる

### E2. 注入件数の回帰テスト

- いまの「複数件がそのまま積まれる」前提のテストを、1件注入前提に更新する
- `degraded_low_confidence` の既存テストは維持する

### E3. auto path の呼び出し回数テスト

- before_prompt_build / assemble の両方で `k = 7` が渡ることを確認する
- `ep-recall` は対象外のままにする

## F. リスク

| リスク | 影響 | 対策 |
|---|---|---|
| freshnessScore と timestamp の優先順位が曖昧 | 期待と少しズレる | selector の優先順を明文化する |
| `freshnessScore` が JSON から省略されるケース | 0 を falsy と誤判定すると選択がぶれる | `typeof freshnessScore === "number"` で扱う |
| 1件注入に変わることで、今まで見えていた補助記憶が消える | 一時的に文脈が薄くなる | Top-K を 7 に増やして候補の質を保つ |
| Go 側の総合スコアと TS 側の最終選択が別軸になる | 説明しづらくなる | ログに selectedEpisodeId / freshnessScore / timestamp を残す |
