## 0. 背景

`ComputeStage2BatchScores` は Tombstone 判定の入口であり、Replay 選抜の土台になる重要処理。  
現状は機能上は成立しているが、運用規模が上がると「停止耐性」「可観測性」「バッチ粒度」に改善余地がある。

## 2. 問題の本質（1文）

> Stage2 スコア更新は正しく動作しているが、長時間処理時の中断制御と運用可視化が薄く、規模拡大時の安定運用に不利。

---

## 3. 方針オプション

### Option A（採用）: **運用耐性強化（意味変更なし）**

内容:
1. context キャンセルに応答する
2. Stage2 更新を小分け commit 化する
3. 実行サマリ（scanned/skipped/scored/tombstoned/commit回数）を構造化で残す

メリット:
- スコア意味を変えずに安定性を上げられる
- rollback が容易
- 影響範囲が `store.go` 中心で閉じる

デメリット:
- 実行ログ・メタの追加でわずかに管理項目が増える

---

### Option B: **判定モデルも変更（2段階 tombstone 等）**

内容:
- `pending_tombstone` などの中間状態導入

デメリット:
- データモデル影響が大きく、今回の v0.4.26e スコープを超える

---

### Option C: 現状維持

内容:
- 変更なし

デメリット:
- 運用可観測性と中断耐性の改善機会を逃す

---

## 4. 方針決定（Decision Lock）

- v0.4.26e では **Option A** を採用する
- **スコア計算式 (`scoring.go`) と閾値 (`0.3 / 0.8`) は変更しない**
- Option B は別版（v0.4.27+ 候補）で検討する
- **ロック戦略は現状維持（`ComputeStage2BatchScores` の `s.mutex.Lock()` 方針を変更しない）**
- 分割 commit 導入後の整合性契約は **「部分反映を許容」** とする
- cancel 時の契約は **「未 commit 分は破棄し、直近 commit 済み分のみ有効」** とする

## 5. 実装計画（最小差分）

### 5.1 変更ファイル
- `go/internal/vector/store.go`
- （必要時）`go/internal/vector/*_test.go` 追加

### 5.2 変更項目

#### Fix 1 — context 中断対応
- ループ内に `select { case <-ctx.Done(): ... }` を追加
- 中断時は **未 commit 分を flush しない（破棄）**
- `ctx.Err()` を返し、summary に `cancelled=true` と `cancelReason` を残す

#### Fix 2 — 小分け commit
- 1バッチ単発 commit をやめ、一定件数ごとに commit
- 例: `stage2BatchCommitSize`（初期値 300）
- 最終端で残件 commit
- **部分反映許容ポリシー**をコメントと plan に明記（all-or-nothing へ戻さない）

#### Fix 3 — 実行サマリ可視化
- 以下をカウントして summary 出力:
  - `agentWs`, `runId`, `startedAt`, `durationMs`
  - `scanned`, `eligible`, `skippedRecent`, `rescored`, `tombstoned`, `commitCount`, `cancelled`, `cancelReason`
- 既存ログに加えて、運用で追える1行サマリを出す

#### Fix 4 — 非変更ガード（回帰防止）
- `CalculateScoreStage2` の式は触らない
- Tombstone条件式は据え置き
- Replay 側閾値は据え置き
- `ComputeStage2BatchScores` のロック方針変更（Lock→RLock化や分離ロック化）は本版で行わない

## 8. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| 小分け commit で処理時間が微増 | 低〜中 | commit サイズを 200〜500 で実測調整 |
| 中断時の部分反映で理解が難しい | 中 | 「未 commit 分破棄」契約を固定し、`cancelReason/commitCount` を必ず記録 |
| ログ増加 | 低 | サマリは1回/Passに限定 |
| ロック最適化を同時実施して回帰 | 中〜高 | v0.4.26e ではロック戦略変更禁止（別版へ分離） |

### Post-implementation 検証 (2026-04-22)

**Bug #2 発見・修正**: `commitBatch()` 失敗時に `Stage2RunSummary` が保存されなかった（cancel時は保存されるのに非対称）。
- **修正**: `commitBatch()` の error return 直前に summary 保存を追加
- **追加**: `Stage2RunSummary.CommitError string` フィールド追加（`json:"commit_error,omitempty"`）
  - cancel時: `Cancelled=true` + `CancelReason` で識別
  - commit失敗時: `CommitError` で識別
  - 正常終了: 両方とも空
- **3経路の対称性確認**:
  - ✅ 正常終了: summary保存（CommitCount > 0, no error fields）
  - ✅ Cancel: summary保存（Cancelled=true, CancelReason set）
  - ✅ Commit失敗: summary保存（CommitError set, DurationMs set）

**その他検証項目**:
- ✅ `pebble.Batch.Reset()` API 有効性確認（`go doc` で公式API確認）
