## 2. コア問題（1文）

> CLI skip ログの抑制粒度が「同一プロセス内」に閉じているため、node/gateway 同時運用の多プロセス環境でログ洪水が発生し、障害解析ノイズを増幅している。

## 3. 方針オプション

### Option A+ — helper抽出 + ログ沈黙化先行（採用確定 ✅）

> 元 Option A（低リスク抑制）を拡張 — helper抽出を加えてテスト可能化しつつ、env優先/daemon化は先送り。

**Approach**: D1（helper抽出・既存動作の純粋リファクタ）+ D2（ログ沈黙化）を先行実装。env優先判定もnode daemon化も先送り。  
**Cost**: Low  
**Risk**: Low

**理由**（Pro Engineer Review Code-Verified）:
- ログ洪水（運用痛み）と node分類（設計債務）は別問題。KISSは「痛みを先に止める」
- `OPENCLAW_SERVICE_KIND=node` 優先判定を実装すると、helperが `mode=daemon` を返し、register()が全初期化（NarrativeWorker + OpenRouterClient + kuromojin + watcher）を走らせる — CPU 73.1% 環境で gateway timeout 悪化の実害リスク
- helper抽出は純粋リファクタ（既存動作を変更しない） — 後からenv優先/daemon化に切り替えるのは1行変更で可能

### Option B — `node` daemon化 + `OPENCLAW_SERVICE_KIND` 優先（参考・先送り）

**Approach**: `DAEMON_CMDS` に `node` を追加し、さらに `OPENCLAW_SERVICE_KIND=node|gateway` を argv より優先判定。  
**Cost**: Medium（lazy-init 化込み）  
**Risk**: Medium-High

**懸念**:
- node サービス側で plugin 全初期化が走り、CPU/起動経路に新規影響を持つ（Evidence D: 73.1% CPU）。
- 安全な実施には register() lazy-init 化が前提（~50行+テストの Medium リファクタ）。
- 事故時の切り戻し判断が難しくなる。

## 4. 変更仕様（Fix D1〜D5）

### Fix D1 — runtime 判定を関数化（テスト可能化）

- `src/index.ts` に pure helper を追加:
  - 例: `resolveRuntimeMode(argv): { mode: "daemon" | "cli"; reason: string }`
- **v0.4.28d 範囲**: 既存の argv 判定のみを関数化（純粋リファクタ・動作変更なし）
- daemon 許可: `gateway | agent | test`（既存 `DAEMON_CMDS` と同一）
- それ以外は cli
- > **DEFER**: `OPENCLAW_SERVICE_KIND` env 優先判定・`node` の daemon 許可は別PR（⇒ Deferral Record）

### Fix D2 — CLI skipログの追加抑制（保険）

- `mode=cli` 時、デフォルトでは `console.log("CLI mode detected...")` を出さない。
- デバッグ時のみ出すフラグを追加（例: `EPISODIC_LOG_CLI_SKIP=1`）。
- 既存の `Symbol.for("episodic.cli.skipped")` 抑制は維持（同一プロセス内重複抑止）。
> 注: v0.4.28d では `node` は daemon 側へ移動しないため、D2 が主たるログ洪水対策。node 分類の改善は別PR。

### Fix D3 — 監査しやすい最小観測イベント

- daemon 起動時のみ1回、runtime 判定結果を短く出力（既存 register ログに統合可）。
- 例: `event=runtime-mode mode=daemon reason=argv`。
- > 注: env優先判定は別PRスコープのため、v0.4.28d では reason=argv のみ。

### Fix D4 — 回帰防止テスト追加

- 新規テスト（専用 `test_runtime_mode_detection.ts`）:
  1. `argv=[...,"gateway"]` → daemon
  2. `argv=[...,"agent"]` → daemon
  3. `argv=[...,"test"]` → daemon
  4. `argv=[...,"node"]` → **cli**（v0.4.28d では変更なし）
  5. `argv=[...,"start"]` → cli（意図的除外の回帰確認）
  6. `argv=[]` → cli
  7. CLI mode で `EPISODIC_LOG_CLI_SKIP` 未設定なら skip 文言を出さない
  8. `EPISODIC_LOG_CLI_SKIP=1` で skip 文言を出す
  9. daemon 起動時に runtime mode event が出力される
- > **DEFER**: `OPENCLAW_SERVICE_KIND` env 優先判定テスト・`node` daemon化テストは別PR

### Fix D5 — 運用Runbook追記（incident連携）

- `docs/incidents/...investigation.md` または本 plan に「再発時の一次切り分け」を短文化:
  - node停止→probe回復可否
  - CPU高騰時の確認順
  - pluginノイズ無効化フラグ

### 📍 Current Reality (Source Code vs. Document)

- ✅ Document correctly identifies CLI skip log source: `src/index.ts:548-552` (`DAEMON_CMDS`, `isDaemon`)
- ✅ Document correctly identifies `Symbol.for` limitation: same-process only, multi-process environments re-emit
- ⚠️ **Critical discrepancy**: Plan underestimates daemon initialization cost. When `isDaemon=true`, the code runs:
  - `loadConfig()` — config parsing + validation
  - `new EpisodicCoreClient()` — RPC client
  - `new EpisodicRetriever()` — semantic recall engine  
  - `new OpenRouterClient()` — HTTP client with API key (L602-610)
  - `new NarrativeWorker()` — heavy narrative processing pipeline (L611-613)
  - Fire-and-forget `kuromojin` dictionary warm-up (L630-643)
  - 15 `api.on()` hook registrations — event handlers for gateway lifecycle, prompt building, file watching, etc.
  - File watcher registration per workspace (L766-800)
  - **This is NOT "plugin init" — it's full service bootstrap.**
- ⚠️ **Critical discrepancy**: Incident Evidence D shows `openclaw-node` at **73.1% CPU** *without* episodic daemon init. Adding all the above will **increase** CPU load on node, worsening the gateway timeout problem (Evidence E: node stop → probe recovery).
- ⚠️ `OPENCLAW_SERVICE_KIND` is **not referenced anywhere in `src/`** — it's set by DennouAibou's `service-env.ts` and available via `process.env`, but the plan doesn't note this cross-repo dependency.
- ⚠️ Plan's Option B risk is "Medium-High" but doesn't detail *what specifically* breaks or how to detect it in canary.

### 🎯 Core Problem (1 sentence)

> CLI skipログの多プロセス反復出力がログ洪水を起こしている — 根本痛みは「ノイズ」であって「nodeの分類ミス」ではない。

### 🔍 Principle Filter

| Check | Result | Note |
|-------|--------|------|
| YAGNI — Is node daemon化 actually needed now? | ❌ No | ログ洪水は分類修正なしでも解決可能。daemon化は「将来の正しさ」で今の痛みに不要 |
| KISS — Simpler solution exists? | ✅ Yes | ログ沈黙化（D2）だけで洪水は止まる。これが最短経路 |
| DRY — Duplication to eliminate? | ✅ Yes | `isDaemon` 判定がインライン → helper 抽出（D1）は正当な DRY 改善 |
| SOLID — Violation causing real problems? | ⚠️ Yes | `register()` が判定 + 初期化 + フック登録を1関数で担当（SRP違反）。helper抽出は妥当 |

**優先順位**: YAGNI + KISS > DRY > SOLID — ログ洪水を止めるのに node daemon化は不要

### 🛤️ Solution Options

#### Option A+ — Enhanced Low-Risk（推奨）
**Approach**: D1（helper抽出・既存動作の純粋リファクタ）+ D2（ログ沈黙化）を先行実装。**env優先判定もnode daemon化も先送り**。  
**Implementation cost**: Low  
**Risk**: Low  
**Why recommended**: 
- ログ洪水（運用痛み）と node分類（設計債務）は**別問題**。KISSは「痛みを先に止める」
- ⚠️ `OPENCLAW_SERVICE_KIND=node` 優先判定を実装すると、helperが `mode=daemon` を返し、**register()が全初期化を走らせる** — Option Bと同じCPU負荷増。env優先の追加はregister()のlazy-init化とセットでなければ安全ではない
- helper抽出は純粋リファクタ（既存動作を変更しない）であり、後からenv優先/daemon化に切り替えるのは1行変更で可能（ロックインなし）

**Concrete steps**:
1. `resolveRuntimeMode(argv, env)` helper を追加 — **既存のargv判定のみ**を関数化（D1）
2. CLI skipログをデフォルト沈黙化 + `EPISODIC_LOG_CLI_SKIP=1` flag（D2）
3. daemon起動時に runtime mode event を1行出力（D3）
4. テスト追加（D4）— 既存判定のテストのみ
5. **DEFER**: `OPENCLAW_SERVICE_KIND` env優先判定 + `DAEMON_CMDS` に `node` 追加は、register() lazy-init化完了後の別PRで（⇒ Deferral Record）

#### Option B — node daemon化 + service kind優先（プラン元案）
**Approach**: D1〜D5 を一括実装。`DAEMON_CMDS` に `node` を追加。  
**Implementation cost**: **Medium**（単純な配列追加は Low だが、必須の lazy-init 化は ~50行+テスト追加で Medium）  
**Risk**: Medium-High  
**When to choose this instead**: node が軽量な hook-only プラグインであれば問題ない。**ただし現在のコードは hook-only ではない**（NarrativeWorker + OpenRouterClient + kuromojin + watcher を全起動する）。これらが node に不要であれば、先に lazy-init 化または条件分岐が必要。

**Concrete steps**:
1. D1〜D5 全実装
2. **必須追加**: register() の lazy-init 化（service kind 別に初期化段階を制御） — これは「低コスト追加」ではなく **Medium のリファクタ**。`OPENCLAW_SERVICE_KIND=node` 時は NarrativeWorker/OpenRouterClient/kuromojin を skip し、hook登録のみ実行する分岐が必要
3. **必須追加**: canary で node CPU使用率の前後比較を明示的に監視（startup spike と steady-state を分離）
4. **必須追加**: 1行ロールバック条件（`DAEMON_CMDS` から `node` を削除するだけで元に戻ることを確認）

**前提確認（prerequisite）**: nodeがepisodic pluginのどの機能を必要としているかの調査が必須 — hook-only で十分なら lazy-init は不要。NarrativeWorker も必要なら lazy-init 化が必須。この調査は Option A+ でも env優先追加の前提になる

### ✅ Pro Recommendation

> **Choose Option A+ because**: ログ洪水と node分類は別問題。前者は D2（ログ沈黙化）だけで即解決。

### 🚨 Risk: node daemon化の実害シナリオ

```
現在の openclaw-node（Evidence D）:
  CPU: 73.1%（steady-state）
  episodic plugin: SKIP（CLI扱い → 軽量）

daemon化後の openclaw-node（lazy-init なし）:
  Startup spike: +OpenRouterClient初期化 + kuromojin辞書ロード（数百ms〜数秒）

lazy-init ありの場合:
  OPENCLAW_SERVICE_KIND=node → hook登録のみ実行、重コンポーネントは初回使用時まで遅延
  → startup spike は最小限、steady-state も必要時のみ起動
  → これが Option B の安全な実施条件
```
