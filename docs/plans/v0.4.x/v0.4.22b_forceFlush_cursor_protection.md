## 0. 目的

未物語化メッセージを **1件ずつ低遅延で耐久化** し、再起動/強制終了でロスしない構成にする。

- StateDB(Pebble): 設定/cursor/save-hashのみ（メッセージを入れない）
- WAL(JSONL): 1メッセージ1行で追記
- CacheDB(queue): 章が閉じた時にチャンク一括enqueue

## 2. 監査で出た Must-fix（実装前に必須）

### MF-1 (BLOCKER) — WAL clear競合の解消

**問題:** 古いflushの `walClear` が新規append後に走ると、最新行まで消える可能性。  
**対策:** 「active WAL を clear」ではなく、**rotate（世代分離）** を採用。

### MF-2 (BLOCKER) — afterCompaction の署名整合

`afterCompaction()` に `agentWs/agentId` が必要。  
`index.ts` 呼び出し側も合わせて変更する。

### MF-3 (HIGH) — multi-agent同一workspace衝突

WALファイル名に `agentId` を含める。

### MF-4 (MED) — 64K判定ロジック統一

`Math.ceil(chars/4)` ではなく、既存の `estimateTokens()` を使い同一推定器に統一。

### MF-5 (MED) — WAL読込の安全ガード

WAL読込はサイズガード + 行単位復元（部分行skip）を入れる。

## 3. 設計（最小で頑丈）

### 3.1 WALファイル構成

- Active: `{agentWs}/.episodic-wal.{agentId}.active.jsonl`
- Staged: `{agentWs}/.episodic-wal.{agentId}.flush-{flushId}.jsonl`

**理由:** activeを直接clearしない。flush対象世代だけ別ファイルに切り出して削除する。

### 3.2 メッセージ受信時

1. dedup
2. `buffer.push(...)`
3. `fs.appendFileSync(activeWalPath, line)`

### 3.3 章を閉じる時（surprise / 64K / idle / force）

1. `walRotateForFlush(flushId)` を実行
   - active → staged に rename
   - 新しい空activeを即作成
2. 既存の splitIntoChunks → `cache.enqueueBatch`
3. enqueue成功時のみ `walDeleteStaged(flushId)`
4. enqueue失敗時は staged を残す（再起動復元用）

### 3.4 再起動時

復元順序:
1. staged WAL 全件（古い順）
2. active WAL

部分行・破損行は skip して warning ログ。

## 7. Acceptance Criteria

1. `processTurn` でメッセージ追加ごとに active WAL へ1行追記される
2. boundary時に active→staged rotate され、新規メッセージは新activeへ追記される
3. enqueue成功時のみ staged削除、失敗時は staged保持
4. warm-startで staged→active の順に復元される
5. 破損した末尾行はskipされ、復元処理は継続される
6. `forceFlush` 後に `lastProcessedLength` が保存前値に復元される
7. B-1後の再起動で全量再処理が発生しない
8. `segmentationTimeGapMinutes=30` で idle/time-gap が同値で動作する

#### 4.1 `src/segmenter.ts` — processTurn組み込み箇所

| processTurn内の位置 | WAL処理 |
|---|---|
| `buffer.push(...dedupedMessages)` — first absorb | `for (msg of dedupedMessages) { walAppend(...) }` |
| `isTimeGapBoundary` → boundary | `walRotateForFlush` → `handleSegmentBoundary(..., timeGapFlushId)` → 新メッセージ `walAppend` |
| `shouldBoundary` → surprise/size | `walRotateForFlush` → `handleSegmentBoundary(..., boundaryFlushId)` → 新メッセージ `walAppend` |
| `!shouldBoundary` → append | `walAppend` per deduped message |
| `catch` → error recovery | `walAppend` per deduped message（best-effort） |

#### 4.1 `src/segmenter.ts` — poolAndQueue / handleSegmentBoundary

- `handleSegmentBoundary` 署名: `(agentWs, agentId, surprise, reason, walFlushId = -1)`
- `poolAndQueue` 署名: `(agentWs, agentId, surprise, reason, walFlushId = -1)`
- `enqueueNarrativeChunks` の `.then()` 内で `walDeleteStaged(agentWs, agentId, walFlushId)` 呼び出し
- 失敗時は staged 保持（再起動時の `walRestore` で回収）

#### 4.1 `src/segmenter.ts` — forceFlush cursor保護

```
1. savedCursor = this.lastProcessedLength     // 保存
2. walRotateForFlush → enqueue
3. 成功: pool.clear() + buffer=[] + lastProcessedLength=0 + persistCursor + walDeleteStaged
4. 失敗: this.lastProcessedLength = savedCursor  // 復元
         this.persistCursor(...)                   // 永続化
         // staged は保持（再起動復元用）
```

#### 4.4 `src/segmenter.ts` — 64K判定統一

変更前:
```typescript
const estimatedChars = this.buffer.reduce((acc, m) => acc + extractText(m.content).length, 0);
const sizeLimitExceeded = estimatedChars > this.maxBufferChars;
```

変更後:
```typescript
const bufferText = this.buffer.map(m => extractText(m.content)).join("\n");
const estimatedBufferTokens = estimateTokens(bufferText);
const sizeLimitExceeded = estimatedBufferTokens >= HARD_TOKEN_CAP;
```

`maxBufferChars`（デフォルト7200文字）は `HARD_TOKEN_CAP`（64Kトークン）に置換。v0.4.22cで `maxBufferChars` 自体をdeprecated化する予定。
