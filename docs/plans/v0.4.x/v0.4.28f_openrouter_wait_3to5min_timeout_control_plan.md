# v0.4.28f — OpenRouter 応答待ちを 3〜5 分まで許容し、超過時に失敗判定する

> Date: 2026-04-25

> Scope: `episodic-claw`（設定/クライアント配線/回帰テスト）

## 0. 目的

現状は OpenClaw 側の OpenRouter request timeout が 30 秒固定で、
OpenRouter 側で後から完走するケースでも、OpenClaw 側は失敗扱いを継続してしまう。

本プランの目的は以下。

1. 応答待ち時間を **3〜5分**に設定可能化
2. 指定時間を超えたら明示的に失敗判定
3. 既存運用への blast radius を最小化（デフォルト互換維持）

---

## 1. 実読証拠（3点以上）

### Evidence A — OpenClaw 側は 30 秒で timeout 失敗を出している

- `X:\tmp\openclaw\openclaw-2026-04-25.log:496`
  - `Attempt 4/4 failed [timeout] ... timeout after 30000ms`
- `X:\tmp\openclaw\openclaw-2026-04-25.log:497`
  - `primary attempt 11/12 failed [timeout] ...`

**意味**: 現在の失敗判定が 30 秒ベースで発生している。

### Evidence B — OpenRouterClient は timeoutMs=30000 をデフォルト採用

- `src/openrouter-client.ts:147`
  - `timeoutMs: 30000`
- `src/openrouter-client.ts:286`
  - `setTimeout(() => controller.abort(), this.config.timeoutMs)`

**意味**: 30秒超の生成はクライアント都合で中断される。

### Evidence C — index 側で timeout/retry の上書き設定を渡していない

- `src/index.ts:620-626`
  - `new OpenRouterClient({ apiKey, model, maxTokens, temperature, reasoning })`

**意味**: 現状は `openrouter-client.ts` のデフォルト（30s, maxRetries=3）に依存。

### Evidence D — 同一 chunk が長時間失敗ループに入る

- `X:\tmp\openclaw\openclaw-2026-04-25.log:379, 386, 391, 396, 402, 407, 409, 419, 432, 456, 475, 497`
  - `main:2026-04-25T10-05-17-154Z-0001` が `attempt 1/12 → 11/12` まで失敗継続

**意味**: 短い timeout + 上位リトライで「失敗が続いて見える」症状が拡大する。

### Evidence E — ユーザー提供 OpenRouter Activity では同時刻帯に成功履歴あり

- 添付画像（Apr 25, 17:19 / 17:40, Gemma 4 31B free, stop finish）

**意味**: 「OpenRouter成功」と「OpenClaw失敗連続」が同時に起こり得る。

---

## 2. 根本原因（要約）

OpenRouter 側の完走可能時間に対して、OpenClaw 側の request timeout (30s) が短すぎる。
その結果、OpenClaw は先に失敗判定し、同一 chunk の retry ループが伸びる。

---

## 3. 方針オプション

### Option A（推奨）: timeout と transport retry を configSchema で明示制御

- `openrouterConfig.timeoutMs` を追加（3〜5分まで設定可能）
- `openrouterConfig.maxRetries` も追加（0〜5）
- **3〜5分で打ち切りたい運用**は `maxRetries=0` を推奨

**理由**: 最小差分で確実に挙動を制御できる。既存実装を壊さない。

### Option B: 「総待ち時間 budget」を新規実装して retries 全体を強制打ち切り

- 厳密な総時間管理は可能
- ただし変更範囲が広く、今回の即応修正としては重い

**判断**: v0.4.28f は Option A、budget 方式は将来版で検討。

> OpenRouterClient の `timeoutMs`/`maxRetries` がハードコードのデフォルト（30s/3回）に固定されており、ユーザー設定から配線されていない。

### 🛤️ Solution Options

#### Option A — 最小差分で配線 *(推奨)*
**Approach**: F1〜F6 をそのまま実装。ただし命名を `openrouterMaxRetries`（`Transport` なし）に統一。  
**Implementation cost**: Low（変更ファイル数: 5、変更行数: 計 20行以下）  
**Risk**: Low（デフォルト値を変えない、既存パターンに沿う）  
**Why recommended**: `OpenRouterClient` のコンストラクタが既に `Partial<OpenRouterConfig>` なので F3 は2行追加のみ。`clampFiniteInt()` 再利用で F2 も簡潔。命名統一で将来の混乱を防ぐ。

**Concrete steps**:
1. `openclaw.plugin.json` に `openrouterConfig.timeoutMs` / `openrouterConfig.maxRetries` を追加（F1）
2. `types.ts`: `openrouterTimeoutMs?: number` / `openrouterMaxRetries?: number` を追加（F2）
3. `config.ts`: `loadConfig()` に 2行追加 — `clampFiniteInt` で clamp（F2）
   ```typescript
   openrouterTimeoutMs: clampFiniteInt(rawConfig?.openrouterConfig?.timeoutMs, 30000, 300000, 30000),
   openrouterMaxRetries: clampFiniteInt(rawConfig?.openrouterConfig?.maxRetries, 0, 5, 3),
   ```
4. `index.ts:657-663`: `timeoutMs: cfg.openrouterTimeoutMs` / `maxRetries: cfg.openrouterMaxRetries` を追加（F3）
5. `index.ts:647`: Config loaded ログに2キーを追記（F4）
6. `test_config_pipeline.ts`: expected key セット + clamp テスト追加（F5）
7. build + test（F6）

#### Option B — 「総待ち時間 budget」方式
**Approach**: retry 全体の総経過時間に上限を設け、強制打ち切りする新機能。  
**Implementation cost**: High（`OpenRouterClient` の retry ループ改修が必要）  
**Risk**: Medium（retry ロジックへの変更は既存動作への影響が大きい）  
**When to choose instead**: retry 回数ではなく「総経過時間」で厳密に制御したい場合（v0.4.29以降の検討候補）

### ✅ Pro Recommendation
> **Option A を選択する**。`OpenRouterClient` が既に `Partial<OpenRouterConfig>` を受け付けているため、F3 の配線は2行追加のみ。`clampFiniteInt()` の DRY 再利用で F2 も5行以内。全体の blast radius は最小。  
> 推定実装: 30〜45分  
> Rollback plan: デフォルト値を据え置いているため、設定ファイルから追加キーを削除するだけで元の挙動に戻る。
