# v0.4.30c: Transport retry schedule hardening (60/120/240/480/960/1280s)

## 目的

Episodic-Claw の **モデル呼び出しリトライが 60 秒待たずに 3〜12 秒で回ってしまう**件を、ログとソースに grounded して原因を切り分け、修正方針を確定する。

ここで言う「60 秒」は v0.4.30a で導入した `GATE_RETRY_DELAY_MS = 60_000` の意図（モデルに出力改善の猶予を与える）と、**rate-limit/429 系で短すぎる再試行を避ける**運用要請の両方を満たすための下限。

## 現象（証拠）

### 証拠1: Gemini Direct 429 が 3s, 6s, 12s... で再試行

`openclaw-2026-05-05.log` にて、`gemma-main` が 429 を受けた直後に **Retrying in 3000ms / 6000ms / 12000ms ...** で回っている。

- `openclaw-2026-05-05.log:1616`
  - `Please retry in 32.269782683s.. Retrying in 3000ms...`
- `openclaw-2026-05-05.log:1617`
  - `Please retry in 29.119693768s.. Retrying in 6000ms...`
- `openclaw-2026-05-05.log:1618`
  - `Please retry in 22.924009053s.. Retrying in 12000ms...`

→ サービス側（Gemini）が「32秒待て」と言っているのに、クライアント側は 3 秒で再試行している。

### 証拠2: OpenRouter 429 も 3s / 6s / 12s… の表記が混在

- `openclaw-2026-05-05.log:1629`（NarrativeWorker）
  - `Retrying in 3000ms...`
- `openclaw-2026-05-05.log:1634`（NarrativeWorker）
  - `Retrying in 6000ms...`
- `openclaw-2026-05-05.log:1639`（NarrativeWorker）
  - `Retrying in 12000ms...`

→ 60秒待ちが効いていない（少なくともこの経路では 3/6/12 秒）。

### 証拠3: 60秒待ちは「品質ゲート」専用で、transport/429 は別経路

`src/narrative-worker.ts` には 60秒定数があるが、使われる場所が限定されている。

- `src/narrative-worker.ts:60`
  - `const GATE_RETRY_DELAY_MS = 60_000; // 60秒`
- `src/narrative-worker.ts:766, 776, 786, 803, 821, 854, 876, 893, 984, 1196` など
  - 品質ゲート失敗時に `await this.sleep(GATE_RETRY_DELAY_MS)`

一方で、モデル呼び出しが例外（HTTP 429 等）で落ちた場合は別のバックオフが使われる。

- `src/narrative-worker.ts:57-58, 1038-1044`
  - `const RETRY_BASE_DELAY_MS = 3000;`
  - `const delayMs = Math.min(RETRY_BASE_DELAY_MS * Math.pow(2, attempt), MAX_RETRY_DELAY_MS);`
  - `... Retrying in ${delayMs}ms...` → `await this.sleep(delayMs)`

→ **「60秒」は品質ゲート用で、429など transport の再試行は 3秒起点の指数バックオフ**。

## 根本原因（整理）

1. v0.4.30a の `GATE_RETRY_DELAY_MS=60s` は「品質ゲート再生成」を対象にしている。
2. 429 / quota exceeded は品質ゲートに到達する前に例外として落ちるため、`RETRY_BASE_DELAY_MS=3000` の transport バックオフで回る。
3. Gemini のエラーメッセージには `Please retry in XXs` が含まれているが、現状の実装はそれを**遅延計算に反映していない**。
4. OpenRouter 側も `Retry-After` ヘッダが無い（or 0扱い）ケースでは `baseRetryDelayMs/maxRetryDelayMs`（デフォルト cap 30s）で回り続ける。

## 修正方針（実装プラン）

### A. NarrativeWorker: 通信エラー全体を固定スケジュール化（B方針）

ユーザー指定により、本件は **429だけでなく、5xx/timeout/network を含む通信系失敗を全て** 同じ待ち方に揃える（B）。

待ち時間テーブル（秒）：

```
60, 120, 240, 480, 960, 1280
```

ルール：

- attempt=0（1回目の失敗後の待ち）→ 60s
- attempt=1 → 120s
- attempt=2 → 240s
- attempt=3 → 480s
- attempt=4 → 960s
- attempt=5 → 1280s
- attempt>=5 → 1280s（上限固定）

このスケジュールは `src/narrative-worker.ts` の `narrativizeWithModel()` の `catch` に適用する。

根拠：現状はここで `RETRY_BASE_DELAY_MS=3000` を起点に指数バックオフ（3/6/12…秒）を計算しているため（`src/narrative-worker.ts:57-58, 1038-1044`）、ログ上の連打と一致する。

### B. （任意）429 の Retry-After / サーバー指示は「上乗せ」扱い

固定スケジュールにした上で、429 だけはサーバー側が明示する待機時間（Gemini の `Please retry in XXs`、OpenRouter の `Retry-After`）が取得できた場合、
`finalDelay = max(scheduleDelay, retryAfterMs)` として **長い方を採用**する。

実装詳細（擬似コード）：

```
const scheduleSec = [60, 120, 240, 480, 960, 1280];
const scheduleDelayMs = scheduleSec[Math.min(attempt, scheduleSec.length - 1)] * 1000;

let retryAfterMs = 0;
if (err is OpenRouterError) retryAfterMs = err.retryAfterSeconds * 1000;
if (err is GeminiDirectError) retryAfterMs = parsePleaseRetryInSeconds(err.message) * 1000;

const finalDelayMs = Math.min(Math.max(scheduleDelayMs, retryAfterMs), MAX_RETRY_DELAY_MS);
await sleep(finalDelayMs);
```

### C. OpenRouterClient 側の変更は原則不要

今回の主戦場は NarrativeWorker の `catch`（transport再試行）なので、OpenRouterClient 側の maxRetryDelayMs をいじらずに済む。

### D. ログの分かりやすさ（観測強化）

通信失敗のとき、以下を1行で出す：
- `errorClass`
- `scheduleDelayMs`
- `retryAfterMs`（取れたときだけ）
- `finalDelayMs`

例：
`[NarrativeWorker] gemma-main ... failed [gemini_http_429] ... retryAfter=32269ms floor=60000ms finalDelay=60000ms`

### E. non-retriable は即handoff（無駄な長期待ちを避ける）

固定スケジュール（B）を適用しても、**成功しない失敗**は待っても解決しない。

- OpenRouter: 401/403、provider policy/mismatch 400 など（`OpenRouterError.retriable=false`）
- Gemini: 既に `GeminiDirectError.retriable=false` は即handoff している

方針：

- `OpenRouterError` で `retriable=false` のときは **transport schedule を使わず即handoff**（return null → phase handoff）。

理由：

- 認証/設定ミスで 21分待ち→再試行 を繰り返すと、復旧が遅れ、ログも汚れ、障害切り分けが難しくなる。

## テスト計画

1) **Gemini 429 のメッセージ抽出（任意上乗せ）**
- `GeminiDirectError.message = "... Please retry in 32.2s.."` → `retryAfterMs=32200` が取れる
- 取れない場合は 0

2) **固定スケジュール**
- attempt=0..5 → 60/120/240/480/960/1280秒
- attempt>=6 → 1280秒固定

3) **Retry-After 上乗せ**
- `retryAfterMs > scheduleDelayMs` のとき final が retryAfter を採用

4) **非429でもスケジュール通り**（B方針）
- `gemini_http_5xx` / `gemini_timeout` / `gemini_network` / `http_5xx` などでも final がスケジュールになる

## リスクとトレードオフ

- 一時的なネットワーク瞬断でも待ちが長くなる（3秒→60秒）。
  - ただし「叩かれまくる」問題は確実に止まり、API/プロバイダ側の負荷も下がる。
- 復旧が遅くなる可能性。
  - ここは B方針（全通信失敗に強い待ち）を優先する。

## 実装順序

1. `src/narrative-worker.ts` に固定スケジュール定数/ヘルパーを追加
2. `catch` の遅延計算を固定スケジュールに差し替え（B）
3. （任意）Gemini/OpenRouter の retryAfter 抽出を追加し、finalDelay に上乗せ
4. 単体テスト追加（固定スケジュール + 上乗せ）
5. 既存テスト一式実行（少なくとも `npm test`）

## 実装済み変更記録

### F1: transport retry ロジックを独立モジュールに抽出 (`src/transport-retry.ts`)
- `TRANSPORT_RETRY_SCHEDULE_SEC = [60, 120, 240, 480, 960, 1280] as const`
- `MAX_TRANSPORT_RETRY_DELAY_MS = 1_280_000`
- `parseGeminiPleaseRetryInSeconds(message)` — `"Please retry in Xs"` メッセージをパース
- `computeTransportRetryDelayMs(attempt, err)` — スケジュール値 vs Retry-After の大きい方を返す
- `src/narrative-worker.ts` から import して利用、inline 定義は削除

### F2: OpenRouter non-retriable エラーを即 handoff (`src/narrative-worker.ts`)
- `narrativizeWithModel()` の `catch` に `err instanceof OpenRouterError && !err.retriable` ガードを追加
- 401/403/provider_400_policy などで無駄な 60-1280 秒待ちをしなくなった
- Gemini 側 (`narrativizeWithGemini()`) には v0.4.30a で既に同等ガードあり → 対称化

### F3: 単体テスト追加 (`test_transport_retry.ts`)
テストケース一覧：
1. `TRANSPORT_RETRY_SCHEDULE_SEC` の値が `[60,120,240,480,960,1280]` に一致
2. `MAX_TRANSPORT_RETRY_DELAY_MS` が 1280s に一致
3. `parseGeminiPleaseRetryInSeconds()` — ヒントなし/浮動小数点パース
4. `computeTransportRetryDelayMs()` — attempt 0/5/999 のスケジュールマッピング
5. OpenRouter `Retry-After` 上乗せ（schedule=60s, retryAfter=180s → final=180s）
6. Gemini メッセージヒント上乗せ（schedule=60s, hint=120.5s → final=120.5s）
7. **[B6修正]** non-retriable handoff ガードがソース上に存在することを検証（OpenRouter/GeminiDirect 両経路）
