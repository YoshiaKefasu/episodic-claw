## 0. 背景

v0.4.3 で idle flush timer（`scheduleIdleFlush` / `handleIdleFlush`）を実装済みだが、**2つの経路でバッファが未物語化のまま放置されるバグ**が見つかった。

1. **warm-start 後の processTurn early return で scheduleIdleFlush が呼ばれない**
2. **gateway_stop フックがバッファを flush せずにプロセス終了する**

これにより「最後の会話から15分経ってもフラッシュされない」症状が再発している。

- Go側 `SleepTimer Idle 19h~25h` が延々出力されるが、TS側の `Idle timeout` ログが一度も出ない

## 2. Core Problem（3つの独立した証拠に基づく）

### Bug A: processTurn early return で scheduleIdleFlush 未呼び出し

**該当箇所**: `segmenter.ts` L218-221

```typescript
const newMessages = currentMessages.slice(this.lastProcessedLength);
if (newMessages.length === 0) {
  console.log(`processTurn: no new messages (...)`);
  return false;  // ← scheduleIdleFlush に到達しない
}
```

**影響**:
- warm-start後の初回 `before_prompt_build` で `newMessages=0` → 即return
- `bootstrapCursor()` が `clearIdleFlushTimer()` を呼ぶ（L482）が、代替のスケジュールなし
- **結果**: idle flushタイマーがセットされず、以降の会話で新規メッセージが来るまで何もフラッシュされない

**確信度**: 95% — コード3箇所（L218-221, L115-126, L482）+ ログ1件で証明

**実害の前提条件**:
- 通常運用（再起動なし）では、ユーザー発言 → processTurn進行 → scheduleIdleFlush呼び出し → 15分後に発火、で正常動作する
- **問題が顕在化するのは再起動後**: warm-startでcursor復元 → newMessages=0 → タイマー未セット → 以降の会話開始までタイマー不在

### Bug B: gateway_stop がバッファを flush しない

**該当箇所**: `index.ts` L833-848

```typescript
api.on("gateway_stop", async (event?, _ctx?) => {
  await _singleton!.narrativeWorker.stop();  // worker停止
  await rpcClient.stop();                     // RPC停止
  // ❌ _singleton.agentStates の各segmenter.bufferをflushしていない
});
```

**影響**:
- SIGTERM等でGatewayが停止する時、各agentのsegmenterバッファ内の未物語化メッセージが消失
- `before_reset` はSIGTERMで発火保証なし（OpenClawのvoid発火）
- **結果**: 再起動後、cursorはDBから復元されるが、バッファ内容は復元不可 → 未物語化メッセージのロス

**確信度**: 90% — コード1箇所で明らかにflush漏れ。SIGTERM発火保証の欠如はOpenClaw側の仕様

### Bug C: bootstrapCursor が clearIdleFlushTimer するが再スケジュールしない

**該当箇所**: `segmenter.ts` L476-490

```typescript
bootstrapCursor(currentMessagesLength, reason, agentWs, agentId) {
  this.lastProcessedLength = next;
  this.buffer = [];               // ← バッファクリア
  this.clearIdleFlushTimer();     // ← タイマークリア
  // ❌ scheduleIdleFlush の再スケジュールなし
}
```

**影響**:
- warm-start直後、バッファ空 + タイマーなし の状態になる
- バッファが空なら `scheduleIdleFlush` を呼んでも `this.buffer.length === 0`（L116）で何もしない
- しかし**バッファ内容を復元する将来修正**（Fix B-2）を行う場合、ここの再スケジュールが必須になる

**確信度**: 85% — 現状はbuffer空なので実害低いが、Fix B-2と組み合わせないと不完全

## 5. 修正詳細

### 5.1 Fix A: processTurn early return に scheduleIdleFlush 追加

**ファイル**: `src/segmenter.ts` L218-221

**現状**:
```typescript
const newMessages = currentMessages.slice(this.lastProcessedLength);
if (newMessages.length === 0) {
  console.log(`[Episodic Memory] processTurn: no new messages (...)`);
  return false;
}
```

**修正後**:
```typescript
const newMessages = currentMessages.slice(this.lastProcessedLength);
if (newMessages.length === 0) {
  // [v0.4.22] Fix A: buffer非空かつtimer未セットならidle flushタイマーをセット
  // warm-start後等でnewMessages=0でもbufferに未処理分がある場合、
  // タイマーが未セットなら15分後にflushされないバグを防ぐ
  if (this.buffer.length > 0 && !this.idleFlushTimer) {
    this.scheduleIdleFlush(agentWs, agentId);
  }
  console.log(`[Episodic Memory] processTurn: no new messages (...)`);
  return false;
}
```

**リスク**: 極低。`scheduleIdleFlush` は `buffer.length === 0` で何もしない（L116）ので、buffer空時の挙動は変わらない。buffer非空 **かつ timer未セット時のみ** なので既存タイマーの不要な延長も起きない。

**注意**: `!this.idleFlushTimer` ガードを入れないと、`before_prompt_build` の多重呼び出しでタイマーが延長され続け、逆にflushが遅れる。必ずガード付きで実装する。

### 5.2 Fix B-1: gateway_stop でバッファ flush

**ファイル**: `src/index.ts` L833-848

**現状**:
```typescript
api.on("gateway_stop", async (event?, _ctx?) => {
  // narrative worker停止
  await _singleton!.narrativeWorker.stop();
  await rpcClient.stop();
  _singleton!.sidecarStarted = false;
});
```

**修正後**:
```typescript
api.on("gateway_stop", async (event?, _ctx?) => {
  console.log("[Episodic Memory] Stopping plugin...", event?.reason ? `(reason: ${event.reason})` : "");

  // [v0.4.22] Fix B-1: gateway停止時に全agentのバッファをflush
  // SIGTERM等でプロセスが終了する場合、segmenterバッファ内の
  // 未物語化メッセージが消失するのを防ぐ
  if (_singleton?.agentStates) {
    const flushPromises: Promise<void>[] = [];
    for (const [agentId, state] of _singleton.agentStates) {
      if (state.segmenter && state.lastAgentWs) {
        console.log(`[Episodic Memory] gateway_stop: flushing buffer for ${agentId}...`);
        flushPromises.push(
          state.segmenter.forceFlush(state.lastAgentWs, agentId)
            .catch(err => console.error(`[Episodic Memory] gateway_stop: flush error for ${agentId}:`, err))
        );
      }
    }
    await Promise.all(flushPromises);
    console.log("[Episodic Memory] gateway_stop: all buffers flushed.");
  }

  // Narrative architecture (v0.4.0) — graceful stop of narrative worker
  if (_singleton!.narrativeWorker) {
    console.log("[Episodic Memory] Stopping narrative worker...");
    await Promise.race([
      _singleton!.narrativeWorker.stop(),
      new Promise(resolve => setTimeout(resolve, 15000)),
    ]);
    console.log("[Episodic Memory] Narrative worker stopped.");
  }

  await rpcClient.stop();
  _singleton!.sidecarStarted = false;
});
```

**リスク**: 低。`forceFlush` は既存メソッドで、`buffer.length === 0` なら即returnする（L541）。各agentのflushを `Promise.all` + `.catch` で独立させているので、1つのagentでエラーが起きても他に影響しない。

**トレードオフ**: gateway_stopの完了が数秒延びる可能性（flush + enqueueのRPC往復）。しかし15秒のworker停止timeoutよりは短いはず。

### 5.3 Fix B-2: warm-start 後の cursor 差分から未処理分を buffer 再積み

**ファイル**: `src/segmenter.ts` + `src/index.ts`

**現状の問題**:
- `bootstrapCursor()` が `this.buffer = []` でバッファをクリアする
- cursor差分（`msgs.length - restoredCursor`）> 0 の場合、次回 `processTurn` が差分を「新規」として処理する
- しかし `cursor = current` の場合（全メッセージ処理済み）、差分=0 → processTurn即return → **バッファに積まれるものがない**

**修正方針**: `bootstrapCursor` でバッファをクリアするのではなく、**cursor差分メッセージをバッファに再積み**する。これにより：
1. 差分 > 0 → bufferに未処理分が積まれる → scheduleIdleFlushがセットされる → 15分後にflush
2. 差分 = 0 → buffer空 → scheduleIdleFlushは何もしない → 正常（flushすべきものなし）

**実装**:

`segmenter.ts` に新メソッド追加:
```typescript
/**
 * [v0.4.22] Warm-start後のcursor差分から未処理メッセージをbufferに再積みする。
 * bootstrapCursorの代わりに呼び出すことで、再起動前の未物語化メッセージを
 * 復元し、idle flushタイマーをセットする。
 *
 * @param currentMessages 現在のセッションメッセージ全て
 * @param agentWs workspaceパス
 * @param agentId agent識別子
 */
restoreBufferFromCursor(currentMessages: Message[], agentWs: string, agentId: string): void {
  const unprocessed = currentMessages.slice(this.lastProcessedLength);
  if (unprocessed.length > 0) {
    // 未処理メッセージをバッファに再積み（dedupなし — 再起動後はbuffer空なので重複なし）
    this.buffer.push(...unprocessed.filter(m => !EXCLUDED_ROLES.has(m.role)));
    this.scheduleIdleFlush(agentWs, agentId);
    console.log(JSON.stringify({
      source: "episodic-claw",
      event: "restore-buffer-from-cursor",
      cursor: this.lastProcessedLength,
      bufferLength: this.buffer.length,
      unprocessedCount: unprocessed.length,
    }));
  } else {
    // 差分なし = 全メッセージ処理済み → buffer空 → scheduleIdleFlush不要
    console.log(JSON.stringify({
      source: "episodic-claw",
      event: "restore-buffer-from-cursor",
      cursor: this.lastProcessedLength,
      bufferLength: 0,
      unprocessedCount: 0,
      reason: "all_processed",
    }));
  }
  // bootstrapCursor相当のクリーンアップ
  this.turnSeq = 0;
  // clearIdleFlushTimer は呼ばない — restoreBufferFromCursor が scheduleIdleFlush を呼ぶため
}
```

`index.ts` の warm-start パス（L941-960）で `bootstrapCursor` の代わりに `restoreBufferFromCursor` を呼ぶ:
```typescript
// 現状: bootstrapCursor(clamped, "warm-start", agentWs, agentId)
// 修正後:
if (restoredCursor > 0) {
  const clamped = Math.min(restoredCursor, msgs.length);
  // [v0.4.22] bootstrapCursorではなくrestoreBufferFromCursorで
  // cursor差分メッセージをバッファに再積み + idle flushタイマーセット
  state.segmenter.restoreBufferFromCursor(msgs, agentWs, agentId);
  // cursor位置を正確に設定（restoreBufferFromCursorはcursorを進めない）
  state.segmenter.bootstrapCursor(clamped, "warm-start", agentWs, agentId);
  // bootstrapCursorがbufferをクリアしてしまうので、順序を逆にする必要あり
  // → 実際は restoreBufferFromCursor の後に bootstrapCursor を呼ぶと
  //   bufferがクリアされてしまう。統合設計が必要。
}
```

**⚠️ 設計上の課題**: `bootstrapCursor` が `this.buffer = []` を呼ぶため、`restoreBufferFromCursor` の後に `bootstrapCursor` を呼ぶとバッファがクリアされてしまう。以下のいずれかで対応:

- **Option 1**: `bootstrapCursor` に `preserveBuffer` フラグを追加
- **Option 2**: `bootstrapCursor` の `this.buffer = []` を削除し、`restoreBufferFromCursor` で明示的にクリア
- **Option 3**: `restoreBufferFromCursor` 内でcursor設定も行い、`bootstrapCursor` を呼ばない

**推奨**: **Option 3** — `restoreBufferFromCursor` は `bootstrapCursor` の代替として設計し、内部でcursor設定 + buffer再積み + scheduleIdleFlushを一括で行う。`bootstrapCursor` は他の呼び出し元（after_compaction等）のために残す。

```typescript
restoreBufferFromCursor(currentMessages: Message[], agentWs: string, agentId: string): void {
  // cursor設定（bootstrapCursor相当）
  const next = Math.max(0, this.lastProcessedLength);
  const changed = this.lastProcessedLength !== next;
  // bufferはクリアせず、差分メッセージを再積みする
  this.turnSeq = 0;
  this.clearIdleFlushTimer();

  const unprocessed = currentMessages.slice(this.lastProcessedLength);
  if (unprocessed.length > 0) {
    this.buffer = unprocessed.filter(m => !EXCLUDED_ROLES.has(m.role));
    this.scheduleIdleFlush(agentWs, agentId);
  } else {
    this.buffer = [];
  }

  console.log(JSON.stringify({
    source: "episodic-claw",
    event: "restore-buffer-from-cursor",
    cursor: this.lastProcessedLength,
    bufferLength: this.buffer.length,
    unprocessedCount: unprocessed.length,
  }));

  if (changed) {
    this.persistCursor(agentWs, agentId);
  }
}
```

**リスク**: 中。バッファに再積みされたメッセージが重複処理される可能性。ただし：
- cursor差分 > 0 で再積み → processTurn が newMessages = 0 でearly return → **Fix AでscheduleIdleFlushが呼ばれる** → 15分後にidle flush → 物語化
- または、processTurn が newMessages > 0 を検出 → 既存のsurprise boundary判定が走る → 正常動作
- 重複の懸念: dedupWindow（デフォルト5）がbuffer内直近5件と照合 → 再起動後はbufferに再積みされたメッセージが既に入っている → processTurnのnewMessagesが「既存bufferと重複」→ dedupでスキップ → OK

## 7. Acceptance Criteria

### Fix A
1. `processTurn` の early return（newMessages=0）で buffer非空時に `scheduleIdleFlush` が呼ばれる
2. buffer空時の挙動は変更なし（scheduleIdleFlushが何もしない）
3. 既存の surprise boundary / size limit / forceFlush は壊れない
4. idle flushタイマーのリスケジュールが「最後のprocessTurn呼び出しから15分」に更新される

### Fix B-1
1. `gateway_stop` フックで全agentのsegmenter.forceFlushが呼ばれる
2. forceFlushのエラーが1agentで起きても他agentに影響しない
3. buffer空のagentではforceFlushが即returnする（不要なRPCなし）
4. gateway_stopの完了がworker停止timeout（15秒）を超えない

### Fix B-2
1. warm-start後のcursor差分 > 0 の場合、未処理メッセージがbufferに再積みされる
2. 再積み直後にscheduleIdleFlushがセットされる
3. cursor差分 = 0 の場合、buffer空のまま（既存挙動と同じ）
4. dedupWindowが再起動後の重複メッセージを正しく弾く

### Fix C
1. `before_prompt_build` ごとに `runId/sessionId/msgCount/lastRole` が1行で出力される
2. `retriever.ts` で「選定された末尾N件 user message」のフィンガープリントが出力される
   - 形式: `idx`, `len`, `hash8`, `isDominant`, `cleanedLen`
3. ログだけで「最新 user が window に入っていたか」「入っていたが attachment/noise で落ちたか」を判定できる
4. 検索ロジック自体（query生成・recall結果）を変更しない（観測追加のみ）

   - ただし「最新ユーザーメッセージ未採用」の体感は再現報告があるため、**観測不足**として Fix C を追加する。

### 11.2 プラン補強（この Addendum を優先）

- **Fix A はガード付きで実装**: `buffer非空 && idleFlushTimer未セット` のときだけ schedule。
- **Fix B-1 は必須**: gateway_stop 全agent flush。
- **Fix B-2 は設計見直し前提**:
  - `msgs.length - restoredCursor` だけでは、`cursor==msgs.length` かつ `buffer未flush` のケースを再構築できない。
  - 本件は「cursorは進んでいるがバッファは揮発」という設計ギャップで、差分再積みだけでは不十分。
- **Fix C（新規）を追加**: recall window に最新ユーザー発話が乗っているかをログで可視化。

### 11.3 Fix C（新規）仕様

**目的**: `recallQueryRecentMessageCount=2` で「最新が入らない」体感の真因を切り分ける。

**実装（低リスク・挙動不変）**
1. `retriever.ts` で query構築前に以下を debugログ出力
   - `currentMessages.length`
   - `userMessages.length`
   - 選定された末尾N件 user message のフィンガープリント
     - `idx`（window内順序）
     - `rawLen` / `cleanedLen`
     - `hash8`（SHA-1先頭8桁）
     - `isDominant`（attachment/noise判定）
   - 最後の message role（`currentMessages.at(-1)?.role`）
   - `latestUserIncludedInWindow` / `latestUserDroppedByClassifier` の真偽値
2. `index.ts` `before_prompt_build` で同一 runId/sessionId の msgCount を1行出力

**期待効果**
- 「イベント時点で最新 user が messages 配列に入っていない」のか
- 「入っているが attachment/noise 判定で query から落ちる」のか
- 「実際は入っているが体感上ズレている」のか
を判別可能にする。
