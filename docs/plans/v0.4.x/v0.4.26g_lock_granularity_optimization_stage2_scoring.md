`ComputeStage2BatchScores`（Pass 3）は機能面は安定しているが、
ロック保持時間が長い構造のため、運用規模が上がると Store 全体の待ち時間（渋滞）を招く可能性がある。

ロック粒度を段階的に最適化するための独立計画。

> Stage2 の「長時間一括ロック」は安全だが、処理量増加時に Store 全体の待ち時間を悪化させる潜在リスクを持つ。

## 3. Decision Lock（v0.4.26g の境界）

2. `CalculateScoreStage2` の式は変更しない

## 4. 方針オプション

### Option A（推奨）: 2-Phase Snapshot + Narrow Write Lock

**概要**
- Phase 1（Read phase）: 必要データをスナップショット取得（RLock/短時間）
- Phase 2（Compute phase）: ロック外で score計算
- Phase 3（Write phase）: 最小区間だけ Lock して batch write/commit

**狙い**
- 「重い計算」を排他区間から外し、待ち時間を削減。

**注意点**
- Read→Write の間にレコード更新が入る可能性（staleness）を許容するか、再検証条件が必要。

---

### Option B: 現状維持 + 観測強化のみ

**概要**
- ロック粒度は変えず、待ち時間メトリクスのみ追加。

**メリット**
- 回帰リスクが最小。

**デメリット**
- 渋滞そのものは解消しない。

---

### Option C: 粒度分割（topicIndex/DB 等のロック分離）

**概要**
- 1本の mutex を責務別に分離。

**評価**
- 効果は大きい可能性があるが、回帰リスクも高い。
- v0.4.26g の最小差分としては過大。

---

## 5. 推奨案

**Option A を段階導入（観測ゲート付き）**

導入順:
1. まず計測（lock wait / hold / scanned / rescored / commit duration）
2. 次に 2-Phase 化（最小対象から）
3. 問題なければ対象拡大

理由:
- KISS: 目的に直結する変更のみ
- YAGNI: 大規模ロック分割を先送り
- 回帰時の切り戻しが容易

### 既知制限（明記・受容済み）

1. **Stale 検出の gap**: `Add()`/`UpdateRecord()`/`RecordHit()` は Hits/Retrievals/Tags/Topics を変更するが LastScoredAt を変更しないため、それらのみの変更は stale として検出されない。score-only patch が現在のフィールド値を保持するため data loss は発生しないが、PruneState 決定が古い feature inputs に基づく可能性がある。Stage2 は periodic であり次回実行で再評価されるため受容可能。

2. **Stale 時の 30min cooldown**: stale=true でも LastScoredAt が `now` に設定されるため、PruneState が未再評価でも 30分間再 score されない。hot-loop re-scoring を防ぐため意図的。

> Perspective: Google / IBM Production Engineering  
> Principles applied: YAGNI · KISS · DRY · SOLID

### 📍 Current Reality (Source Code vs. Document)

- ✅ Document matches code: `ComputeStage2BatchScores` currently acquires `s.mutex.Lock()` for the entire function and performs scan + compute + batch write under the lock.
- ✅ Document matches code: `main.go` Pass 3 uses a 10-minute timeout and persists the returned Stage2 summary to StateDB after the call.
- ⚠️ **Discrepancy found: Evidence 3 is incorrect.** `RunGarbageCollector` uses `s.mutex.RLock()` during scan (store.go:1929), not `s.mutex.Lock()`. It is therefore **not an exclusive-lock contender** in the way the plan suggests.
- ⚠️ **Discrepancy found: Lock purpose under-explained.** The document implies the lock is primarily for Pebble DB protection, but Pebble has internal synchronization. The exclusive store lock's real purpose is **higher-level consistency — preventing lost updates** during Stage2's read-compute-write cycle. Without the lock, concurrent `Add()`/`BatchAdd()`/`UpdateRecord()` could modify the same episode between Stage2's read and write-back, causing Stage2 to clobber `Retrievals`, `Hits`, `Tags`, `Topics`, etc.
- ⚠️ **Discrepancy found: 2-phase revalidation strategy is insufficient.** The plan mentions checking `LastScoredAt`/`PruneState` for revalidation, but these fields are **not modified by `Add()`/`UpdateRecord()`**, so they cannot detect concurrent changes to `Hits`, `Retrievals`, `Tags`, etc. A proper 2-phase design requires version field, CAS, or merge-safe patch writes — all beyond "light optimization" scope.
- ✅ Document correctly identifies that `BatchAdd` also holds the lock during bulk operations.

### 🎯 Core Problem (1 sentence)
> The real problem is not simply long lock hold time, but **how to reduce wait time without introducing semantic lost-update bugs** — and no measured contention exists yet to justify the risk.

### 🔍 Principle Filter
| Check | Result | Note |
|-------|--------|------|
| YAGNI — Is 2-phase actually needed now? | ❌ No | No measured contention or timeout regression is shown yet. Fix 1 (measurement) is the only YAGNI-compliant step. |

| DRY — Any duplication to eliminate? | ✅ Yes | `BatchAdd` already has a fairness pattern (`Unlock`/`Lock` every 100 items). Reuse this idea before designing a new 2-phase architecture. |
| SOLID — Any violation causing real problems? | ✅ None requiring redesign | Full lock splitting / 2-phase abstraction is over-scoped for current evidence level. |

### 🛤️ Solution Options

#### Option A — Measure Only *(推奨)*
**Approach**: Add lock timing and Stage2 timing metrics only (`lockWaitMs`, `lockHoldMs`, commit duration, timeout/cancel rate), without changing behavior.  
**Implementation cost**: Low  
**Risk**: Low  
**Why recommended**: Preserves correctness, gives baseline data, and avoids speculative complexity.  
**Concrete steps**:
1. Measure time before/after `s.mutex.Lock()` to record lock wait.
2. Measure total lock hold duration and per-phase breakdown (iter/commit).
3. Persist metrics in Stage2 summary; compare against timeout/cancel trends.
4. Define promotion thresholds (e.g., `lockHoldMs p95 > 1000ms`, timeout rate worsening) before considering further optimization.

#### Option B — Lock-Yield Pattern *(Only if metrics justify it)*
**Approach**: Introduce short unlock/relock fairness windows at safe commit boundaries, inspired by `BatchAdd` (store.go:588-589).  
**Implementation cost**: Medium  
**Risk**: Medium  
**When to choose this instead**: If measured data shows meaningful reader starvation (Recall RLock wait) or long lock hold times.  
**Concrete steps**:
1. Yield only at commit boundaries when pending batch is empty (ensures no partial-write state). 
2. Ensure iterator resume semantics are safe after relock.
3. Validate no lost-update regression is introduced.
4. **Does not solve Add/BatchAdd lost-update** but dramatically reduces RLock starvation for Recall queries.

#### Option C — Full 2-Phase Snapshot + Narrow Write Lock
**Approach**: Separate read / compute / write phases as described in the plan.  
**Implementation cost**: High  
**Risk**: High  
**Why not recommended now**: Requires a real version/CAS/merge-safe strategy to prevent lost updates. The plan's proposed revalidation keys (`LastScoredAt`, `PruneState`) cannot detect concurrent updates to `Hits`, `Retrievals`, `Tags`, `Topics`. This is a correctness design gap, not just an implementation detail. Until a merge-safe write strategy exists, 2-phase is unsafe.

#### Option D — Status Quo
**Approach**: Keep current behavior unchanged.  
**Implementation cost**: None  
**Risk**: Low  
**Trade-off**: Safest behaviorally, but lacks observability — you can't improve what you don't measure.

### ✅ Pro Recommendation
> **Choose Option A now because** it is the only option that improves decision quality without weakening correctness.  
> If metrics later show real reader starvation or timeout regression, evaluate Option B next.  
> Do **not** implement full 2-phase (Option C) until a merge-safe or versioned write strategy exists — it is a separate correctness project, not a "light optimization."
