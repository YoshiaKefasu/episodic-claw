# v0.4.26c — SleepTimer Idle Log Cleanup after D1 Deprecation

> Date: 2026-04-22  
> Status: ✅ PASSOFF VERIFIED (Local, 2026-04-22) / 🔍 Production log confirmation pending

---

## 0. 背景

運用ログに以下が継続出力される。

```text
[SleepTimer] Idle 11h50m for /home/.../episodes (consolidation disabled in v0.4.1+)
```

ユーザー要求:
- D1 consolidation は Deprecated 済み
- このログノイズを解消したい
- 依存がないなら SleepTimer 側の整理も検討

---

## 1. 実読ベースの事実（Source Evidence）

### Evidence 1 — Option A は既にソースへ反映済み
- `go/main.go:2825-2829`
  - `checkSleepThreshold()` の idle 判定ブロックに `EmitLog("[SleepTimer] Idle ...")` は存在しない。
  - 代わりに「idle log removed」のコメントのみが残っている。

### Evidence 2 — ただし SleepTimer 機能自体は現役
- `go/main.go:2734-2750`
  - `startSleepTimer()` が存在し、2分 ticker で巡回する。
- `go/main.go:2795-2824`
  - `checkSleepThreshold()` が `meta:last_activity` を監視する。
- `go/main.go:3080`
  - `main()` で `startSleepTimer(apiKey)` を呼び出している。

### Evidence 3 — D1 consolidation 自体は無効化済み
- `go/main.go:2833-2839`
  - `handleConsolidate` は noop で「disabled」レスポンスのみ。
- `docs/plans/v0.4.x/v0.4.1_post_release_hardening.md:115-129, 131-143`
  - SleepTimer から consolidation 呼び出し削除済み、idleログのみ残す設計と明記。

### Evidence 4 — SleepTimer 参照の副作用
- `go/main.go:2796` で `GetRawMeta("meta:last_activity")` を読む
- `go/main.go:1717, 1970` で `last_activity` 更新が残っている（ingest/batchIngest）

### Evidence 5 — 運用ログとソースの不一致が起き得る
- ソースでは idle行が削除済みでも、旧ビルド/旧プロセスが稼働中だと旧ログが継続する。

**解釈**: 現状は「A実装済み」だが、機能本体が残るため運用面では揺れが残る。Bで完全停止して再発余地を消す。

---

## 2. 問題の本質（1文）

> Option A（idle行削除）は既に実装済みだが、SleepTimer自体が残っているため運用一貫性が崩れやすく、完全停止（Option B）へ転換して再発余地を断つ必要がある。

---

## 3. 方針オプション

### Option A（廃止）: Idleログのみ停止（最小差分）

**内容**
- `checkSleepThreshold()` の idle `EmitLog` 行だけ削除（または debug gate 化）
- `startSleepTimer()` は維持（将来の軽監視用途を温存）

**メリット**
- ノイズ即時解消
- 影響範囲最小

**デメリット**
- SleepTimer 自体は残る（不要コード感は残る）

---

### Option B（採用）: SleepTimer全体停止（中差分）

**内容**
- `main()` から `startSleepTimer(apiKey)` 呼び出しを削除
- `startSleepTimer()` / `checkSleepThreshold()` を削除

**メリット**
- ノイズ完全解消
- 死活性の低い定期処理を整理できる

**デメリット**
- `last_activity` 観測経路が将来使いたくなった際、再導入が必要

---

### Option C: 設定化（最大差分）

**内容**
- `sleepTimerEnabled`, `sleepTimerLogIntervalMinutes` を plugin config に追加

**メリット**
- 環境ごとに調整可能

**デメリット**
- いまの課題に対して過剰（YAGNI）

---

## 4. 方針確定（2026-04-22 追記）

### Decision Lock

- ユーザー意思により、**Option B（SleepTimer完全停止）を唯一の実装方針**とする。
- Option A はこのプラン上で **廃止**。以後このプランで選択しない。

### 責任明記

- 先行認識で「A未実装」と扱ったのは私の確認ミス。
- 現在のコード状態は **A 実装済み + SleepTimer本体は稼働中**。
  - `go/main.go:2825-2829` idle EmitLog は削除済み（A反映）
  - `go/main.go:2734, 2795, 3080` SleepTimer経路は残存（B未反映）

### 現在地（As-Is）

- A（idleログ削除）: ✅ 実装済み
- B（SleepTimer完全停止）: ❌ 未実装
- 目標: **Aの上からBへ完全転換**
