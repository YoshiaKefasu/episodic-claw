## 3. Gate番号体系の整理（前提作業）

### 問題: 2つのGate体系で番号衝突

コードには2つの独立したGate体系が存在し、番号が衝突していた：

```
checkNarrativeFormat() 内（フォーマット検査）:     ← 旧呼称 "Gate 1-6"
  Fmt-G1: マークダウン検出         (L280)
  Fmt-G2: CoT/Planning検出         (L293)
  Fmt-G3: アシスタント文検出       (L316)
  Fmt-G4: 絵文字/顔文字検出        (L348)
  Fmt-G5: 一行目ナラティブ開始 chk (L354)  ← プラン旧G5と衝突
  Fmt-G6: 段落構造チェック         (L365)  ← プラン旧G6と衝突

applyQualityGates() 内（品質検査）:               ← 旧呼称 "Quality gate 0-4"
  G0: 言語ガード                   (L666)  v0.4.28a追加
  G1: 圧縮率                       (L723)
  G2: エコー検出                   (L734)
  G3: フォーマット（↑のcheckNarrativeFormatを呼出し）(L744)
  G3b: テンプレート語句ボディスキャン              (L754)
  G4: アンカー網羅率               (L773)
  → ここに G5(文数床)・G6(内容床) を追加
```

### 解決: 接頭辞による区別

- `checkNarrativeFormat()` 内のコメント: 全6Gate を `// Gate 1` → `// Fmt-G1`、...、`// Gate 6` → `// Fmt-G6` に統一リネーム（衝突箇所だけでなく全Gateを接頭辞付きにして体系を一望可能にする）
- `applyQualityGates()` 内のコメント: 統一番号 G0〜G6 に整理（新規G5/G6を含む）
- **コードの動作は一切変更しない** — コメントのリネームのみ

## 4. 変更仕様（Fix B1〜B6 — Option A 適用版）

### Fix B1 — ~~Validator Chain 化~~ → DEFERRED（スキップ）

> **理由**: YAGNI + KISS。設計書 §16 (L256-270) は「既存の applyQualityGates に短文対策と corrective feedback を差し込む方が、新しいシステムを作るより良い」と明記。現状6Gate（+2追加で8Gate）の規模では逐次実行で十分可読。GuardValidator[] 型・実行器・テストの導入は過度設計。
>
> **再評価タイミング**: Gate数が10以上に増えた場合、または on_fail 戦略が複雑化した場合。
>
> **実装**: なし。`applyQualityGates()` の既存逐次構造に G5/G6 をそのまま差し込む。

### Fix B2 — G5: Minimum Sentence Gate（文数床）

`applyQualityGates()` の G4（アンカー網羅率）の直後に追加。

- CJK: `>=3` 文
- Latin: `>=4` 文
- reason: `narrative-content: too-few-sentences`
- 文数判定: `text.split(/[。！？!?.]+/).filter(s => s.trim().length > 0).length`（KISS — 句点・感嘆符で分割）
- 言語判定: 既存 `detectLanguage()` を使用。`unknown` 返却時は Latin 閾値を適用（安全側フォールバック）
- **設計決定**: `narrativeGuardMinSentences` は1変数のみ定義。runtime で `detectLanguage()` 結果に基づき CJK 閾値 / Latin 閾値に分岐。2変数（`minCjkSentences` / `minLatinSentences`）は YAGNI — 1変数 + 分岐で十分

### Fix B3 — G6: Minimum Content Floor（内容量床）

G5 の直後に追加。

- CJK: `>=120` chars（`text.replace(/\s+/g, "").length`）
- Latin: `>=80` words（`text.split(/\s+/).filter(w => w.length > 0).length`）
- reason: `narrative-content: too-short-content-floor`
- 言語判定: G5 と同じロジックを共有

### Fix B4 — ~~G7: Corrective Feedback Classifier~~ → v0.4.28c へ分離

> **理由**: corrective feedback は gate 失敗理由別に補正ヒントを生成し、**次試行 prompt 末尾へ付与**する。これは `resolveUserPrompt()`（prompt生成パイプライン）の変更が必要で、本フェーズのリスクを不必要に上げる。G5/G6のreject reasonは既存の再試行ループで自然に伝播するため、即座の補正ヒントがなくても再試行は機能する。
>
> **v0.4.28c での実装予定**:
> - gate失敗理由別に補正ヒントを生成
> - `resolveUserPrompt()` に feedback hint 注入経路を追加
> - 例: too-short-content-floor → 具体例/段落増加指示
> - 例: low-anchor-coverage → アンカー3件以上明示指示

### Fix B5 — `contentGateEnabled=false` 経路の回帰防止

G5/G6 は G3b/G4 と同じパターンで `contentGateEnabled` に従う：

- `contentGateEnabled=true` → reject（`pass: false` + `isContentGate: true`）
- `contentGateEnabled=false` → **softwarn のみ**（警告ログを出すが、保存は止めない）
- 目的: item-loss 回帰を防ぐ（v0.4.27b意図維持）

### Fix B6 — MiniGuard設定追加（3キー）

`src/types.ts` / `src/config.ts` に optional設定を追加:

- `narrativeGuardMinSentences` — 文数床閾値（number, default: CJK=3 / Latin=4 を言語判定で分岐）
- `narrativeGuardMinCjkChars` — CJK文字数床（number, default: 120）
- `narrativeGuardMinLatinWords` — Latin単語数床（number, default: 80）

> ~~`narrativeGuardEnableCorrectivePrompt`~~ — B4(G7)のv0.4.28c分離に伴い削除。3キーに縮小。

#### B6-1: 設定公開（schema）
- `openclaw.plugin.json` に上記3キーを追加し、型・範囲・説明を明示。
- 目的: 実装担当/運用担当が UI/設定ファイルから閾値調整できる状態にする。

#### B6-2: 正規化（config）
- `src/config.ts` で default/clamp を適用。
- 異常値は安全側デフォルトへフォールバック。
- `narrativeGuardMinSentences`: clamp to [1, 20], default 3
- `narrativeGuardMinCjkChars`: clamp to [10, 500], default 120
- `narrativeGuardMinLatinWords`: clamp to [5, 300], default 80

#### B6-3: 回帰テスト（config pipeline）
- `test_config_pipeline.ts` の `expectedKeys` / `extraKeys` / default consistency に3キーを追加。
- 目的: 「typesに追加したが loadConfigで取りこぼす」既知回帰を防止。

### 🛤️ Solution Options

#### Option A — 最小差分追加（G5/G6のみ、B1スキップ） *(採用)*
**Approach**: Validator Chain化（B1）をスキップ。`applyQualityGates()` の既存逐次構造に G5/G6 をそのまま差し込む。Gate番号は `applyQualityGates` 内で G0-G6 の連番に整理し、`checkNarrativeFormat` 内の Gate 5/6 は「Fmt-G5/Fmt-G6」と明記して区別。G7（B4 corrective feedback）は次フェーズへ分離。
**Implementation cost**: Low（1-2h）
**Risk**: Low
**Why chosen**:
1. 設計書 §16 自身が「差し込む方が良い」と推している
2. Validator Chain は YAGNI — 今は6Gate（+2で8）、Chain化の恩恵が出るのは10Gate以上から
3. G7（corrective feedback）は prompt 生成パイプラインの変更が必要で本フェーズのスコープに合わない
4. Gate番号衝突を先に解決しないと実装者が混乱する
**Concrete steps**:
1. Gate番号整理: `checkNarrativeFormat()` 内 全6Gate → 「Fmt-G1」〜「Fmt-G6」にリネーム（コメントのみ）
2. G5・G6 を `applyQualityGates()` の G4 の直後に追加（既存構造のまま）
3. B5（softwarn）を実装: `contentGateEnabled=false` 時は softwarn ログのみ
4. B6（config）を実装: 3キーを types.ts / config.ts / plugin.json / test_config_pipeline.ts に追加
5. G7（B4）は v0.4.28c へ分離 — prompt生成パイプラインの変更が必要なため

#### Option B — フル実装（B1〜B6全て）
**Approach**: プラン通り GuardValidator[] Chain化 + G5/G6/G7 を実装。設計書 §14/§17 の完全実装。
**Implementation cost**: Medium-High（4-6h）
**Risk**: Medium — Chain化による回帰、G7 prompt注入の統合テスト不足
**When to choose this instead**: Gate数が10以上に増える見込みがあり、Chain化の保守性恩恵が確実な場合。または v0.4.28c を待てず G7 も今すぐ必要な場合。

### 実装後バグ修正

#### 🔴 BUG#1: `detectLanguage='unknown'` 時の G6 CJK回帰

**発見**: 検証フェーズで発見。`detectLanguage()` が `'unknown'` を返した場合（eld未ロード、短テキスト、判定失敗）、`isCjk=false` となり G6 が Latin 語数パスを実行。CJK叙事テキストに対して `text.split(/\s+/).length` は1〜5程度しか返さず、`minLatinWords=80` に対して**必ずreject**される回帰。

**影響**:
- `contentGateEnabled=true`（Gemini fallback有り）→ primaryフェーズの試行が全てG6で無駄に消費
- `eld`未ロード時や短テキストで言語判定が不安定な時に発火

**修正**:
- `CJK_CHAR_PATTERN` 正規表現と `hasCjkChars()` 関数を追加 — Unicode script ranges (Hiragana, Katakana, Han, Hangul) で先頭200文字をチェック
- `isCjk` 計算を変更: `CJK_LANG_CODES.has(detectedLang) || (detectedLang === "unknown" && hasCjkChars(text))`
- reason文字列に `CJK (heuristic)` ラベルを追加 — オペレーターがログで heuristic fallback を識別可能

**検証**: `tsc --noEmit` ✅ / `npm test` 39 passed ✅ / `test_config_pipeline.ts` 52 passed ✅

#### 🟡 BUG#2: config値 NaN/Infinity で gate が無声無効化

**発見**: 深掘り検証フェーズで発見。`loadConfig()` の `??` 演算子は `null/undefined` のみキャッチし、`NaN` をスルーする。`Math.max(1, NaN) = NaN` → `sentenceCount < NaN = false` → G5/G6 が常に通過してしまう（gate無効化）。

**影響**: JSON.parseはNaNを生成しないため実運用での発火は極めて稀だが、防御的プログラミングとして対処必須。

**修正**:
- `clampFiniteInt(value, min, max, fallback)` ヘルパーを `clampUnitInterval()` と同じパターンで抽出
- 3キーをインライン三項演算子から `clampFiniteInt()` 呼出しに変更
- NaN/Infinity テスト5件追加（3キーNaN + Infinity + -Infinity）

**検証**: `tsc --noEmit` ✅ / `npm test` 39 passed ✅ / `test_config_pipeline.ts` 57 passed ✅
