# v0.4.31 — BUG-1 Episodic-Claw 単独根本解決プラン

> **作成日**: 2026-05-22  
> **ステータス**: Implemented / 未リリース / 2026-05-22 scope revised
> **前段プラン**: `v0.4.30g_bug1_guard_root_cause.md`  
> **目的**: OpenClaw / DennouAibou 側を触らず、Episodic-Claw 側だけで BUG-1 の実害を根から止める。

---

## A. 結論

v0.4.30g で `DEBUG_EPISODIC_PLUGIN_LIFECYCLE=2` を入れた結果、BUG-1 の正体はほぼ見えた。

**根本原因は Episodic-Claw ではなく、OpenClaw 側の複数サブシステムが同一プロセス内で `loadOpenClawPlugins()` を別々に呼び、同じ外部プラグインの `register()` を繰り返していること。**

Episodic-Claw の `global` singleton guard は、壊れないための保険として正しい。  
ただし、それは「二重呼び出しを受け止める壁」であって、「二重呼び出しを止める蛇口」ではない。

v0.4.31 の本命修正は、Episodic-Claw 側で以下を実現すること。

1. **web-fetch / secrets snapshot 経路では Episodic-Claw を即 no-op return する**
2. **`register()` 自体を軽い宣言関数に寄せ、重い runtime 作成を実イベントまで遅延する**
3. **同一 process の runtime state は global singleton で1つだけ維持する**
4. **OpenClaw 側の多重 `register()` は残っても、Episodic-Claw の sidecar / watcher / worker / config load は重複させない**

> 実装メモ: まず web-fetch snapshot no-op と duplicate api guard を入れて、register 再入の実害を止めた。lazy runtime 化は次段階の最適化候補として残している。

> Scope rule: この v0.4.31 では DennouAibou / OpenClaw core repository を変更しない。  
> OpenClaw 側の registry root fix は理想案として残すが、実装対象から外す。

それでも web-fetch provider 解決時に `register()` されているため、resolver 側が「候補なしなら全 plugin を full scan する」経路へ落ちている可能性が高い。

## C. 根本原因の分解

### C1. 直接原因

`resolvePluginWebFetchProviders()` が「web-fetch provider 一覧の取得」のために `loadOpenClawPlugins()` を呼ぶ。  
その時点で Episodic-Claw は web-fetch provider ではなく memory plugin なのに、full registry load に巻き込まれて `register()` される。

### C2. 構造原因

OpenClaw には複数の registry 入口がある。

| 入口 | 目的 | 今の副作用 |
|---|---|---|
| `resolvePluginWebFetchProviders()` | web-fetch provider 解決 | memory plugin まで snapshot load される |
| `ensureMemoryRuntime()` | memory backend 解決 | registry 互換が合わないと再 load |
| `ensureRuntimePluginsLoaded()` | embedded runtime plugin 初期化 | runtimeOptions 差で再 load 可能 |

それぞれの入口が「自分の用事だけ」を見て plugin registry を要求している。  
結果、同じプラグインが同じプロセスで複数回 `register()` される。

### C3. v0.4.30g の位置づけ

v0.4.30g はログ flood と診断不足を解決した。  
しかし根本原因は OpenClaw loader 側なので、v0.4.30g は **安全ガード + 診断フェーズ** として扱う。

## D. v0.4.31 修正方針（改訂版 — Episodic-Claw only）

### D1. できること / できないことを分ける

Episodic-Claw だけでは、OpenClaw が `register()` を何回呼ぶかは止められない。  
これはホスト側の plugin loader の交通整理だから。

ただし、Episodic-Claw 側で以下は止められる。

| 現象 | Episodic-Claw 単独で止められるか | 方針 |
|---|---:|---|
| web-fetch snapshot 経路で heavy runtime を作る | Yes | stack origin を見て no-op return |
| `register()` たびに config / client / worker を作る | Yes | lazy runtime 化 |
| 同じ process 内で sidecar / watcher / narrative worker が増える | Yes | global singleton 維持 |
| OpenClaw が `register()` を複数回呼ぶこと自体 | No | 診断ログに残すだけ。OpenClaw 側修正が必要 |

つまり v0.4.31 のゴールは、**呼ばれても壊れない** から一段進めて、**関係ない経路ではそもそも起動しない** に変えること。

### D2. web-fetch / secrets snapshot 経路は no-op return

KASOU ログでは、最初の create/reuse が次の stack で発生している。

```text
loadOpenClawPlugins
→ resolvePluginWebFetchProviders
→ resolveRuntimeWebTools
→ prepareSecretsRuntimeSnapshot
```

Episodic-Claw は `openclaw.plugin.json` で `kind: "memory"`。  
`registerWebFetchProvider()` も `registerWebSearchProvider()` も使っていない。  
だからこの経路で Episodic-Claw が runtime 初期化される理由はない。

実装案:

```typescript
type RegistrationOrigin =
  | "web-fetch-snapshot"
  | "memory-runtime"
  | "embedded-runtime"
  | "unknown";

function classifyRegistrationOrigin(stack?: string): RegistrationOrigin {
  if (stack?.includes("resolvePluginWebFetchProviders") || stack?.includes("resolveRuntimeWebTools")) {
    return "web-fetch-snapshot";
  }
  if (stack?.includes("ensureMemoryRuntime")) return "memory-runtime";
  if (stack?.includes("ensureRuntimePluginsLoaded")) return "embedded-runtime";
  return "unknown";
}
```

`web-fetch-snapshot` の場合:

- `runtime-mode` / `Registering plugin...` を出さない
- singleton を作らない
- hook / context engine / tools を登録しない
- `DEBUG_EPISODIC_PLUGIN_LIFECYCLE=2` の時だけ `skip origin=web-fetch-snapshot` を出す

これで、現ログの `call #1 (create)` / `call #2 (reuse)` が web-fetch 経路から発生する状態を止める。

`memory-runtime` と `embedded-runtime` は v0.4.31 では診断分類だけに使う。  
この2つは早期 return の対象にしない。理由は、memory runtime / embedded runtime 側が active registry に hook / tool / context engine 登録を必要としている可能性があり、Episodic-Claw 側だけで安全に捨てられると断言できないため。

### D3. `register()` を cold path にする

現在の `src/index.ts` は `register()` の中で以下をすぐ作る。

- `loadConfig()`
- `EpisodicCoreClient`
- `EpisodicRetriever`
- `OpenRouterClient`
- `NarrativeWorker`
- `initLanguageDetector()` warm-up
- per-agent state factory

これは `register()` が1回だけ呼ばれる世界なら自然。  
でも今回のログでは、OpenClaw が複数 subsystem から同じ plugin を読む。

v0.4.31 では、`register()` は薄い callback 登録だけに寄せる。

実装案:

```typescript
function getOrCreateRuntime(api: OpenClawPluginApi, reason: string): EpisodicRuntimeState {
  const existing = globalThis[EPISODIC_RUNTIME_KEY];
  if (existing) return existing;

  // ここで初めて loadConfig / client / worker / warm-up を行う
}
```

実際に runtime を作ってよいタイミング:

- `gateway_start`
- `before_prompt_build`
- `before_compaction`
- `after_compaction`
- context engine `ingest()` / `assemble()`
- `ep-recall` / `ep-save` / `ep-expand` / `ep-anchor` 実行時

この形なら、OpenClaw が discovery / snapshot 用に `register()` を呼んでも、Episodic-Claw の重い中身はまだ起きない。

影響を受ける主な closure 変数:

| 現在の参照 | 移行後 |
|---|---|
| `cfg` | `const { cfg } = getOrCreateRuntime(api, reason)` |
| `rpcClient` | runtime state から取得 |
| `retriever` | runtime state から取得 |
| `openRouterClient` | runtime state から取得 |
| `narrativeWorker` | runtime state から取得 |
| `openClawGlobalConfig` | runtime state の `openClawGlobalConfig` として保持 |
| `recallCalibration` | runtime state で cfg から一度作る |
| `recallReInjectionCooldownTurns` | runtime state で cfg から一度作る |
| `getAgentState()` | runtime state を引数に取る helper へ寄せる |
| `ensureSegmenterCursorInitialized()` / `ensureWatcher()` / `prepareWorkspaces()` | runtime state を使う helper へ寄せる |

handler 側の共通パターン:

```typescript
const runtime = getOrCreateRuntime(api, "before_prompt_build");
const { cfg, rpcClient, retriever, openClawGlobalConfig } = runtime;
```

この表にないローカル helper も、`_singleton!` 直接参照を減らし、runtime state 経由へ寄せる。

### D4. 同一 API object への二重登録だけ WeakSet で止める（MVPでは任意）

OpenClaw が別 registry object を作る場合、Episodic-Claw 側だけで安全に統合するのは危険。  
ただし、同じ `api` object に対する二重登録は明確に不要。

実装案:

```typescript
const REGISTERED_API_SET_KEY = Symbol.for("__episodic_claw_registered_api_set__");
const registeredApis = (globalThis[REGISTERED_API_SET_KEY] ??= new WeakSet<OpenClawPluginApi>());

if (registeredApis.has(api)) return;
registeredApis.add(api);
```

これは `api` object 単位の安全な重複排除に限定する。  
別 registry まで勝手にまとめると、OpenClaw の active registry に hook が入らないリスクがあるためやらない。

ただし、これは D2 / D3 より優先度が低い。  
v0.4.31 MVP では、まず `web-fetch-snapshot` no-op と lazy runtime 化を優先し、WeakSet は同一 API object の重複がテストで確認できた場合だけ入れる。

### D5. singleton guard は削除しない

v0.4.31 でも global singleton guard は残す。

理由:

- 古い OpenClaw / third-party host では多重 register が残る
- hot reload / test / dev server でも同種の再入が起き得る
- `getOrCreateRuntime()` の最終防衛線になる

ただし役割は変わる。

| v0.4.30g | v0.4.31 |
|---|---|
| register 時に singleton を作り、reuse を受け止める | 実イベント時に singleton を作り、snapshot 経路では作らない |

## E. 実装ステップ案（Episodic-Claw のみ）

対象ファイル:

- `src/index.ts`
- `test_phase4_5_cache_compaction_segmenter.ts` など、既存の dist-copy 型テストで必要なら補助
- `docs/plans/v0.4.x/v0.4.31_bug1_episodic_claw_root_fix.md`
- `CHANGELOG.md` は実装後に追記

### Step 1 — origin classifier を追加 (done)

`src/index.ts` に `classifyRegistrationOrigin()` を追加する。

分類:

- `web-fetch-snapshot`
- `memory-runtime`
- `embedded-runtime`
- `unknown`

`DEBUG_EPISODIC_PLUGIN_LIFECYCLE=2` のログには、既存の call count / stack / api identity に加えて以下を出す。

```text
[BUG-1 DIAG] origin=web-fetch-snapshot registrationMode=full
```

テストしやすくするため、classifier は純粋関数にする。  
`register()` では `new Error().stack` をそのまま直書き判定せず、取得した stack 文字列を `classifyRegistrationOrigin(stack)` に渡す。必要なら `__testing` export で classifier を直接検証する。

### Step 2 — web-fetch snapshot no-op (done)

`register()` の CLI 判定直後、かつ `Registering plugin...` ログより前で判定する。

```typescript
if (origin === "web-fetch-snapshot") {
  if (lifecycleDebugLevel === "2") {
    console.log("[BUG-1 DIAG] skipped web-fetch snapshot registration");
  }
  return;
}
```

ここで返すことで、web-fetch snapshot 経路では runtime-mode ログも singleton ログも出さない。

### Step 3 — runtime creation を lazy 化 (deferred)

現状の `if (!_singleton) { ... create ... }` ブロックを `getOrCreateRuntime(api, reason)` に切り出す。

注意点:

- `openClawGlobalConfig` は runtime 作成時点で読む
- `cfg` / `rpcClient` / `retriever` / `narrativeWorker` は runtime state に入れる
- `getAgentState()` など register 内 callback が使う helper は、callback 実行時に `getOrCreateRuntime()` から state を取る
- language detector warm-up は runtime create 時に一度だけ fire-and-forget

### Step 4 — same-api WeakSet guard (done)

同じ `api` object への二重 callback 登録だけ止める。

別 `api` object まで一括で止めない。  
そこまでやると active registry に必要な hook が入らない危険がある。

### Step 5 — テスト

最小テスト:

1. classifier unit test
   - web-fetch stack → `web-fetch-snapshot`
   - memory stack → `memory-runtime`
   - embedded stack → `embedded-runtime`
   - unknown stack → `unknown`

2. register no-op test
   - web-fetch stack を注入できる形にして `register()` を呼ぶ
   - `api.on` / `api.registerContextEngine` / `api.registerTool` が呼ばれない
   - runtime singleton が作られない
   - `DEBUG_EPISODIC_PLUGIN_LIFECYCLE=2` で skip ログが出る

3. lazy runtime test
   - non-web-fetch register 直後は heavy runtime 未作成
   - `gateway_start` handler 実行時に初めて runtime が作られる
   - unknown origin は v0.4.30g 相当の安全 fallback になり、web-fetch skip しない

4. 既存 suite
   - `npm test`
   - `npm run build`
   - Go 側に影響が無いことのため `go test ./...`

## H. Plain 解説

今回の方針は、OpenClaw の道路工事ではなく、Episodic-Claw の玄関を賢くする修正。

今までは、宅配業者が間違って何度もチャイムを押すたびに、Episodic-Claw が玄関まで出て、家の中の機械も少し起こしていた。  
v0.4.30g では「もう起きてるから二度寝しないよ」と守った。  
v0.4.31 ではさらに進めて、「これはうち宛ての荷物じゃない」と分かったチャイムには玄関を開けない。

具体的には、web-fetch 用の点検で呼ばれた時は即帰る。  
本当に memory が必要になった時だけ、Episodic-Claw の本体を起こす。
