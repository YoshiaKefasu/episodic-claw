# v0.4.28e — Untrusted Metadata が Recall Query に混入する経路の遮断

> Date: 2026-04-25  
> Status: ✅ PASSOFF VERIFIED (Local Re-Verification — 2026-04-25)  
> Release Target: v0.4.29  
> Goal: `Conversation info (untrusted metadata)` 系テキストが `latestUserAnchor` 経由で query に混入する経路を止める。


---

## 0. 目的

今回の不具合は「画像添付由来ノイズ」ではなく、**before_prompt_build の anchor 正規化経路**で `untrusted metadata` を拾ってしまうことが根本。

v0.4.28e では以下を最小差分で行う。

1. anchor 正規化時に untrusted metadata ブロックを確実に除去
2. `raw_prompt_fallback` のときに「生 prompt 全体」を anchor 採用しない
3. query 生成側でも metadata トークンを最終防衛で除去

## 2. コア問題（1文）

> `raw_prompt_fallback` 経路で metadata 混在 prompt を anchor として採用し、その anchor を latest user として window 注入するため、`untrusted metadata` 語が query キーワード枠を汚染する。

---

## 3. 方針オプション

### Option A — Anchor sanitize + fallback hardening + query最終防衛（推奨）

**Approach**: 既存の metadata strip 発想を anchor 経路へ再利用し、さらに query 側にも防衛線を追加する。  
**Cost**: Medium  
**Risk**: Low-Medium

**採用理由**:
- YAGNI/KISS: 大規模設計変更なしで原因経路を直接塞げる
- DRY: `large-payload.ts` の metadata strip ルールを共通化できる
- 再発防止: anchor 側と query 側の二重ガードにできる

### Option B — `raw_prompt_fallback` を全面停止（非推奨）

**Approach**: role block が取れない時は anchor を常に空にする。  
**Cost**: Low  
**Risk**: Medium-High

**非推奨理由**:
- 最新 user の取りこぼしを再発させる（v0.4.25系の目的と衝突）
- 短期的に汚染は止まるが recall 品質が落ちる

---

## 4. 変更仕様（Fix E1〜E6）

### Fix E1 — metadata strip を共通ヘルパー化

- 新規: 例 `src/untrusted-metadata.ts`
  - `stripUntrustedMetadataBlocks(text: string): string`
  - 対象: `Conversation info / Sender / Replied message` + fenced json
- `src/large-payload.ts` はこの共通ヘルパーを利用
- `src/retriever.ts:149-152`（`classifyAndStripAttachment()` 内部）に既存する inline の同一パターンも共通ヘルパー呼び出しに置き換える
  - そのまま放置すると Fix E4 追加時に3箇所目の同一パターンが生まれる（DRY 練）


### Fix E2 — `normalizePromptAnchor()` で sanitize を必須化

- `src/index.ts`
  - `candidate` 決定後に `stripUntrustedMetadataBlocks(candidate)` を適用
  - metadata 見出し行単体（json除去後の残骸）も除去
  - `anchorAcceptedReason` を細分化（例: `last_user_block_sanitized`, `raw_prompt_tail_sanitized`）

### Fix E3 — `raw_prompt_fallback` を tail 優先抽出へ変更

- `src/index.ts`
  - role block 不在時は「raw全文」採用をやめる
  - sanitize 後の末尾有意味テキスト（例: 最終非空行群）を anchor 候補にする
  - 有意味テキストが無ければ reject（`anchorRejectedReason=metadata_only_after_sanitize`）

### Fix E4 — query 側の最終防衛を追加

- `src/retriever.ts`
  - `instantDeterministicRewrite()` の Phase 1（`cleanedPerMessage` 生成）で
    - `Conversation info / Sender / Replied message` 見出し行除去
    - `untrusted metadata` 定型語の除去
  - **実装上の注意**: Phase 1 に既存する `System:` 行除去パターン（`/^System:\s*\[.*?\]\s*/gm`）の隔に 1 行追加するだけで済む。独立な「防衛レイヤー」新設は不要。
  - 目的: anchor 側で取り漏れた場合でも query 汚染を止める


### Fix E5 — observability 強化（再発判定可能化）

- `src/index.ts` ログ (`before-prompt-build-arrival`)
  - `anchorSanitizedLength`
  - `anchorSanitizeApplied` (bool)
  - `anchorSanitizeDroppedMetadata` (bool)
- `src/retriever.ts` fingerprint
  - `metadataResidueDetected`（window各要素の簡易判定）

### Fix E6 — 回帰テスト追加

- `test_phase4_5.ts`
  1. metadata + user本文の prompt から anchor が user本文のみになる
  2. `raw_prompt_fallback` でも query に `Conversation/info/untrusted/metadata` が入らない
  3. `windowAnchorInjected=true` でも `windowLatestPreview` が実本文になる
- `test_classify_attachment.ts`（必要なら拡張）
  4. metadata-only テキストは空化される（誤ってキーワード化しない）

## 11. 死角監査レポート（Post-Implementation Blind Spot Audit — 2026-04-25）

### 監査手順

実装完了後に以下の5項目を系統的に検証した。

1. E4 Phase 1 — fenced json ブロックの残存有無
2. `anchorSanitizeApplied` 意味論
3. `missing_or_non_string_prompt` 早期リターンの型整合
4. `classifyAndStripAttachment()` 中途 `.trim()` の副作用
5. `stripUntrustedMetadataBlocks()` エッジケース（空文字列・冪等性）

### 発見された死角

#### BS-1 (Critical) — E4 Phase 1: fenced json ブロックが残存

- **症状**: Phase 1 はヘッダー行（`Conversation info ... :` など）は除去するが、その後の ` ```json ... ``` ` ブロックは除去していなかった。結果として json の中身（`chatId`, `platform`, `ContaminationRisk` など）が query キーワードに混入し続ける。
- **再現**: `instantDeterministicRewrite()` の `cleanedPerMessage` マップに ````json{"chatId":"abc"}```\n合格ライン` を通すと、`chatId`, `abc` が keyword 候補に残る。
- **修正**: `src/retriever.ts` Phase 1 の `.replace()` チェーンに ` `.replace(/```json[\s\S]*?```/g, "")` を追加（E4a）。
- **テスト**: `test_untrusted_metadata.ts` Case 7 + Case 12 が BS-1 の回帰テストとして機能する。

#### BS-2 (Minor) — `anchorSanitizeApplied` の意味論が冗長

- **症状**: `const anchorSanitizeApplied = anchorSanitizeDroppedMetadata;` — sanitize は常に呼ばれているのに、metadata が drop されなかった場合は `anchorSanitizeApplied = false` を返していた。E5 の観測性フィールドとして誤解を招く。
- **修正**: `const anchorSanitizeApplied = true;` に変更（コメントで意図を明示）。`anchorSanitizeDroppedMetadata` が「実際に変化があったか」を示す別フィールドとして機能する。

### 監査結果サマリー

| 項目 | 結果 | 対応 |
|---|---|---|
| BS-1 (E4 fenced json 残存) | ❌ Critical | `retriever.ts` Phase 1 に E4a として即修正 |
| BS-2 (`anchorSanitizeApplied` 意味論) | ⚠️ Minor | `index.ts` で `true` に修正 |
| BS-3 (json regex case-sensitive) | ❌ Critical | `untrusted-metadata.ts` + `retriever.ts` E4a に `i` フラグ追加 |
| missing_or_non_string 早期リターン型整合 | ✅ 問題なし | E5 フィールドは `false/0/false` でハードコード正当 |
| `classifyAndStripAttachment` `.trim()` 副作用 | ✅ 問題なし | 後続コードが再 normalize するため安全 |
| `stripUntrustedMetadataBlocks` エッジケース | ✅ 問題なし | 空文字列・冪等性・複数ブロックすべて正常 |
