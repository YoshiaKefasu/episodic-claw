# v0.4.33 — Go 日本語 Query Parser / Yomitan風文節Parser

> **作成日**: 2026-05-24  
> **ステータス**: Proposed / Unimplemented  
> **目的**: Episodic-Claw の recall query 生成前段に、Go製の日本語文節Parserを追加し、Yomitan `/search.html` に近い自然な切り分けで日本語 recall 精度を上げる。  
> **スコープ**: Episodic-Claw のみ。DennouAibou / OpenClaw core は変更しない。  
> **性能方針**: Go parser cold 最大 150ms 狙い。150ms を超えたら即座に現行 TS parser へ fallback する。

---

## A. 結論

今の Episodic-Claw の日本語 query parser は、温まった後は十分速い。実測では、5ユーザーメッセージ相当の query 生成が warm p99 約 0.47ms だった。  
ただし切り分けは素朴で、Yomitan `/search.html` のような「意味の塊ごとの分割」ではない。

今回やるべきことは、速度改善そのものではなく、**日本語の recall query 精度改善**。  
そのために、Go sidecar に小さな `query.parseJapanese` RPC を追加し、Yomitan風の `text / reading / lemma / kind` segment を返す。

ただし、エージェント返信前の処理なので待たせてはいけない。  
Go parser は **150ms hard timeout** を持つ「賢い近道」として扱い、失敗・timeout・低品質結果なら今の TS parser に戻す。

## B. 調査で読んだ証拠

### B1. 現行 query 生成の差し替え地点

`src/retriever.ts:298-388`:

```ts
export async function instantDeterministicRewrite(messages: Message[], config?: EpisodicPluginConfig): Promise<string> {
  ...
  const keywords = await extractPolyglotKeywords(cleanedText, config);
  ...
  return result.length > 0 ? result.join(" ") : fallbackText;
}
```

意味: recall query は `instantDeterministicRewrite()` で作られている。  
Go parser を入れるなら、ここを壊すのではなく、この関数の前段または中で「Go parser → 成功なら採用 / 失敗なら既存処理」という形にするのが安全。

### B2. 現行日本語 parser は速いが、surface 抽出だけ

`src/cjk-tokenizer.ts:23-35`:

```ts
const JA_CONTENT_POS = new Set(["名詞", "動詞", "形容詞", "副詞"]);

async function tokenizeJapanese(text: string): Promise<string[]> {
  const tokens = await tokenize(text);
  return tokens
    .filter((t) => JA_CONTENT_POS.has(t.pos))
    .map((t) => t.surface_form);
}
```

意味: 今の処理は `kuromojin` の品詞で surface を抜く。  
`reading`、`lemma`、助詞を含めた文節表示、Yomitanのような辞書一致ベースの最長寄り切り分けは扱っていない。

### B3. TS → Go RPC は既にある

`src/rpc-client.ts:506-543`:

```ts
private async request<T>(method: string, params: any = {}, timeoutMs = 120000): Promise<T> {
  ...
  const reqStr = JSON.stringify({ jsonrpc: "2.0", method, params, id }) + "\n";
  this.socket!.write(reqStr);
}
```

意味: 既存の JSON-RPC 経路に `query.parseJapanese` を足せる。  
`request(..., timeoutMs)` が既にあるので、TS側から 150ms timeout を強制しやすい。

### B4. Go sidecar 側も RPC method switch 方式

`go/main.go:3006-3060`:

```go

case "ai.recall":
    go handleRecall(conn, req)

case "cache.retry":
    go handleCacheRetry(conn, req)

```

意味: Go側は handler を追加する構造。  
`case "query.parseJapanese": go handleQueryParseJapanese(conn, req)` を足すのが自然。

### B5. Yomitan の `/search.html` parser は segment を返す

`A:\yomitan\types\ext\api.d.ts:54-75`:

```ts
export type ParseTextSegment = {
    text: string;
    reading: string;
    lemma?: string;
    lemmaReading?: string;
    headwords?: ...;

```

意味: 欲しい形は `text` だけではない。  
`reading` と `lemma` を持つ segment 形式に寄せると、後から query 生成の精度を上げやすい。

### B6. Yomitan の scanning parser は左から辞書一致で進む

`A:\yomitan\ext\js\background\backend.js:1707-1776`:

```js
while (i < ii) {
  const substring = text.substring(i, i + scanLength);
  const {dictionaryEntries, originalTextLength} = await this._translator.findTerms(...);
  ...
  if (textSegments.length > 0) {
    results.push(textSegments);
    i += originalTextLength;
  } else {
    previousUngroupedSegment = {text: character, reading: ''};

```

意味: Yomitan は単なる tokenizer ではなく、左から見て「辞書で見つかった長さ」だけ進む。  
これが `/search.html` の自然な「一番 / 安全 / で / 強い / 案 / は / これ / です」に近い見え方を作っている。

## E. 実装方針

### E1. Go側に parser package を追加

候補パス:

```text
go/internal/queryparser/japanese.go
go/internal/queryparser/japanese_test.go
```

公開関数案:

```go
func ParseJapaneseQuery(ctx context.Context, text string, opts Options) Result
```

戻り値案:

```go
type Segment struct {
    Text         string `json:"text"`
    Reading      string `json:"reading,omitempty"`
    Lemma        string `json:"lemma,omitempty"`
    LemmaReading string `json:"lemmaReading,omitempty"`
    Kind         string `json:"kind"` // content | particle | aux | punct | unknown
    Start        int    `json:"start"`
    End          int    `json:"end"`
}

type Result struct {
    Segments  []Segment `json:"segments"`
    Keywords  []string  `json:"keywords"`
    ElapsedMs float64   `json:"elapsedMs"`
    TimedOut  bool      `json:"timedOut"`
    Source    string    `json:"source"` // go-japanese-query-parser
}
```

### E2. 初期実装は小さく、でもYomitan風の見え方を守る

初期段階では外部辞書DBを持ち込まない。  
かわりに、まず以下を丁寧に実装する。

- Unicode rune ベースで左から走査
- 連続漢字・カタカナ・英数字を候補 token にする
- 小さな固定 `particle` / `aux` lexicon を Go 側に持つ
  - `particle`: `は`, `が`, `を`, `に`, `で`, `と`, `も`, `へ`, `の`, `から`, `まで`, `より`, `や`, `か` など
  - `aux`: `です`, `ます`, `でした`, `ません`, `ない`, `た`, `だ`, `たい`, `れる`, `られる`, `せる`, `させる` など
  - これは辞書DBではなく、固定の小さな分類表。Yomitan GPL コードも辞書データもコピーしない
- ひらがな助詞を `particle` として segment に残す
- `です/ます/でした/ません/ない/た/だ` などは `aux` として segment に残す
- 形容詞らしい語尾（例: `強い`, `速い`, `良い`）を content として残す
- query keywords は `content` 優先で抽出
- `particle` / `aux` は segment には残すが query keyword からは原則除外
- 同一 keyword は dedupe
- 最大 keyword 数は既存と合わせて 12

この段階の目標は「完全なYomitan再現」ではなく、スクショ例のような query 用分割を安定させること。

### E3. 150ms timeout をGoとTSの両方で持つ

Go側:

```go
timeout := clampMaxMs(params.MaxMs, 20, 150)
ctx, cancel := context.WithTimeout(parent, time.Duration(timeout)*time.Millisecond)
defer cancel()
```

TS側:

```ts
return this.request<JapaneseQueryParseResult>("query.parseJapanese", params, 150);
```

理由: Go側だけに任せると、ソケット・goroutine・予期しない待ちでTSが待つ可能性がある。  
TS側 timeout も必ず持つ。

さらに、`rpc-client.request()` の timeout は request 送信後の pending request timer なので、socket reconnect 時間が前段で乗る可能性がある。  
そのため `retriever.ts` 側の Go parser 呼び出しは、RPC timeout だけでなく **reconnect を含む全体**を `Promise.race(..., 150ms)` で包む。

```ts
const parsed = await Promise.race([
  this.rpcClient.parseJapaneseQuery(text, 150),
  timeoutAfter(150, "go-ja-query-parser-timeout"),
]);
```

この全体 timeout により、sidecar 再起動や socket 断絶時も、Go parser 待ちで 150ms を大きく超えない。

### E4. TS側 wrapper を追加

`src/rpc-client.ts`:

```ts
async parseJapaneseQuery(text: string, maxMs = 150): Promise<JapaneseQueryParseResult> {
  return this.request<JapaneseQueryParseResult>("query.parseJapanese", { text, maxMs }, maxMs);
}
```

`src/retriever.ts` 側では、現行 `instantDeterministicRewrite()` を消さない。  
`EpisodicRetriever` class 内に、`this.rpcClient` を使える private wrapper を作る。

```ts
private async buildRecallQueryWithGoFallback(recentMessages: Message[]): Promise<string> {
  const go = await this.tryGoJapaneseParserWithin150ms(recentMessages);
  if (go.ok) return go.query;
  return instantDeterministicRewrite(recentMessages, this.config);
}
```

そして `retrieveRelevantContext()` の query 作成箇所を明示的に差し替える。

```ts
// before
const query = await instantDeterministicRewrite(recentMessages, this.config);

// after
const query = await this.buildRecallQueryWithGoFallback(recentMessages);
```

kill switch も用意する。実装時はどちらか一方を選ぶ。

- 設定として出す場合: `enableGoJapaneseQueryParser?: boolean`（default `true`）
- 内部運用だけにする場合: `EPISODIC_DISABLE_GO_JA_QUERY_PARSER=1` を `getEnvVal()` 経由で読む

直近で config schema cleanup を行ったため、公開設定を増やすかどうかは実装前に再確認する。最小実装では env kill switch の方が安全。

### E5. Go parser の結果採用条件

Go結果を採用するのは全部満たす時だけ。

1. `timedOut === false`
2. `elapsedMs <= 150`
3. `keywords.length >= 3`
4. query 文字数が `500` 文字以下
5. Go 側の `Result.Keywords` は authoritative filter として扱う。ただし malformed response 対策として、TS 側でも「keywords が助詞・助動詞だけではない」ことを safety net として確認する

それ以外は現行 TS parser に戻す。

## H. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| Go parser がTS現行より遅い | エージェント返信が遅くなる | TS側 150ms timeout + 即 fallback |
| 初期実装がYomitanほど賢くない | 精度改善が限定的 | golden test を増やし、段階的に語彙ルールを追加 |
| Yomitanコードの混入 | ライセンス問題 | コードコピー禁止。挙動・型思想のみ参考にしてGoで新規実装 |
| 助詞をqueryに入れすぎる | recall noise増加 | segmentには残すがkeywordsでは除外 |
| 漢字連続を長く取りすぎる | queryが粗くなる | まず短いgolden testで制御し、後で軽量辞書/trieを検討 |
| fallbackが効かずrecallが落ちる | メモリ注入が失敗する | Go失敗は例外にせず、必ず既存TS pathへ戻す |
| socket reconnect が 150ms timeout 外で走る | 体感遅延が 150ms を超える | `retriever.ts` 側で reconnect + RPC 全体を `Promise.race` 150ms で包む |
| query採用条件が曖昧 | 実装者ごとに挙動がぶれる | query文字数上限を 500 文字に固定し、TS safety net の役割を明記する |
