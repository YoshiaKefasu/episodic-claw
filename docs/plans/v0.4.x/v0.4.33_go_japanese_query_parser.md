# v0.4.33 — Go 日本語 Query Parser / Yomitan風文節Parser

> **作成日**: 2026-05-24  
> **ステータス**: Implementation in progress / Kagome enhancement planned  
> **目的**: Episodic-Claw の recall query 生成前段に、Go製の日本語文節Parserを追加し、Yomitan `/search.html` に近い自然な切り分けで日本語 recall 精度を上げる。  
> **スコープ**: Episodic-Claw のみ。DennouAibou / OpenClaw core は変更しない。  
> **性能方針**: Go parser cold 最大 150ms 狙い。150ms を超えたら即座に安全fallbackへ戻す。Kagome導入後は軽量Go parserを第一fallbackにする。

---

## A. 結論

今の Episodic-Claw の日本語 query parser は、温まった後は十分速い。実測では、5ユーザーメッセージ相当の query 生成が warm p99 約 0.47ms だった。  
ただし切り分けは素朴で、Yomitan `/search.html` のような「意味の塊ごとの分割」ではない。

今回やるべきことは、速度改善そのものではなく、**日本語の recall query 精度改善**。  
そのために、Go sidecar に小さな `query.parseJapanese` RPC を追加し、Yomitan風の `text / reading / lemma / kind` segment を返す。

2026-05-26 の実測では、初期Go parser は通常 **10.0〜14.7µs/op**、5ms throttle込みでも **約5.19ms/op** だった。  
150ms 制約に対してかなり余裕があるため、次段階では旧TS日本語parserを温存するより、**日本語入力は原則Go側へ通す**方針へ寄せる。

ただし、エージェント返信前の処理なので待たせてはいけない。  
Go parser は **150ms hard timeout** を持つ「賢い近道」として扱い、失敗・timeout・低品質結果なら安全fallbackへ戻す。Kagome導入後は、旧TS日本語parserではなく軽量Go parserを第一fallbackにする。

## B. 調査で読んだ証拠

### B1. 現行 query 生成の差し替え地点

`src/retriever.ts:298-388`:

```ts
export async function instantDeterministicRewrite(messages: Message[], config?: EpisodicPluginConfig): Promise<string> {
  ...
  const keywords = await extractPolyglotKeywords(cleanedText, config);
  ...
  return result.length > 0 ? result.join(" ") : fallbackText;
}
```

意味: recall query は `instantDeterministicRewrite()` で作られている。  
Go parser を入れるなら、ここを壊すのではなく、この関数の前段または中で「Go parser → 成功なら採用 / 失敗なら既存処理」という形にするのが安全。

### B2. 現行日本語 parser は速いが、surface 抽出だけ

`src/cjk-tokenizer.ts:23-35`:

```ts
const JA_CONTENT_POS = new Set(["名詞", "動詞", "形容詞", "副詞"]);

async function tokenizeJapanese(text: string): Promise<string[]> {
  const tokens = await tokenize(text);
  return tokens
    .filter((t) => JA_CONTENT_POS.has(t.pos))
    .map((t) => t.surface_form);
}
```

意味: 今の処理は `kuromojin` の品詞で surface を抜く。  
`reading`、`lemma`、助詞を含めた文節表示、Yomitanのような辞書一致ベースの最長寄り切り分けは扱っていない。

### B3. TS → Go RPC は既にある

`src/rpc-client.ts:506-543`:

```ts
private async request<T>(method: string, params: any = {}, timeoutMs = 120000): Promise<T> {
  ...
  const reqStr = JSON.stringify({ jsonrpc: "2.0", method, params, id }) + "\n";
  this.socket!.write(reqStr);
}
```

意味: 既存の JSON-RPC 経路に `query.parseJapanese` を足せる。  
`request(..., timeoutMs)` が既にあるので、TS側から 150ms timeout を強制しやすい。

### B4. Go sidecar 側も RPC method switch 方式（初期実装済み）

`go/main.go:3040-3060`:

```go
switch req.Method {
case "ai.recall":
    go handleRecall(conn, req)
...
case "cache.retry":
    go handleCacheRetry(conn, req)

```

意味: Go側は handler を追加する構造。  
初期実装では `case "query.parseJapanese": go handleQueryParseJapanese(conn, req)` を追加済み。

実体 handler は `go/main.go:2446-2478` にあり、`MaxMs` を 20〜150ms に clamp してから `queryparser.ParseJapaneseQuery(ctx, text)` を呼ぶ。

### B5. Yomitan の `/search.html` parser は segment を返す

`A:\yomitan\types\ext\api.d.ts:54-75`:

```ts

    text: string;
    reading: string;
    lemma?: string;
    lemmaReading?: string;
    headwords?: ...;

```

意味: 欲しい形は `text` だけではない。  
`reading` と `lemma` を持つ segment 形式に寄せると、後から query 生成の精度を上げやすい。

### B6. Yomitan の scanning parser は左から辞書一致で進む

`A:\yomitan\ext\js\background\backend.js:1707-1776`:

```js
while (i < ii) {

  const {dictionaryEntries, originalTextLength} = await this._translator.findTerms(...);
```

意味: Yomitan は単なる tokenizer ではなく、左から見て「辞書で見つかった長さ」だけ進む。  
これが `/search.html` の自然な「一番 / 安全 / で / 強い / 案 / は / これ / です」に近い見え方を作っている。

## E. 実装方針

### E1. Go側に parser package を追加

候補パス:

```text
go/internal/queryparser/japanese.go
go/internal/queryparser/japanese_test.go
```

公開関数案:

```go
func ParseJapaneseQuery(ctx context.Context, text string) Result
```

Kagome導入時に辞書・mode・stopword設定が増える場合のみ、`Options` を追加する。

戻り値案:

```go
type Segment struct {
    Text         string `json:"text"`
    Reading      string `json:"reading,omitempty"`
    Lemma        string `json:"lemma,omitempty"`
    Kind         string `json:"kind"` // content | particle | aux | punct | unknown
    Start        int    `json:"start"`
    End          int    `json:"end"`
}

type Result struct {
    Segments  []Segment `json:"segments"`
    Keywords  []string  `json:"keywords"`
    ElapsedMs float64   `json:"elapsedMs"`
    TimedOut  bool      `json:"timedOut"`
    Source    string    `json:"source"` // go-japanese-query-parser
}
```

### E2. 初期実装は小さく、でもYomitan風の見え方を守る

初期段階では外部辞書DBを持ち込まない。  
かわりに、まず以下を丁寧に実装する。

- Unicode rune ベースで左から走査
- 連続漢字・カタカナ・英数字を候補 token にする
- 小さな固定 `particle` / `aux` lexicon を Go 側に持つ
  - `particle`: `は`, `が`, `を`, `に`, `で`, `と`, `も`, `へ`, `の`, `から`, `まで`, `より`, `や`, `か` など
  - `aux`: `です`, `ます`, `でした`, `ません`, `ない`, `た`, `だ`, `たい`, `れる`, `られる`, `せる`, `させる` など
  - これは辞書DBではなく、固定の小さな分類表。Yomitan GPL コードも辞書データもコピーしない
- ひらがな助詞を `particle` として segment に残す
- `です/ます/でした/ません/ない/た/だ` などは `aux` として segment に残す
- 形容詞らしい語尾（例: `強い`, `速い`, `良い`）を content として残す
- query keywords は `content` 優先で抽出
- `particle` / `aux` は segment には残すが query keyword からは原則除外
- 同一 keyword は dedupe
- 最大 keyword 数は既存と合わせて 12

この段階の目標は「完全なYomitan再現」ではなく、スクショ例のような query 用分割を安定させること。

ただし、これは恒久的な日本語辞書ではない。  
`particleAffixes` / `auxAffixes` / `contentLexicon` は初期版の足場であり、長期運用で語彙を手作業追加し続けるのは避ける。

### E2.5. 旧TS日本語parserの廃止方針

初期実装では安全のため `instantDeterministicRewrite()` fallback を残す。  
ただし、Kagome版が 150ms 制約内で安定したら、recall query の日本語経路は以下へ整理する。

```text
日本語 dominant input
→ Go query.parseJapanese
→ Kagome search-mode tokenizer + POS/stopword filter
→ query keywords
```

廃止対象:

- recall query 用の旧TS日本語 tokenizer 依存
- 日本語 stopword / こそあど除去を TS 側だけで持つ構造
- `contentLexicon` を日本語語彙辞書として育てる運用

残すもの:

- attachment / noise cleanup など、言語非依存のTS前処理
- Go RPC失敗時の安全fallback
- env kill switch `EPISODIC_DISABLE_GO_JA_QUERY_PARSER=1`

意味: 旧TS日本語pathは「主役」から降ろす。  
ただし sidecar 障害時に recall 全体が落ちないよう、非常口としての fallback は残す。

### E2.6. Kagome版 parser を実装する

採用候補:

```text
github.com/ikawaha/kagome/v2
github.com/ikawaha/kagome-dict/ipa
```

現状: `go/go.mod` にはまだ Kagome 依存は入っていない。Kagomeはこの追記時点では **planned** 扱い。

外部確認:

- `github.com/ikawaha/kagome/v2` は pure Go の日本語形態素解析器。
- pkg.go.dev では v2.11.0、MIT License、Go 1.24.0 と確認できる。
- tokenizer は `normal / search / extended` mode を持つ。
- Kagome wiki では IPADIC / UniDIC を Go package として embed できると説明されている。
- 検索用途では `search` mode が候補。まず IPADIC + search mode で始める。

実装案:

1. `go/internal/queryparser` 内に Kagome tokenizer を lazy singleton として持つ。
2. 初回だけ辞書をロードし、以後は同じ tokenizer を再利用する。
3. `tokenizer.Search` 相当の search mode を使い、長い複合語を検索向けに分割する。
4. POS で助詞・助動詞・記号・代名詞/こそあど系を keywords から除外する。
5. `reading` / `lemma` が取れる場合は `Segment` に詰める。
6. Kagome初期化または解析が timeout したら、現行Go手書きparserまたはTS fallbackへ戻す。

推奨fallback順:

```text
Kagome Go parser
→ current lightweight Go parser
→ emergency TS fallback
```

理由:

- Kagome が品質担当。
- current lightweight Go parser が速度・安全担当。
- TS fallback は sidecar 障害時の非常口。

Kagome導入後に改めて実測する値:

| 指標 | 目標 |
|---|---:|
| Kagome first parse p95 | <= 150ms |
| Kagome warm parse p95 | <= 20ms |
| Kagome throttle 5ms込み | <= 150ms |
| fallback込みの最悪追加遅延 | <= 150ms |

もし Kagome cold が 150ms を超える場合:

- gateway起動時に tokenizer を warm-up する案を検討する。
- それでも重い場合は、Kagomeを optional path にし、通常は lightweight Go parser + stopword set に戻す。

### E3. 150ms timeout をGoとTSの両方で持つ

Go側:

```go
timeout := clampMaxMs(params.MaxMs, 20, 150)
ctx, cancel := context.WithTimeout(parent, time.Duration(timeout)*time.Millisecond)
defer cancel()
```

TS側:

```ts
return this.request<JapaneseQueryParseResult>("query.parseJapanese", params, 150);
```

理由: Go側だけに任せると、ソケット・goroutine・予期しない待ちでTSが待つ可能性がある。  
TS側 timeout も必ず持つ。

実装後レビューで、RPC client 側の `request(..., 150)` timeout と Go側 context timeout の二重管理で十分と判断した。  
そのため現時点では `retriever.ts` 側の追加 `Promise.race(...)` は入れない。

ただし、sidecar 再起動や socket 断絶で reconnect 待ちが 150ms を超える実ログが出た場合は、改めて `retriever.ts` 側で reconnect を含む全体 timeout を足す。

### E4. TS側 wrapper を追加（初期実装済み）

`src/rpc-client.ts`:

```ts
async parseJapaneseQuery(text: string, maxMs = 150): Promise<JapaneseQueryParseResult> {
  return this.request<JapaneseQueryParseResult>("query.parseJapanese", { text, maxMs }, maxMs);
}
```

`src/retriever.ts` 側では、現行 `instantDeterministicRewrite()` を消さない。  
`EpisodicRetriever` class 内に、`this.rpcClient` を使える private wrapper を作る。

初期実装では `src/rpc-client.ts:569-571` に `parseJapaneseQuery()`、`src/retriever.ts:706-749` に `buildRecallQueryWithGoFallback()` を追加済み。

```ts
private async buildRecallQueryWithGoFallback(recentMessages: Message[]): Promise<string> {
  const go = await this.tryGoJapaneseParserWithin150ms(recentMessages);
  if (go.ok) return go.query;
  return instantDeterministicRewrite(recentMessages, this.config);
}
```

そして `retrieveRelevantContext()` の query 作成箇所を明示的に差し替える。

```ts
// before
const query = await instantDeterministicRewrite(recentMessages, this.config);

// after
const query = await this.buildRecallQueryWithGoFallback(recentMessages);
```

kill switch も用意する。実装時はどちらか一方を選ぶ。

- 設定として出す場合: `enableGoJapaneseQueryParser?: boolean`（default `true`）
- 内部運用だけにする場合: `EPISODIC_DISABLE_GO_JA_QUERY_PARSER=1` を `getEnvVal()` 経由で読む

直近で config schema cleanup を行ったため、公開設定を増やすかどうかは実装前に再確認する。最小実装では env kill switch の方が安全。

### E5. Go parser の結果採用条件

Go結果を採用するのは全部満たす時だけ。

1. `timedOut === false`
2. `elapsedMs <= 150`
3. `keywords.length >= 3`
4. query 文字数が `500` 文字以下
5. Go 側の `Result.Keywords` は authoritative filter として扱う。ただし malformed response 対策として、TS 側でも「keywords が助詞・助動詞だけではない」ことを safety net として確認する

それ以外は安全fallbackへ戻す。Kagome導入後は lightweight Go parser を第一fallbackにし、TS fallback は sidecar 障害時の非常口に限定する。

## H. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| Go parser がTS現行より遅い | エージェント返信が遅くなる | TS側 150ms timeout + 即 fallback |
| 初期実装がYomitanほど賢くない | 精度改善が限定的 | golden test を増やし、段階的に語彙ルールを追加 |
| Yomitanコードの混入 | ライセンス問題 | コードコピー禁止。挙動・型思想のみ参考にしてGoで新規実装 |
| 助詞をqueryに入れすぎる | recall noise増加 | segmentには残すがkeywordsでは除外 |
| 漢字連続を長く取りすぎる | queryが粗くなる | まず短いgolden testで制御し、後で軽量辞書/trieを検討 |
| fallbackが効かずrecallが落ちる | メモリ注入が失敗する | Go失敗は例外にせず、必ず既存TS pathへ戻す |
| socket reconnect が 150ms timeout 外で走る | 体感遅延が 150ms を超える | 実ログが出た場合のみ `retriever.ts` 側で reconnect + RPC 全体 timeout を追加する |

## M. 2026-05-26 方針追記 — Go速度実測とKagome採用

### M1. 実測からの判断

軽量Go parser は、150ms制約に対して十分以上に速い。  
通常ベンチは約 **25.8µs/op**、5ms throttle込みでも **約5.30ms/op** だった。

Kagome warm ベンチは約 **127.5µs/op**、5ms throttle込みでも **約5.40ms/op**。  
一方、process-cold parse は約 **857.6ms/op** だった。

つまり、今のボトルネックは速度ではなく、以下の2点。

1. 日本語の切り分け品質
2. 手書き `contentLexicon` を育て続ける保守コスト

### M2. Pro Engineer 判断

YAGNI/KISSで見ると、最初から巨大な独自辞書を作るべきではない。  
一方で、`contentLexicon` を手で増やし続けるのもDRY/KISSに反する。

したがって次の実装は、**Kagomeを日本語品質担当として導入し、今の軽量Go parserをfallbackへ降格する** のが現場判断として一番バランスがよい。  
ただし process-cold parse が 150ms を超えるので、`go/main.go` で background warm-up をかけ、初回は軽量 fallback で逃がせるようにしている。

### M3. 推奨アーキテクチャ

```text
recent user messages
→ TS noise/attachment cleanup
→ Go query.parseJapanese first
   ├─ Japanese/CJK → Kagome search mode + POS/stopword/こそあど除外
   ├─ Kagome unavailable/timeout → lightweight Go parser fallback
   └─ Go sidecar error/kill-switch/low signal → existing deterministic TS fallback
→ ai.recall(query)
```

現実装では、Go呼び出し前に `detectDominantScript()` で日本語だけを分岐していない。これは処理を単純に保つためで、Latin-only input も Go RPC を一度通る。非日本語 query は Go結果の採用条件を満たせばそのまま使い、失敗時は従来TS fallbackへ戻る。将来、RPC往復が実測で負担になった場合だけ Japanese-dominant gate を足す。

### M4. 旧型TS日本語pathの扱い

Kagome版が通った後は、旧TS日本語 tokenizer は recall query 主経路から外す。  
ただし、Go sidecarが落ちた時に recall 全体が死なないよう、TS fallback 自体は非常口として残す。

この整理により、今後の日本語改善は TS と Go に分散せず、Go側の `queryparser` に集約される。
