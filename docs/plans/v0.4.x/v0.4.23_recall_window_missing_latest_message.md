> Date: 2026-04-21
> Status: 🔍 INVESTIGATION

## 1. 問題の概要

`recallQueryRecentMessageCount=2` 設定時、最新のユーザーメッセージがrecallクエリに含まれていないように見える現象。

### ユーザーの期待（正しいロジック）

```
recallQueryRecentMessageCount=1 なら → 最新ユーザーメッセージ1件だけでクエリ構築
recallQueryRecentMessageCount=2 なら → 最新2件のユーザーメッセージでクエリ構築
recallQueryRecentMessageCount=N なら → 最新N件
```

**最新ユーザーメッセージが常にwindowの最後尾に含まれるべき。** これが成り立たないならバグ。

### 2026-04-21 観測ログ

```
14:28:37 recall-window-fingerprint:
  currentMsgCount: 498
  userMsgCount: 162
  windowSize: 2                ← recallQueryRecentMessageCount=2
  lastRole: "assistant"       ← 配列末尾はassistant（正常）
  latestUserInWindow: true    ← コード上は「最新ユーザーMSGがwindowに含まれる」と判定
  latestUserDroppedByClassifier: false  ← 分類除外もされていない

  fingerprints:
    idx=0: rawLen=53,  cleanedLen=53,  isDominant=false
    idx=1: rawLen=181, cleanedLen=181, isDominant=false

14:28:37 recall query: "バック エンド エンジニアリング マジ 血 だらけ 格闘 直し Kasou"
  recentMsgs=2, eligible=2, skipped=0

```

**矛盾点**: ユーザーが14:27に送ったメッセージは「じゃあ 毎日 何枚か手書きをすればいいですよね?」（~30文字）。
しかし `idx=1` のrawLenは181文字。「毎日」「手書き」がクエリに含まれていない。

## 2. 根本原因の仮説（2026-04-21 再評価）

### 仮説A: 最新 user は window に入っているが、query rewrite で語が落ちている（主仮説）

現行実装は、直近 N 件の user message を message 単位で保持せず、まず 1 本の文字列へ連結してからキーワード抽出している。
このため、1つ前の長いユーザーメッセージが先頭側のキーワード枠を埋めると、短い最新メッセージは window に含まれていても query 語へ反映されない。

**証拠 1**: `src/retriever.ts:519-523`
- `recentMessages = currentMessages.filter(m => m.role === "user").slice(-recentMessageCount)`
- window 選定自体は単純で、設定 `2` なら user の末尾 2 件を取る。

**証拠 2**: `src/retriever.ts:300-314`
- `instantDeterministicRewrite()` は eligible text を `join("\n")` してから 1 回だけ `extractPolyglotKeywords()` を呼ぶ。
- つまり「最新メッセージごと」ではなく「2件を混ぜた1本の塊」として query 化している。

**証拠 3**: `src/retriever.ts:357-368` + `src/cjk-tokenizer.ts:30-35`
- 日本語トークンは出現順で並び、CJK 優先時は `primaryCount=8` の固定枠を先頭から埋める。
- 長い 1 件前のメッセージが前半の 8 席を埋めると、短い最新文は後ろへ押し出されやすい。

**観測ログとの整合**: `openclaw-2026-04-21.log:445-446`
- `latestUserInWindow=true`
- `latestUserDroppedByClassifier=false`
- `eligible=2 skipped=0`
- それでも query は `"バック エンド エンジニアリング マジ 血 だらけ 格闘 直し Kasou"` で、ユーザーが期待した最新文の語が見えない。
- この症状は「window 未選定」より「query 圧縮で席を失った」でより自然に説明できる。

### 仮説B: `before_prompt_build` タイミング問題（副仮説、未否定）

OpenClaw本体の `before_prompt_build` が最新ユーザーメッセージ追加前に発火している可能性はまだ残る。
ただし、現行の `latestUserInWindow=true` は episodic-claw が受け取った `currentMessages` の中での最新 user を示すだけで、
UI 上で「今送ったばかりの最新」と同一とはまだ証明していない。

**証拠**: `DennouAibou/src/agents/pi-embedded-runner/run/attempt.ts:1520-1523` と `DennouAibou/src/agents/pi-embedded-runner/run/attempt.prompt-helpers.ts:38-46`
- 上流互換実装では `before_prompt_build` に `activeSession.messages` をそのまま渡す契約になっている。
- ただし今回の本番 OpenClaw 実体で、送信直後メッセージがその配列へ入る直前か直後かまでは未観測。

**検証方法**: `before_prompt_build` 側で `msgs.length`、末尾 3 role、`latestUserPreview` を同時出力して、UI の最新送信と照合する。

### 仮説C: rawLen=181 は reply/引用文脈を含み、短い最新文が長文側へ飲まれている

今回の `rawLen=181` は、ユーザー本人が意識している短い最新文そのものではなく、reply 由来の引用や文脈込みの text である可能性が高い。
その場合でも、問題の本質は「window から落ちた」ではなく「長い text が query の前半席を占有した」に寄る。

**証拠**: `src/large-payload.ts:136-174`
- Telegram の untrusted metadata JSON は strip しているが、通常の reply 文脈や本文として入ってきた引用テキストまでは別扱い。

### 版境界の暫定判定

この症状は **v0.4.20 以後に初めて入った可能性は低い**。

**証拠 1**: `CHANGELOG.md:383-388`
- `Instant Deterministic Query Rewriting` は v0.3.7 で導入。

**証拠 2**: `git show v0.4.20:src/retriever.ts:279-368`
- v0.4.20 時点ですでに `join("\n")` → `extractPolyglotKeywords()` → `primaryCount=8` / `secondaryCount=4` の構造が存在する。

**証拠 3**: `CHANGELOG.md:41-58`
- v0.4.20 の変更は watcher/rebuild 系で、recall query 組み立て変更ではない。

したがって、もし「前は体感上うまく効いていた」のが事実なら、
原因は v0.4.20 以後の query rewrite 実装変更ではなく、
会話の長さ・文体・reply 形態・OpenClaw 側の message 内容差で症状が表面化した可能性が高い。

## 3. Fix 1: フィンガープリント観測強化（preview + per-message query観測）

### 目的
window内の各メッセージの**実際の内容**と、各メッセージが query にどう寄与したかをログで見える化する。
これにより「window未選定」なのか「query rewriteで押し負けた」のかを切り分ける。

### 変更概要

**`src/retriever.ts`** — `recall-window-fingerprint` イベント出力箇所:

```typescript
// Before (v0.4.22 Fix C)
const fingerprints = recentMessages.map((m, i) => {
  const rawText = extractText(m.content);
  const text = stripReasoningTagsFromText(rawText, { mode: "strict", trim: "both" });
  const { isDominant, cleanedText } = classifyAndStripAttachment(text);
  return { idx: i, rawLen: rawText.length, cleanedLen: cleanedText.length, isDominant };
});

// After (v0.4.23 Fix 1)
const fingerprints = recentMessages.map((m, i) => {
  const rawText = extractText(m.content);
  const text = stripReasoningTagsFromText(rawText, { mode: "strict", trim: "both" });
  const { isDominant, cleanedText } = classifyAndStripAttachment(text);
  const preview = rawText.substring(0, 80).replace(/\n/g, "\\n");
  return { idx: i, rawLen: rawText.length, cleanedLen: cleanedText.length, isDominant, preview };
});
```

**`latestUserMsg` のプレビューも追加:**

```typescript
// Before
latestUserDroppedByClassifier: boolean

// After  
latestUserDroppedByClassifier: boolean,
latestUserPreview: string  // 最新ユーザーメッセージの先頭80文字
```

**ログ出力イメージ:**
```json
{
  "event": "recall-window-fingerprint",
  "latestUserPreview": "じゃあ 毎日 何枚か手書きをすればいいですよね? // ←これを14:27で送った...",
  "fingerprints": [
    { "idx": 0, "rawLen": 53, "preview": "[System: ...] バックエンドの...", "isDominant": false },
    { "idx": 1, "rawLen": 181, "preview": "毎日 何枚か手書きをすればいいですよね? ...", "isDominant": false }
  ]
}
```

**追加観測（今回の再評価で必須）:**

- 各 `fingerprint` に `queryKeywordsPreview` を追加
  - その message 単体から抽出された先頭 6 語だけを出す
- `before_prompt_build` 側で `msgCount` / `last3Roles` / `latestUserPreview` を 1 行で出す

これで、

1. plugin が受け取った `event.messages` に UI の最新送信が入っているか
2. 入っているなら、その message 単体から何語取れているか
3. 2件を混ぜた最終 query でどちらが席を取ったか

を一発で追える。

- **AC-2**: `latestUserPreview` フィールドが最新ユーザーメッセージの先頭80文字を示す
- **AC-3**: 各 message について `queryKeywordsPreview` が出力される

## 4. Fix 2: 根本原因の特定と修正（観測結果に依存）

Fix 1 の観測結果に基づいて根本原因を確定し、修正する。

### 想定される修正パターン

#### パターンA: message-aware query rewrite（推奨）

最新 user message の語が、1つ前の長文に押し潰されないように query 組み立てを message 単位へ変更する。

**修正案**:

- `recentMessages` を newest-first で処理
- 各 message ごとにキーワード抽出
- 最新 message に固定席を予約（例: 12語中 4 語）
- 残りを 1 件前以降で埋める
- 重複語は dedupe する

```typescript
// image で言えば「最新メッセージ専用レーン」を1本確保する。
// 古い長文が高速道路を全部塞いでも、最新の短文が必ず数語は前に出る。
```

**期待効果**:
- `latestUserInWindow=true` なのに query から消える症状を直接止められる
- `before_prompt_build` のタイミングが正常でも効く
- KISS/YAGNI 的にも `retriever.ts` 内で閉じる最小修正

#### パターンB: `before_prompt_build` タイミング問題の場合

OpenClawが `currentMessages` に最新ユーザーメッセージを追加する**前**にフックが発火している場合、episodic-claw側で末尾のユーザーメッセージを補正する。
これはOpenClaw本体の仕様なので、episodic-claw側でワークアラウンドを入れる。

**修正案**: `retrieveRelevantContext` で、最新ユーザーメッセージが `recentMessages` の末尾にない場合、強制的に `allUserMsgs.at(-1)` をクエリに含める。

```typescript
// currentMessages の最後が assistant の場合でも、
// その前のユーザーメッセージが最新であり、
// .slice(-recallQueryRecentMessageCount) に含まれていることを guarantee する。
```

#### パターンC: reply/引用混入が主因の場合

rawLen=181 が reply/引用込みで正しいなら、query 構築ロジック自体は「窓選定」ではなく「混ぜ方」が問題。
この場合もまずはパターンAを優先し、必要なら reply 部分の除去ルールを追加する。

## 5. 実装フェーズ

### Phase 1: 観測強化（Fix 1）— 即デプロイ

1. `retriever.ts` に `preview` + `latestUserPreview` + `queryKeywordsPreview` を追加
2. `index.ts` `before_prompt_build` で `msgCount` / `last3Roles` / `latestUserPreview` を1行出力
3. ビルド → デプロイ → 会話1往復 → ログ分析
4. 「window未選定」か「query rewrite偏り」かを確定

### Phase 2: 根本修正（Fix 2-A 推奨）

1. `instantDeterministicRewrite()` を message-aware 化
2. 最新 user message に query 枠を予約
3. dedupe + newest-first 優先で最終 query を構築
4. build/test を通す

**Phase 2 Acceptance Criteria**

- **AC-2-1**: `recallQueryRecentMessageCount=2` で、最新 user message が 3 文字以上の有意味テキストなら、その message 由来の語が最終 query に最低 1 語は残る
- **AC-2-2**: 1 件前の長文 + 最新短文の組み合わせでも、最新短文が query から完全消失しない
- **AC-2-3**: 既存の attachment/noise 除去挙動を壊さない
- **AC-2-4**: `npm run build:ts` がPASS
- **AC-2-5**: `npm test` がPASS

### Phase 3: タイミング補正（必要時のみ）

Phase 1 で **本当に** `before_prompt_build` が送信直後の最新 user を受け取っていないと確認できた場合のみ、
`allUserMsgs.at(-1)` 強制補正を追加する。

現時点ではこの補正を Phase 2 より先に入れない。
- 理由: `latestUserInWindow=true` のケースには効かず、症状の本丸を外す可能性がある。

**Phase 3 へ進む条件**

- `before_prompt_build` の `latestUserPreview` が、UI で今送った最新 user message と一致しない
- かつ `msgCount` / 末尾 role 列から見ても、plugin が 1 ターン古い `event.messages` を受け取っている

**Phase 3 Acceptance Criteria**

- **AC-3-1**: 送信直後ターンで、plugin が参照する末尾 user が UI の最新送信と一致する
- **AC-3-2**: 補正追加後も `recallQueryRecentMessageCount=N` の上限件数契約を壊さない
- **AC-3-3**: `npm run build:ts` がPASS
- **AC-3-4**: `npm test` がPASS
