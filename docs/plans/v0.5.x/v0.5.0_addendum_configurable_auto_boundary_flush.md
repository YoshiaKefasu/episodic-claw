# v0.5.0 Addendum — Configurable Auto Boundary Flush

Status: Phases A, B, C, D, E implemented and code-reviewed APPROVE. Phase F verification effectively covered by focused tests and review evidence.

Date: 2026-06-28

## Goal

Make automatic narrative episode creation configurable.

The user should be able to disable these automatic send paths:

1. idle flush — sending after a quiet period
2. time-gap boundary — sending when user-message timestamps have a large gap
3. Surprise boundary — sending immediately when Surprise says the topic changed

But this must still keep:

1. manual `ep-boundary`
2. Surprise checkpoint recording
3. near-64K auto flush up to the last Surprise checkpoint
4. hard safety flush when the buffer is too large

Plain version:

The system may stop automatically closing the book just because the room went quiet or the topic changed. But it must still keep bookmarks. When the book gets too thick, it can still close the chapter at the latest bookmark before the 64K cliff.

## Current evidence

Note:

The evidence line numbers below were captured during the pre-implementation investigation pass. After Phases A-E landed, some exact line numbers shifted, but the structural facts remained the same.

### Evidence A — idle flush is automatic today

`src/segmenter.ts:468-479` schedules an idle timer whenever the buffer is non-empty.

`src/segmenter.ts:485-522` turns that timer into `handleSegmentBoundary(..., "idle-timeout", ...)`, then clears buffer/checkpoint state.

Meaning:

The system currently has a quiet-room timer. If the chat stays quiet long enough, it automatically sends the current buffer to narrative generation.

### Evidence B — time-gap boundary is automatic today

`src/segmenter.ts:529-543` computes whether the gap between the last buffered user message and first new user message exceeds `segmentationTimeGapMinutes`.

`src/segmenter.ts:683-701` immediately calls `handleSegmentBoundary(..., "time-gap", ...)` when that condition is true.

Meaning:

The system currently says, “too much time passed, so this must be a new chapter,” and sends the previous buffer automatically.

### Evidence C — Surprise scoring and Surprise sending are currently coupled

`src/segmenter.ts:721-723` computes `shouldBoundary = sizeLimitExceeded || !!score?.isBoundary`.

`src/segmenter.ts:724-740` records a Surprise checkpoint when `score.isBoundary` is true, or when `rawSurprise >= segmentationMinRawSurprise` even if cooldown prevents immediate boundary creation.

Meaning:

The code currently uses Surprise for two jobs:

1. putting a bookmark in the buffer
2. immediately sending the buffer when `score.isBoundary` is true

This addendum separates those two jobs.

### Evidence D — near-64K already depends on checkpoints

`src/segmenter.ts:742-758` runs near-64K prefix flush. It tries `flushPrefixAtCheckpoint()` first. If no safe checkpoint exists, it escalates to full size-limit flush.

Meaning:

near-64K behavior already knows how to use the latest Surprise bookmark. Therefore disabling immediate Surprise sending must not disable checkpoint recording.

### Evidence E — configuration currently lacks this separation

`src/config.ts:138-144` loads segmentation tuning values, including `segmentationTimeGapMinutes`.

`src/types.ts:101-114` exposes segmentation values, but has no field for “observe Surprise but do not auto-send.”

`src/index.ts:519-522` exposes `segmentationTimeGapMinutes` in the TypeBox schema as a forced boundary threshold.

Meaning:

The UI/config surface can tune sensitivity, but cannot yet disable specific automatic send paths.

## Proposed config

Add a nested config object:

```json
"narrativeBoundary": {
  "autoIdleFlush": true,
  "autoTimeGapFlush": true,
  "autoSurpriseFlush": true
}
```

Default values should stay backward-compatible:

```json
{
  "autoIdleFlush": true,
  "autoTimeGapFlush": true,
  "autoSurpriseFlush": true
}
```

Recommended Kasou-style setting:

```json
"narrativeBoundary": {
  "autoIdleFlush": false,
  "autoTimeGapFlush": false,
  "autoSurpriseFlush": false
}
```

This means:

- do not narrativize just because chat became quiet
- do not narrativize just because timestamps jumped
- do not narrativize immediately just because Surprise fired
- still record Surprise checkpoints
- still narrativize near 64K using the last checkpoint
- still allow manual `ep-boundary`
- still preserve hard size safety

## Behavior rules

### Rule 1 — disabling Surprise auto-send must not disable Surprise observation

When `autoSurpriseFlush=false`, `segmentScore()` should still run.

The system should still record `latestSurpriseCheckpoint` when:

- `score.isBoundary === true`, or
- `rawSurprise >= segmentationMinRawSurprise`

Only the immediate `shouldBoundary` decision should be suppressed.

Plain version:

Kasou can tell the system, “keep noticing where the story turns, but do not close the chapter yet.”

### Rule 2 — near-64K is a safety/quality path, not a user-disable toggle

The near-64K path should always remain active. It should flush up to the latest safe checkpoint even if `autoSurpriseFlush=false`.

If no valid checkpoint exists, the existing full size-limit flush should remain as safety fallback.

Plain version:

If the book is about to hit the model window wall, it is allowed to close at the latest bookmark. If there is no bookmark, it must still avoid crashing into the wall.

### Rule 3 — manual `ep-boundary` is unaffected

`ep-boundary` should ignore these automatic boundary switches.

Manual tool use means Kasou explicitly decided to close the chapter.

### Rule 4 — hard size-limit protection is not disabled

The config should not allow users to disable the final hard safety flush.

This prevents oversized chunks from reaching narrative generation or breaking the queue.

### Rule 5 — `segmentationTimeGapMinutes` remains the interval value

For this addendum, do not split `segmentationTimeGapMinutes` into separate idle and time-gap intervals.

It continues to define:

- idle delay, only if `autoIdleFlush=true`
- time-gap threshold, only if `autoTimeGapFlush=true`

Separate interval settings can be a future plan if needed.

```ts
export interface NarrativeBoundaryConfig {

  autoTimeGapFlush?: boolean;

```

Add `narrativeBoundary?: NarrativeBoundaryConfig` to `EpisodicPluginConfig`.

Add TypeBox/schema entries with clear descriptions.

`openclaw.plugin.json` descriptions should follow the existing Blast Radius style. Example intent:

- if `autoIdleFlush=false`, quiet-period episode creation stops and buffers may wait for manual/near-64K/safety paths
- if `autoTimeGapFlush=false`, timestamp gaps no longer force a chapter close
- if `autoSurpriseFlush=false`, Surprise still places bookmarks but no longer closes the chapter immediately

Add config pipeline tests so this field is not silently dropped.

### Phase B — pass config into `EventSegmenter`

File:

- `src/index.ts`
- `src/segmenter.ts`

Extend the `EventSegmenter` tuning object to include boundary switch values.

Inside `EventSegmenter`, keep them as private booleans with safe defaults.

### Phase C — gate idle flush

File:

- `src/segmenter.ts`

If `autoIdleFlush=false`:

- gate at the method level: the first part of `scheduleIdleFlush()` should call `clearIdleFlushTimer()` and return early
- this covers all current callers uniformly, including WAL restore, ordinary processTurn paths, prefix flush, and error fallback paths
- manual `forceBoundary()` should still work

### Phase D — gate time-gap flush

File:

- `src/segmenter.ts`

Change the time-gap branch from:

```ts
if (this.isTimeGapBoundary(dedupedMessages)) { ... }
```

to conceptually:

```ts
if (this.autoTimeGapFlush && this.isTimeGapBoundary(dedupedMessages)) { ... }
```

If disabled, the messages continue through Surprise scoring and normal buffering.

### Phase E — gate immediate Surprise flush, but keep checkpoints

File:

- `src/segmenter.ts`

Change boundary decision conceptually from:

```ts
let shouldBoundary = sizeLimitExceeded || !!score?.isBoundary;
```

to:

```ts
let shouldBoundary = sizeLimitExceeded || (this.autoSurpriseFlush && !!score?.isBoundary);
```

Important:

The checkpoint recording block must stay outside this gate.

The Surprise log should include enough context to show when immediate Surprise flushing is disabled, so operators do not mistake `boundary=false` for a broken Surprise score.

### Phase F — verify near-64K checkpoint flush remains always active

File:

- `src/segmenter.ts`

Do not add a user config toggle for near-64K prefix flush.

The existing near-64K path should continue to run when `bufferTokenCount >= SOFT_TOKEN_TARGET`.

This keeps the last-Surprise-checkpoint behavior alive even when immediate Surprise auto-send is disabled.

## Behavioral consequences

If `autoIdleFlush=false`, `autoTimeGapFlush=false`, and `autoSurpriseFlush=false` are all set, ordinary chat will no longer generate episodes just because the room became quiet, timestamps jumped, or Surprise fired.

In that mode, episodes are created by:

1. manual `ep-boundary`
2. near-64K prefix flush to the latest Surprise checkpoint
3. hard size-limit safety flush

This is intentional, but it means buffers can stay live much longer. The WAL continues to protect buffered messages, and hard size safety remains the final guardrail.

If `autoTimeGapFlush=true`, a time-gap boundary keeps existing behavior: it clears the live Surprise checkpoint because the buffer is replaced with the new context. This is not changed by this addendum.

## Test plan

Add focused tests. Reuse existing segmenter mock patterns where possible.

1. `autoIdleFlush=false` does not schedule idle flush and does not enqueue after quiet timer.
2. `autoTimeGapFlush=false` does not enqueue on a large timestamp gap.
3. `autoSurpriseFlush=false` does not enqueue when `score.isBoundary=true`.
4. `autoSurpriseFlush=false` still records a Surprise checkpoint.
5. Near-64K still flushes prefix up to the checkpoint even when `autoSurpriseFlush=false`.
6. No checkpoint + near-64K still escalates to full safety flush.
7. `ep-boundary` still works when all automatic switches are false.
8. `loadConfig({})` defaults all three user-facing switches to true.
9. `loadConfig({ narrativeBoundary: ... })` preserves false values.
10. `openclaw.plugin.json` schema contains `narrativeBoundary` with `additionalProperties:false`.
11. All three auto-flush switches disabled: buffer is not sent by idle/time-gap/immediate-Surprise and still reaches hard safety flush when needed. (Covered by composition of items 1-3 and 6; the hard safety path remains unconditional.)

## Risks and mitigations

### Risk 1 — accidentally disabling checkpoint recording

If the implementation gates the whole Surprise block behind `autoSurpriseFlush`, near-64K will lose its bookmark.

Mitigation:

Add a test where `autoSurpriseFlush=false`, `score.isBoundary=true`, and a checkpoint is still stored.

### Risk 2 — near-64K is accidentally treated as optional

If implementation adds a near-64K disable switch, the system may lose the soft safety net and only flush at the hard cap.

Mitigation:

Do not add `near64kSurpriseFlush` as a user-facing config. Keep near-64K and `HARD_TOKEN_CAP` outside user-disable controls.

### Risk 3 — idle timer remains scheduled after disabled config

If an existing timer survives, disabling idle auto flush may not take effect until restart.

Mitigation:

When disabled, `scheduleIdleFlush()` should clear any existing idle timer and return.

### Risk 4 — config naming confusion

`segmentationTimeGapMinutes` currently affects both idle and time-gap. Adding separate toggles may confuse users.

Mitigation:

Schema descriptions must say the interval is still shared for now.

## Acceptance criteria

1. User can set `narrativeBoundary.autoIdleFlush=false`.
2. User can set `narrativeBoundary.autoTimeGapFlush=false`.
3. User can set `narrativeBoundary.autoSurpriseFlush=false`.
4. near-64K checkpoint flush remains active without a user-facing disable switch.
5. With the above settings, episodes are created by manual `ep-boundary` or near-64K/safety paths, not by idle/time-gap/immediate-Surprise auto-send.
6. Existing default behavior remains unchanged for users who do not set `narrativeBoundary`.
7. Tests and code-reviewer must pass before commit.

## Current state summary

Right now the addendum goal is effectively achieved.

What the user can now disable:

1. idle auto-send via `narrativeBoundary.autoIdleFlush=false`
2. time-gap auto-send via `narrativeBoundary.autoTimeGapFlush=false`
3. immediate Surprise auto-send via `narrativeBoundary.autoSurpriseFlush=false`

What always remains active:

1. manual `ep-boundary`
2. Surprise checkpoint recording
3. near-64K prefix flush to the last valid Surprise checkpoint
4. hard safety flush at the size limit

Plain version:

The automatic doors can now be locked one by one, but the emergency exit is still open. Kasou can close the chapter by hand, and the system still keeps bookmarks so it can safely split near the 64K cliff.

Implementation note:

There is no separate Phase-F feature flag. Phase F was a verification goal: make sure near-64K safety stayed alive while the other auto-send paths became configurable.
