# v0.5.0 — Agent-driven Narrative Boundary + Go Segmenter Migration Plan

Status: Phases 1, 1.5, 2, 3, and 4 implemented and code-reviewed APPROVE  
Scope: Episodic-Claw only  
Release target: v0.5.0  
Release rule: do not publish GitHub or ClawHub until user explicitly approves release.

## 1. Plain summary

v0.5.0 changes who can decide when a story chapter ends.

Today, Episodic-Claw mostly decides episode boundaries automatically: surprise score, time gap, idle timeout, or size limit. That is useful, but Kasou often knows better than the heuristic when a task is actually finished or when the conversation is about to switch topics.

This plan adds an agent-facing tool, tentatively named `ep-boundary`, so Kasou can say:

> “Close the current story here, and include this note as editorial context.”

The note must not be mixed into the conversation transcript as if the user or assistant said it. It should travel as separate boundary metadata and be included in the narrative prompt as an Agent Boundary Note.

If the current segment is approaching the existing 64K narrative split, Episodic-Claw should not wait until it is forced to cut mechanically. It should auto-narrativize immediately up to the latest meaningful Surprise checkpoint. The newer tail after that checkpoint stays live for the next episode.

The second half of v0.5.0 moves the surrounding segmentation state toward Go, matching the project direction: TypeScript is the OpenClaw adapter, Go is the processing engine.

- `src/segmenter.ts:657-660` detects `sizeLimitExceeded` from `HARD_TOKEN_CAP`.

Meaning: the current system protects the model from oversized chunks, but it does not yet ask, “where did Surprise last mark a natural story break before we hit 64K?” v0.5.0 should add that missing semantic cut point.

Plain example: right now, if a chapter gets too long, we cut the manuscript by page count. The new behavior should first look for the last natural scene break.

## 3. Goals

1. Add a tool Kasou can call any time to close the current narrative segment.
2. Let Kasou attach supplemental context to the segment without treating it as transcript text.
3. Preserve all existing automatic boundaries: surprise, time gap, idle timeout, size limit, force flush.
4. Keep ghost-chunk protections intact: cursor restore, warm-start skip, WAL, compaction skip, empty-hook no-op.
5. Move new deterministic boundary state toward Go without a risky one-shot rewrite.
6. Keep TypeScript as the OpenClaw adapter: tool registration, hook entrypoints, config/schema, RPC wrapper, emergency fallback.
7. When the buffer approaches the existing 64K split, auto-flush up to the latest meaningful Surprise checkpoint instead of waiting for mechanical chunking.

## 4. Non-goals

1. Do not change OpenClaw core or DennouAibou.
2. Do not move LLM narrative generation itself to Go in this phase.
3. Do not remove the existing TS `EventSegmenter` until the Go-backed path has soak time.
4. Do not treat boundary notes as user/assistant messages.
5. Do not add a new external dependency unless a later review proves it is necessary.
6. Do not invent a Surprise checkpoint if none exists; fallback to the existing size-limit safety path.

## 5. Proposed user-facing tool

Tool name: `ep-boundary`

Purpose: let the agent close the current narrative segment deliberately.

Parameters:

```ts
{
  note?: string;       // agent editorial note, max 2000 chars
  reason?: "task-complete" | "topic-shift" | "manual" | "safety" | "handoff";
  titleHint?: string;  // optional title hint, max 120 chars
}
```

Recommended tool description:

> Close the current episodic narrative chapter now. Use this when the task is complete, the conversation is switching topics, or you need to attach a short editorial note for the narrative writer. The note is not user speech; it is guidance for summarizing this chapter.

Response shape:

```ts
{
  content: [{ type: "text", text: "Closed the current story segment." }],
  details: {
    flushed: boolean,
    reason: string,
    enqueuedChunks: number,
    fallbackUsed?: boolean
  }
}
```

## 6. Boundary metadata contract

Add metadata to the cache queue item. Tentative fields:

```go
BoundaryNote      string `json:"boundaryNote,omitempty"`
BoundaryBy        string `json:"boundaryBy,omitempty"`
BoundaryReason    string `json:"boundaryReason,omitempty"`
BoundaryTitleHint string `json:"boundaryTitleHint,omitempty"`
BoundaryCreatedAt string `json:"boundaryCreatedAt,omitempty"`
```

Rules:

1. `BoundaryNote` is never appended to `RawText`.
2. `BoundaryBy` should be the resolved `agentId`.
3. `BoundaryReason` is separate from queue `Reason`. Queue `Reason` stays operational, e.g. `force-flush`; boundary reason is semantic, e.g. `task-complete`.
4. `BoundaryNote` is capped at 2000 chars in TS before RPC and capped again at 2000 chars in Go before storage.
5. No full prompt, API key, or large transcript is logged.

### Reason contract table

`Reason` is the operational queue reason. It must remain compatible with existing queue and worker behavior.

`BoundaryReason` is the semantic reason. It explains why this boundary happened and can contain newer v0.5.0 meanings.

| Boundary source | Queue `Reason` | `BoundaryReason` | Notes |
|---|---|---|---|
| Surprise auto boundary | `surprise-boundary` | empty or `surprise-boundary` | Existing behavior stays valid. |
| Size limit fallback | `size-limit` | empty or `size-limit` | Existing 64K protection stays valid. |
| Near-64K last-Surprise cut | `size-limit` | `near-64k-surprise-cut` | Operationally still a size-limit protection; semantically it cut at the last Surprise checkpoint. |
| Idle timeout | `idle-timeout` | empty or `idle-timeout` | Existing queue reason remains. |
| Time gap | `time-gap` | empty or `time-gap` | Existing queue reason remains. |
| Agent tool `ep-boundary` | `force-flush` | `task-complete` / `topic-shift` / `manual` / `safety` / `handoff` | Agent semantic reason is metadata only. |

Compatibility rule:

Do not add `near-64k-surprise-cut`, `task-complete`, or other agent-facing reasons directly to queue `Reason` unless all TS/Go queue unions and worker switches are updated in the same commit. The safer v0.5.0 default is to keep queue `Reason` operational and put new semantics in `BoundaryReason`.

Schema migration rule:

No PebbleDB migration is needed for the new fields because they are optional / `omitempty`. Old queue items deserialize with empty boundary metadata and continue through lease/ack/retry normally.

## 7. Narrative prompt behavior

When the narrative worker builds the prompt, it should include the note in a separate block like:

```text
Agent Boundary Note:
The agent deliberately closed this chapter here.
Reason: task-complete
Title hint: optional title
Note: ...

This note is editorial context. Do not quote it as user or assistant speech.
```

This keeps the LLM aware of Kasou's intent while protecting the transcript from contamination.

Implementation decision:

Do not concatenate the note into `{conversationText}`.

Add a separate prompt variable, tentatively `{boundaryNoteBlock}`, near the existing prompt-template resolution path. If no boundary metadata exists, it resolves to an empty string.

Conceptual template shape:

```text
{previousEpisode}

{boundaryNoteBlock}

Conversation:
{conversationText}
```

This keeps the note outside the transcript while still giving the narrative LLM editorial context.

Custom template compatibility:

Existing custom `narrativeUserPromptTemplate` values only know `{previousEpisode}` and `{conversationText}`. v0.5.0 must avoid silently dropping a non-empty boundary note.

Preferred behavior:

1. Support `{boundaryNoteBlock}` as a new optional template variable.
2. If a custom template does not contain `{boundaryNoteBlock}` and the block is non-empty, append the block outside the transcript after template resolution.
3. Never inject the block into `{conversationText}`.

## 8. Near-64K auto boundary behavior

When the buffered conversation approaches the existing 64K split behavior, the system should immediately create a narrative job instead of waiting for idle/time-gap/manual tool use or mechanical queue chunking.

Desired behavior:

1. Track the latest meaningful Surprise checkpoint while processing turns.
2. A checkpoint should store enough deterministic information to split safely later:
   - buffer message index
   - current cursor / message count
   - raw surprise score
   - score reason / threshold fields when available
   - timestamp
3. When estimated narrative input approaches the 64K split threshold, choose the latest safe checkpoint.
4. Flush only the prefix up to that checkpoint.
5. Keep the tail after that checkpoint in the live segmenter buffer.
6. Attach metadata such as `BoundaryReason = "near-64k-surprise-cut"` and `BoundaryBy = "auto"`.
7. If no checkpoint exists, use the current size-limit fallback rather than guessing.

Threshold decision:

Use `SOFT_TOKEN_TARGET = 48_000` as the first v0.5.0 near-64K trigger. This means Episodic-Claw starts looking for the latest safe Surprise checkpoint before it reaches `HARD_TOKEN_CAP = 64_000`. The hard cap remains the emergency fallback.

Checkpoint decision:

Record checkpoints from raw Surprise evidence, not only the final `score.isBoundary` flag. `score.isBoundary` may be suppressed by cooldown, but the raw surprise point can still be a useful semantic cut when the buffer is approaching 64K.

Initial checkpoint rule:

1. Store a checkpoint when `score.isBoundary === true`.
2. Also store a checkpoint when `rawSurprise >= segmentationMinRawSurprise`, even if cooldown made `score.isBoundary === false`.
3. The checkpoint index is the boundary position immediately after the message that produced the Surprise score.
4. A checkpoint at the beginning of the buffer is allowed, but tests must cover it. If it would produce an empty prefix, ignore it and use fallback.

Important distinction:

- Queue `Reason` can remain operationally compatible as `size-limit` if adding a new queue enum is too risky.
- Boundary metadata should keep the semantic reason, e.g. `near-64k-surprise-cut`.

This matters because the narrative LLM should receive a coherent prefix, not a raw 64K mechanical slice when the agent has already detected a meaningful shift earlier.

Plain example:

If the buffer is about to hit 64K and the last real story turn happened around message 180, send messages up to 180 now. Keep messages 181+ in memory as the beginning of the next episode.

Initial safety rule:

Do not move this logic fully to Go in the first commit. First add tests around the current TS boundary behavior, then introduce Go-backed checkpoint state after the split semantics are proven.

## 9. Phased implementation

### Phase 1 — TS tool + existing boundary path

Add `ep-boundary` in `src/index.ts` beside the other tools.

Initial behavior:

1. Resolve workspace with existing `resolveAgentWorkspaces(ctx, openClawGlobalConfig)`.
2. `prepareWorkspaces(resolution)`.
3. `getAgentState(agentId)`.
4. Call a new `state.segmenter.forceBoundary(...)` or equivalent wrapper.
5. Await the boundary request and return confirmation. `ep-boundary` is an agent-facing tool, so the agent should know whether the boundary was accepted/enqueued or no-op.

Routing rule:

`ep-boundary` must use the `forceFlush`-style direct-enqueue path, not the full `poolAndQueue()` path. `poolAndQueue()` is for automatic accumulated-buffer flushes and maps unknown boundary reasons through `mapBoundaryReasonToCacheReason`; routing `ep-boundary` through it could silently collapse semantic reasons to `size-limit`. Agent semantics must travel via `BoundaryReason` metadata.

Response shape implication:

Because the tool returns `flushed` and `enqueuedChunks`, it should not be pure fire-and-forget. Empty-buffer and compaction-skip cases may return quickly as no-op, but non-empty boundaries should await enqueue acceptance.

Why start here:

The current ghost-chunk protections live around `EventSegmenter`. Reusing it first lowers risk.

Expected files:

- `src/index.ts`
- `src/segmenter.ts`
- `src/types.ts`
- `test_phase4_5_cache_compaction_segmenter.ts` or a new focused test file

### Phase 1.5 — Surprise checkpoint + near-64K prefix flush

Add the near-64K auto boundary before migrating state to Go.

Initial behavior:

1. Record the latest meaningful Surprise checkpoint in `EventSegmenter` after `rpc.segmentScore(...)` returns.
2. Define “meaningful” conservatively but implement both checkpoint rules from the start: `score.isBoundary === true`, or `rawSurprise >= segmentationMinRawSurprise` even if cooldown suppressed `score.isBoundary`.
3. When buffer size approaches the existing 64K split threshold, try to split at the checkpoint.
4. Enqueue the prefix immediately.
5. Keep the suffix in `this.buffer`, recompute token count, and keep cursor/WAL consistent.
6. If prefix/suffix split cannot be done safely, fallback to the current `size-limit` path.

Chosen implementation shape:

Add a focused TS helper first: `EventSegmenter.flushPrefixAtCheckpoint(...)`.

This helper owns the split because the current suffix buffer, token counter, `lastProcessedLength`, and WAL lifecycle are all local to `EventSegmenter` today.

Flow:

1. Validate checkpoint is inside the current buffer.
2. Build `prefix = this.buffer.slice(0, checkpoint.index)`.
3. Build `suffix = this.buffer.slice(checkpoint.index)`.
4. If `prefix.length === 0`, skip checkpoint and use fallback.
5. Enqueue only `prefix` through a narrowly scoped pool/queue helper.
6. Replace `this.buffer = suffix`.
7. Recompute token count from suffix.
8. Reset `lastProcessedLength` to match the suffix state.
9. Clear the used checkpoint.
10. Keep suffix WAL/buffer live so it becomes the beginning of the next episode.

Do not use the current full `poolAndQueue()` for prefix flush because it clears the entire buffer.

If a smaller helper is added to `NarrativePool`, it must accept explicit messages and must not mutate the segmenter's live suffix state. The segmenter remains the owner of prefix/suffix splitting for v0.5.0.

Expected files:

- `src/segmenter.ts`
- `src/narrative-pool.ts` if prefix-only flush needs pool support
- `src/narrative-queue.ts` if queue reason typing needs adjustment
- `src/types.ts`
- focused segmenter tests

Resolved design point:

Resolved by review: prefix splitting belongs in `EventSegmenter` first, because `poolAndQueue()` currently clears the whole buffer. Go-backed state can come later in Phase 3/4 after the TS semantics are covered by tests.

### Phase 3 — Go-backed boundary state, TS fallback retained

Introduce a focused Go RPC for manual boundaries, but keep TS fallback.

Possible RPC:

```json
method: "narrative.forceBoundary"
params: {
  "agentWs": "...",
  "agentId": "...",
  "reason": "task-complete",
  "note": "...",
  "titleHint": "..."
}
```

The Go handler should not call LLM. It should only accept boundary metadata and coordinate deterministic state/queue work.

Guardrails:

1. Accept `context.Context` and respect cancellation.
2. Return explicit fields: `flushed`, `enqueuedChunks`, `fallbackReason`, `elapsedMs`.
3. Keep TS fallback to existing `EventSegmenter.forceFlush` during rollout.
4. Add kill switch: `EPISODIC_DISABLE_GO_BOUNDARY=1`.
5. Validate `reason` against the allowed enum.
6. Cap `note` at 2000 chars and `titleHint` at 120 chars.
7. Reject or sanitize invalid UTF-8/control-heavy text before storage.

Expected files:

- `go/main.go`
- new `go/internal/segmenter/` package, or small first step inside existing code if reviewer prefers less churn
- `src/rpc-client.ts`
- `src/segmenter.ts`
- Go unit tests
- TS fallback tests

### Phase 4 — move segmentation state to Go

Only after Phase 1-3 are stable.

Move these responsibilities carefully:

1. buffer append/dedup
2. cursor persistence
3. WAL active/staged lifecycle
4. idle timer decision state
5. time-gap boundary
6. surprise-score boundary call coordination

Do not move everything in one commit. The migration should be broken into smaller steps, each with a TS fallback.

## 10. Data safety rules

1. Never delete existing WAL files during migration unless the existing reset/compaction code path already does so intentionally.
2. Never mutate existing queue entries when adding metadata support.
3. Manual boundary with empty buffer should be a no-op success, not an error.
4. Manual boundary during compaction skip should not resurrect compacted messages.
5. Manual boundary after empty `before_prompt_build` must not initialize or consume the warm-start lifecycle.
6. Near-64K prefix flush must not lose the suffix messages.
7. Near-64K prefix flush must not advance the cursor past unflushed suffix messages unless the suffix is safely retained in WAL/buffer.
8. If the checkpoint is stale or outside the current buffer, ignore it and use the existing size-limit fallback.
9. Reset `latestSurpriseCheckpoint` to `null` in all state-reset paths: compaction, bootstrap cursor, context reset, WAL clear, manual full flush, and successful prefix flush.
10. If compaction skip is active, `ep-boundary` should return accepted/no-op with a clear reason instead of forcing a new segment from compacted/ignored messages.

## 12. Risk list

### R1 — note contamination into transcript

Risk: boundary note accidentally enters `rawText` and becomes false memory.

Mitigation: separate fields, tests asserting `rawText` excludes note.

### R2 — ghost chunk regression

Risk: manual boundary bypasses cursor/WAL protections.

Mitigation: Phase 1 reuses current `EventSegmenter`; Phase 4 only after tests and soak.

### R3 — tool overuse

Risk: agent calls `ep-boundary` too often and creates tiny episodes.

Mitigation: no-op if buffer empty; optional cooldown later if logs prove overuse.

### R4 — Go migration too broad

Risk: moving buffer/cursor/WAL in one shot breaks restart safety.

Mitigation: split Go migration into small commits with TS fallback and kill switch.

### R5 — schema drift

Risk: TS queue item and Go queue item diverge.

Mitigation: add mirrored tests and keep fields optional.

### R6 — near-64K prefix flush loses the tail

Risk: near-64K auto boundary sends the prefix but drops the messages after the checkpoint.

Mitigation: add tests that assert suffix messages remain in buffer/WAL and are included in the next episode.

### R7 — stale checkpoint cuts the wrong place

Risk: checkpoint points to an old buffer index after compaction, warm-start, or manual flush.

Mitigation: clear checkpoints on compaction, bootstrap cursor, context reset, WAL clear, manual full flush, and successful prefix flush. Validate checkpoint index against the current buffer before use.
