# v0.5.0 Addendum — Timestamped Narrative Transcript

> **Status**: Implemented locally — focused verification passed; code-reviewer APPROVE
> **Created**: 2026-07-12
> **Scope**: Add device-local date/time context to the transcript passed to the narrative LLM. No change to episode retrieval, embeddings, boundary decisions, or Go sidecar behavior.

---

## 1. Goal

The narrative LLM should see when each human/assistant message occurred, not only who said it.

Target format:

```text
(2026-07-05 Sunday)
[19:30] user: A
[19:32] assistant: B
[21:10] user: C
```

When local calendar date changes within one narrative job:

```text
(2026-07-05 Sunday)
[19:30] user: A
[19:32] assistant: B
[23:50] user: C
[23:57] assistant: D

(2026-07-06 Monday)
[00:05] user: E
[00:07] assistant: F
```

This gives the narrative model a real timeline without making the model infer elapsed time from wording alone.

### Non-goals

1. Do not change `ep-boundary`, boundary notes, Surprise scoring, idle/time-gap gates, or near-64K behavior.
2. Do not invent timestamps where OpenClaw did not supply one.
3. Do not add a user-facing time-zone setting. Runtime device-local time is the product requirement.
4. Do not turn queue `createdAt` into a message timestamp; it is a queue-record timestamp and has different meaning.

## 2. Evidence from current code

### A. Live messages already carry an optional source timestamp

`src/segmenter.ts:15-19` defines the live `Message` shape with `timestamp?: string`.

`src/segmenter.ts:551-558` already parses these timestamps for the existing time-gap boundary calculation.

Meaning: message time is already an input fact in the live path. This work exposes that fact to the narrative LLM; it does not create a second clock.

### B. Current narrative transcript discards the timestamp

`src/narrative-pool.ts:64-75` builds `rawText` as only `role: text`.

Meaning: a message at 19:30 and a message at 23:50 are currently indistinguishable to the narrative LLM except from their words and order.

### C. The narrative LLM receives `rawText` unchanged

`src/narrative-worker.ts:933-935` assigns `item.rawText` to `conversationText` and resolves the user prompt from it.

Meaning: formatting the transcript before it becomes a queue item is sufficient. Neither custom prompt file needs a new variable.

### D. Cold-start import currently loses source timestamps

`src/rpc-client.ts:1038-1063` parses session JSONL into `{ role, content }` only.

OpenClaw v2026.4.5 documentation (`skills/session-logs/SKILL.md`) specifies session JSONL entries as having top-level `timestamp` plus `message.role` and `message.content`.

Meaning: cold-start import must preserve `entry.timestamp`; otherwise old sessions cannot receive the new date/time layout even though the source file carries it.

### E. Long transcript splitting needs date context preserved

`src/narrative-queue.ts:114-238` splits `rawText` line-by-line near `SOFT_TOKEN_TARGET`.

With date headers, a later chunk can otherwise begin at `[HH:mm]` without its applicable `(YYYY-MM-DD Weekday)` header.

Meaning: every queue chunk that contains timestamped lines must start with its effective date header, even when the original transcript was split at 48K/64K boundaries.

## 3. Design decisions

### 3.1 Time zone

Format source ISO timestamps in the runtime device's local time zone.

Implementation uses the Node runtime's resolved local zone:

```ts
Intl.DateTimeFormat().resolvedOptions().timeZone
```

Then format explicitly in that zone. This means Kasou uses Kasou's configured local zone, rather than UTC or the Windows developer machine's zone.

Tests inject `Asia/Jakarta` into the pure formatter so assertions stay deterministic regardless of where they run.

### 3.2 Date header

Emit exactly one date header before the first valid timestamped message of a local date:

```text
(YYYY-MM-DD Sunday)
```

Weekday is English (`Sunday` through `Saturday`) as requested. Time is zero-padded 24-hour local `HH:mm`.

No header is emitted for a message with no valid timestamp.

### 3.3 Message lines

For timestamped `user` and `assistant` messages:

```text
[HH:mm] user: text
[HH:mm] assistant: text
```

For non-primary roles, preserve the existing behavior: content remains available but is not given a fabricated user/assistant label.

For multi-line content, only the first line receives the `[HH:mm] role:` prefix. Continuation lines retain their original text and remain part of the same message.

### 3.4 Missing or invalid timestamps

Never fabricate time.

If `timestamp` is absent or invalid:

```text
user: legacy message without a source timestamp
```

No `[HH:mm]` and no new date header are added. A single summary debug/warn log per flush may report the count of omitted timestamps, but must not log message contents.

### 3.5 Boundary notes remain separate

`boundaryNoteBlock` stays outside `conversationText`, exactly as v0.5.0 Phase 2 designed it.

Timestamp formatting applies only to transcript messages. It does not add a time prefix to `Agent Boundary Note` and does not change `rawText` contamination protections.

## 4. Implementation plan

### Phase A — Pure reusable transcript formatter

Create `src/narrative-transcript.ts`.

Provide a pure formatter that accepts normalized message input:

```ts
type TranscriptMessage = {
  role: string;
  text: string;
  timestamp?: string;
};

formatNarrativeTranscript(messages, { timeZone? }): string
```

The module also exports one lower-level pure helper, conceptually:

```ts
formatTranscriptMessageLines(message, { timeZone? }): string[]
```

It returns the exact timestamped role line plus any continuation lines for one normalized message, but does not emit date headers. `formatNarrativeTranscript()` owns date-header insertion by composing this helper over the full ordered message list.

This is intentional: `src/narrative-queue.ts` imports this pure module to rebuild exact `lineToRole` keys from `messages[]`. The dependency direction is one-way:

```text
narrative-pool ─┐
narrative-queue ├─> narrative-transcript (pure; imports neither caller)
rpc-client      ┘
```

There is no `segmenter`/`NarrativePool` import from the new module, so this does not create a circular dependency.

Responsibilities:

1. Parse/validate ISO timestamps safely.
2. Convert valid times to the selected local zone.
3. Insert date headers only when local date changes.
4. Emit `[HH:mm] role: text` for timestamped `user` / `assistant` entries.
5. Preserve the current unprefixed output for missing/invalid timestamp and non-primary role entries.
6. Return no queue or OpenClaw types; this module must remain deterministic and independently testable.

Do not move `extractText()` out of `segmenter.ts` in this phase. Callers normalize OpenClaw content before calling this formatter, avoiding a new circular dependency between `segmenter` and `narrative-pool`.

### Phase B — Live transcript path

Modify `src/narrative-pool.ts` `buildFlushItem()`.

1. Continue using the existing `extractText(m.content)` path.
2. Convert pool messages into `TranscriptMessage` values with their original `m.timestamp`.
3. Replace the inline `role: text` join with `formatNarrativeTranscript(...)`.
4. Preserve `messages: [...this.buffer]` unchanged for the segmenter and queue structured path.

Expected live output changes only in `rawText` / `conversationText`; original in-memory `Message` objects stay untouched.

### Phase C — Queue splitting compatibility and date-header carry-forward

Modify `src/narrative-queue.ts`.

1. Extend `detectRoleLine()` to recognize both existing and timestamped role lines:

```text
user: text
[19:30] user: text
```

2. Update the structured `lineToRole` map to use the exact timestamped first line generated for a message, while preserving role assignment for continuation lines.
   - Import the Phase A `formatTranscriptMessageLines()` helper; never recreate timestamp formatting in the queue.
   - Use its exact first line as the Map key and map its continuation lines to the same source role.
   - This preserves the existing structured guard: literal `user:` text inside an assistant message remains assistant-owned, even with an `[HH:mm]` prefix.
3. Track the most recently seen date header while scanning lines.
4. On a split, reset `currentLines`/`currentTokens` and retain the active date header as `pendingDateHeader`.
5. Before adding the next timestamped line to an otherwise header-less new chunk, prepend `pendingDateHeader` to `currentLines` and add `estimateTokens(pendingDateHeader)` to `currentTokens` first.
6. If the next line is already a new date header, add it normally and replace the active header; do not duplicate it.
7. Do not prepend headers to chunks that contain no timestamped messages.
8. `pushChunk()` continues to calculate its final `estimatedTokens` from the actual joined text, so the carried header is included both in pre-split threshold accounting and stored queue metadata.
9. Preserve existing fallback behavior for raw transcripts with no timestamps (legacy queue items, manual data, tests).

This phase is necessary because queue items are narrated independently. A chunk that starts on `[00:05]` must still tell the LLM which day `00:05` belongs to.

### Phase D — Cold-start and archive paths

Modify `src/rpc-client.ts`.

1. Change `parseJsonlToMessages()` to return optional `timestamp`.
2. Preserve top-level `entry.timestamp` from valid OpenClaw message entries.
3. Route cold-start `rawText` through `formatNarrativeTranscript()` rather than the current manual `${role}: ${content}` join.
4. Preserve the no-API fallback compatibility; functions accepting cold-start messages must tolerate the new optional field.

Modify `src/archiver.ts`.

1. Route large-gap narrative queue text through the same formatter.
2. In the JSONL path, copy the **top-level** session entry timestamp into the parsed message explicitly:

   ```ts
   allMsgs.push({ ...obj.message, content: contentStr, timestamp: obj.timestamp ?? obj.message?.timestamp });
   ```

   OpenClaw v2026.4.5 documents `timestamp` at the entry level. `obj.message?.timestamp` is only a defensive compatibility fallback, not the primary source.
3. In the non-JSONL `session.messages` path, preserve an existing `message.timestamp` when present; undefined remains the deliberate timeless fallback.
4. Keep fallback archive JSON unchanged; this change only formats LLM-bound queue text.

### Phase E — Kasou narrative prompt wording

Update only the custom user prompt at:

`~/.openclaw/prompts/episodic_claw_narrative_user.md`

Add a short instruction near the transcript rules:

```text
ログに日付・時刻がある場合、出来事の時系列を正確に扱う。重要な時間差・日付跨ぎは自然に本文へ織り込むが、全発言の時刻を機械的に列挙しない。
```

Do not change the custom system prompt. The system prompt already asks for concrete log facts; user prompt wording is sufficient and avoids duplicated rules.

## 5. Compatibility and regression rules

| Case | Expected behavior |
|---|---|
| Live OpenClaw message has ISO timestamp | Date header + local `[HH:mm]` role line |
| Legacy/cold-start message lacks timestamp | Current `role: text` layout; no invented time |
| User turns off time-gap auto boundary | Formatting still shows time; this setting controls boundaries, not transcript facts |
| User turns off Surprise auto boundary | Checkpoint and timestamp formatting remain independent |
| near-64K prefix flush | Prefix and retained suffix preserve timestamp/date structure |
| Queue chunk crosses midnight | Later chunk begins with effective local date header |
| Custom narrative prompt | Receives formatted text through existing `{conversationText}`; no new template variable needed |
| `saveRawLog` diagnostic `.raw.md` | Receives the same timestamped `rawText`; this is an intentional diagnostic-format improvement |

## 6. Risks and mitigations

### R1 — Prompt token growth

Risk: `[HH:mm]` on every primary message and date headers increase prompt size.

Mitigation: `HH:mm` adds only six visible characters plus delimiters per message; date headers occur once per local day. Existing near-64K and hard-cap splitting stay enabled. Do not add seconds or time zones to every line.

### R2 — Incorrect local calendar date at midnight

Risk: formatting source UTC directly would put Kasou midnight messages under the wrong date.

Mitigation: explicitly format in the runtime-resolved device time zone; test a UTC-to-Asia/Jakarta midnight transition.

### R3 — Chunk loses date context

Risk: the queue splits after a date header, so a later isolated LLM job only sees `[00:05]`.

Mitigation: Phase C carries the active date header into every timestamped continuation chunk and tests forced splitting.

### R4 — Timestamp prefixes break role-aware chunking

Risk: current role detection expects `user:` at column zero.

Mitigation: update both regex fallback and structured mapping; retain literal-`user:`-inside-assistant regression test.

### R5 — Missing timestamp becomes false historical fact

Risk: a fallback that uses queue time would make the LLM believe an old message occurred when it was enqueued.

Mitigation: no source timestamp means no timestamp output. Queue `createdAt` is never reused.

## 7. Acceptance criteria

1. Kasou narrative LLM sees the requested same-day and day-crossing layout for timestamped messages.
2. The formatting uses Kasou runtime local time, not UTC.
3. Missing/invalid timestamps remain visibly timeless; no fabricated time exists.
4. Custom prompt files continue to work without a new placeholder.
5. Long queue chunks preserve their effective date context and role-aware chunking.
6. `ep-boundary`, boundary notes, auto-boundary gates, Surprise checkpoint, and near-64K safety behavior remain unchanged.
7. All listed tests pass and `@code-reviewer` gives final APPROVE.
